# The console

The console's files, the rules every stop's component follows, the payload keys the stops read, and the map's and the desk's editors.

Moved verbatim from `reports/CLAUDE.md` on 2026-10-11, when CLAUDE.md became a map. A part named in bold elsewhere in this text, such as **The map**, may now sit in another file in `docs/architecture/`; CLAUDE.md lists which file holds which part.

## Console Frontend

**Access:** `http://localhost:3001/console` (local) or `https://console.aboutlastnightgame.com/console` (production)

**Stack:** React 18 + Babel standalone via CDN. Zero build process — edit JS/CSS and refresh.

**Architecture:** Single-page app with `useReducer` state machine. Each `.js` file is a `<script type="text/babel">` tag with its own Babel scope. Components register on `window.Console` namespace.

### Modifying Checkpoint Components

Each checkpoint component follows the same pattern:
1. Registers on `window.Console.checkpoints`
2. Receives `{ data, sessionId, theme, onApprove, onReject, onRollback, dispatch, revisionCache, pendingEdits, pendingNote }` props (`pendingNote`: the stop's note box, restored beside its edits after a remount)
3. Renders checkpoint-specific UI from `data`
4. Calls `onApprove(payload)` / `onReject(payload)` with the checkpoint-specific payload, or `onRollback(checkpointType)` to open the rollback modal

**Conventions:** `const` not `var`, direct destructured imports (no aliasing), `safeStringify` instead of `JSON.stringify`, CSS utility classes over inline styles, aria-labels on interactive elements, functional state updaters for Set manipulation, `useEffect` reset on data change.

`Article.js` validates the bundle on the desk through ONE local `gateEdits` helper that both the approve and the send-back call (the send-back passes `verb: 'send'`, so its message reads "Cannot send …"); a new path that sends edits goes through it too. Its gate is the desk's (task 4.3): it runs on every approve and every send-back, edited or not, on the bundle on the desk, with the desk's checks (`articleDeskLogic.deskProblems`) beside `validateBundleShape`, and its JSON path routes through it too. The map (`Outline.js`, task 4.9) has one send path, `send(action)`, which Approve and Send back both take: it holds the map on screen to `mapProblems`, the gate's decisions, then builds `mapPayload`; the map has no JSON editor. `__tests__/unit/console-edit-gates.test.js` pins both.

**An open editor or an unadded line holds the stop's actions** (task 4.14d). Text in an editor's form, the map's add line, the story meeting's add-a-thread line or the desk's JSON editor is in no payload until the director saves or adds it; before this task the stop's buttons sent without it, and no screen warned. `console/unsaved-input-logic.js` `unsavedInputLine(stop, open)` is the one rule. Each stop asks it once per render for each set of buttons that sends one thing, with what it has open: the meeting, about its add line holding text; the map, about an open editor (a move's named in the line by its words, never its id) or an add line holding text (Outline.js's `adding`, `{slot, move, players}`; brief 1F); the desk twice, since it sends two things. The desk's Approve and Send back (`'article'`, answer `held`) send the bundle on the desk, so they wait for any open editor and for JSON typed in the JSON editor (its text against `jsonSeed`, the text it opened with). The JSON editor's Save & Approve (`'article-json'`, answer `jsonHeld`) sends that JSON, so it waits for any open editor and for any change made on the desk after the JSON editor opened (`jsonSeededAt` against `deskVersion`); its line says to close the JSON editor and open it again. With an editor open too, its line names every step in order (task 4.14g): cancel the edit, or save it and then close the JSON editor and open it again, since a save changes the desk and a cancel does not; once the desk has changed since the JSON editor opened, either step is followed by closing and opening it again. `applyDesk` counts each change to the desk in `deskVersion`; a new way of putting a bundle on the desk counts it too, or this hold misses the change. While an answer holds, its buttons are disabled (Approve, Reweave, Send back, the two answers to `meetingApproveAsk`, the desk's JSON Save & Approve), its line shows beside them, and every function that sends a payload returns before building one (the meeting's and the map's `send`; the desk's `handleApprove` and `handleReject` on `held`, `handleJsonApprove` on `jsonHeld`). A new path that sends a payload checks its answer the same way, and new input that reaches a payload only through its own button goes to the rule with the rest. The desk's actions are one list, `checkpoint-view-logic.js` `DESK_ACTIONS`, which `reviewPayload`'s guard, this line and the harness's `STOP_ACTIONS` read, as the meeting's and the map's are `MEETING_ACTIONS` and `MAP_ACTIONS` (task 4.14g).

**Nor does any other control drop what was typed** (task 4.14g). A control that would close or replace an open editor, or an add line holding text, waits for it as the actions do: the component asks `unsavedInputLine(stop, open, control)` once per render for each kind, about the same `open` its actions are asked about. At the desk a pencil opens its editor in place of the open one (`startBlockEdit`, `startHeadingEdit`, `startSidebarEdit`, `startHeadlineEdit`), and a move, a delete or an insert puts a new bundle on the desk through `applyDesk`, which closes it, so each waits for any open editor (`'edit'`, `'move'`, `'delete'`, `'insert'`; answers `editHeld`, `moveHeld`, `deleteHeld`, `insertHeld`). None of them closes the JSON editor, so typed JSON holds none of them. On the map a pencil (`open`), Edit the words on a selected card among them, waits for an open editor (`'edit'`, `editHeld`), and "+ Add a move" (`openAddLine`) for an add line holding text (`'add'`, `addHeld`). On the board (piece 4, R9) selecting something else (`select`, `'select'`, `selectHeld`) and every other control on the selected card, the selected move in the tray or the selected photo (each through `whenFree`, `'move'`, `moveHeld`: Move up, Move down, Move to another section, Put a photo beside it, Leave it out, Take it out, Bring it back, a photo's places) wait for both, an open editor and a typed add line, so the board never changes under what the director typed. Closing what is selected waits for nothing, and neither does a drop: an editor is keyed by its line, and a card whose editor is open does not drag. The story meeting has no such control. A held control is disabled with the line as its tooltip (`utils.js` `editBtn(onClick, held)`, `deskButton`'s `held` option), its handler returns first, and the line shows under the open editor (at the desk through `withMarks`, which every desk editor renders through) or the add line; on the board a held click shows the line on the card or photo it reached (`heldAt`, `heldHere`), and a selected card's line sits under its controls. A new control that would close or replace what is open joins the rule's `CONTROLS` and checks its answer the same way. A hold is not an error: each held line is rendered by the stop's `heldLine` (the meeting writes its one out) with the class `.held-line`, never `.validation-error`'s red, which stays for a real refusal. `__tests__/unit/console-held-actions.test.js` pins the wiring, and `console/__tests__/unsaved-input-logic.test.js` the rule.

**`onRollback` is the only way a checkpoint may open the rollback modal.** It is the same `setRollbackTarget` callback the stepper uses, so Confirm goes through the existing streaming rollback. A component must NOT dispatch its own rollback action — ArcSelection's zero-arc dead end dispatched `SHOW_ROLLBACK`, which no reducer handles, so the only offered recovery logged `[state] Unknown action` and did nothing.

### The map's and the desk's editors (`Outline.js`, `Article.js` + `outline-edit-logic.js`)

The map's editors (`Outline.js`, task 4.9) are **thin wrappers**: each seeds `useState` from `EditLogic.init*(line)`, composes the module-scope `TextField` and `actionsRow`, and on save merges `EditLogic.build*(form, …)` into the map with `EditLogic.merge*`, which writes the line into the map as it is now. `EditLogic` = `window.Console.outlineEditLogic` (aliased at module scope in both `Outline.js` and `Article.js`).

- **All build/merge/validate logic and the map's moves are PURE and live in `outline-edit-logic.js`, not in the React components.** A build starts from a copy of its line and keeps what the director typed as typed; a move's build writes its title, its summary and its people (the form `{move, synopsis, players}`) and keeps every other field as it is (brief 1D; piece 4), so a move the director added keeps the shape they gave it. The add line at a column's foot takes a move's title and its people, under `adding.move` and `adding.players`, into `addBeat` (brief 1F). The board's moves (moving a card, leaving it out, bringing it back, placing a photo) are the edit logic's too, each called from one handler in `Outline.js` that its button and its drop share (see **The map on screen**).
- **Edited maps are held to the gate's decisions before they are sent** (the B7 gate): client-side through `ViewLogic.mapProblems` (`EditLogic.validateOutlineShape(map, theme, slots, shown, leftOut)`, the map's gate `validateMapShape`: the director-side schema (since brief 1D a beat's keys, `BEAT_KEYS`, and each piece of its evidence, held to `lib/evidence.js` by the copies `EVIDENCE_PIECE_REQUIRED`, `EVIDENCE_PIECE_STANCES` and `EVIDENCE_NAMED_SOURCES`), then the gate's rule for a repeat, then its rule for a left-out photo the director put at the top (task 4.14b); dependency-free, blocks both buttons and renders `.validation-error`), and server-side in `buildResumePayload` (`lib/map.js` `mapResume`, against the director-side map schema and `directorMapProblems`; brief 4.6). Distinct from the generation-time `validateOutlineStructure` removed in 8.23: this gates HUMAN edits.
- **The article stop is the director's desk** (phase 4, task 4.3; spec 2026-10-02 section 6.3). `console/article-desk-logic.js` (`window.Console.articleDeskLogic`, dual-export, loaded before `Article.js`) holds every decision behind it, pure and node-tested:
  - the block operations, each returning a new bundle: `insertBlock` (a paragraph or a quote; photos and cards come from the record), `moveBlock`, `moveToSection` and `stepTarget` (within a section or across sections), `deleteBlock`, and the edits in place, a section's heading included (`setSectionHeading`; the byline edit keeps the guest reporters' credit, one string, each credit joined with " || " since phase 17);
  - the Key Evidence entries' operations (task 4.14c; spec 6.3: cards can be moved or deleted, and C9 puts every inline card in the sidebar too): `deleteSidebarCard`, and `moveSidebarCard` with `sidebarStepTarget`, one place up or down within the sidebar, which each entry's row in `Article.js` offers beside its pencil (`sidebarControls`; the delete takes two clicks, as a block's does);
  - the checks: `deskProblems`, which is `emptyBlocks` (whitespace-only text included) and `headlineProblems` against `HEADLINE_LIMITS`, the schema's limits, which a test holds equal;
  - the naming rule (task 4.3b): `pairSectionBlocks` pairs a section's blocks across two versions, and `stayingInSection` keeps the longest run that kept its order; every other pair is a block the director moved, a move when unchanged and a cut and an addition when changed; a photo, a card or a reference pairs only with a block of its own name, so two the director swapped are two moves, each with its own caption or text (task 4.5d);

- **The pencil has two reveal modes** (pinned by `__tests__/unit/console-editable-pencils.test.js`):
  - `article-block--editable` alone → hidden until `:hover` / `:focus-within`, for a full-width host whose own first line reaches the top-right corner (an always-on corner button landed on the article's prose at 19 of 54 rendered blocks).

  The **article** desk uses neither: each piece of the article is a `deskRow` whose pencil and block controls (move, delete, insert) sit in `.desk-rail`, a grid column of its own beside it, so every editor is visible and none covers the prose.
