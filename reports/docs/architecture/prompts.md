# Themes, prompts and the record

The theme system, the rule set, how prompts are assembled, what LangGraph and the SDK each do, the data wiring, and the record view every writer and judge reads.

Moved verbatim from `reports/CLAUDE.md` on 2026-10-11, when CLAUDE.md became a map. A part named in bold elsewhere in this text, such as **The map**, may now sit in another file in `docs/architecture/`; CLAUDE.md lists which file holds which part.

### Theme System

The pipeline supports multiple report themes via `state.theme`. Each theme produces a different article style with its own voice, structure, and visual design.

| Theme | Output | Voice | Length | Narrator |
|-------|--------|-------|--------|----------|
| `journalist` | NovaNews investigative article | First person: C12: Nova works the case in front of the reader | About 1,500 words (C4) | Nova |
| `detective` (parked, R1) | Detective case file | Third-person investigative | ~750 words | Det. Anondono |

**Theme-aware layers:**
- `lib/theme-config.js` — per theme: its NPCs (the canon lines), its display constants, its map slots (`map.slots`, read through `mapSlotsOf`; phase 4, brief 4.6: the journalist's six; the parked detective has none, R1), its rules folder (`rules`) and its identity lines (`identities`, read through `identityLineOf`; briefs 4.13 and 4.13b)
- `lib/rule-set.js` — each theme's rule set, from the rules folder its config names (`loadRuleSet(call, {theme})`, `loadModeBlock(mode, {theme})`; R14), which every writer, rework and judge of the new stages reads
- `lib/theme-loader.js` — Resolves the image calls' prompt files from `.claude/skills/{theme}-report/references/prompts/`
- `lib/prompt-builder.js` — Builds the writers' prompts from the theme's files: every writer's and judge's system prompt opens through `systemPromptOpening(theme, call, sessionConfig)`
- `lib/map.js` — The map's schema for the theme (`mapSchemaFor`: `lib/schemas/outline.schema.json` with the theme's slots)
- `templates/{theme}/` — Handlebars templates (layouts, partials, content blocks)
- `.claude/skills/{theme}-report/assets/` — CSS variables, layout, components, JS per theme
- `lib/workflow/nodes/evaluator-nodes.js` — The judges: one set of truth criteria for every theme (`getPhaseCriteria`), each judge opening with the theme's identity line and rules

**Adding a new theme.** A theme is files: the weave writer, the map writer, the article writer, their reworks and the two judges read their rules, their mode block and their identity line through the theme they hold (phase 4: the integrator's ruling R14, briefs 4.13 and 4.13b), and the map reads its slots from the theme's config. A theme supplies:
1. **Its config entry** in `THEME_CONFIGS` (`lib/theme-config.js`): its NPCs; `display.printsHero`, which `printedHero` throws without; its map slots (`map.slots`, each with its key, its label on the screen and its default heading), without which it has no story map; and `rules` and `identities` (below).
2. **Its rules folder**, the folder `rules` names, relative to `reports/`: `world.md`, `truth-rules.md`, the eight craft files `RULE_SET_CALLS` names (`lib/rule-set.js`), and the two mode files, `mode-on-site.md` and `mode-remote.md`. Every call reads it through `loadRuleSet(call, {theme})`, and the mode block through `loadModeBlock(mode, {theme})`; a theme with no folder, or a missing or empty file a call reads, throws, naming the theme, the folder or the file. The journalist's is `.claude/skills/journalist-report/references/rules/`.
3. **Its identity lines**, `identities` in its config, read through `identityLineOf(theme, call)`: one line for each call `IDENTITY_CALLS` lists. `IDENTITY_CALLS` derives from `RULE_SET_CALLS`: each call, and each writer's `-rework` beside it, while a judge's call opens `judge-` and has no rework (`arc` is the weave writer, `outline` the map writer, `judge-arc` the story meeting's fact check). So a call added to the rule set needs a line in every theme's `identities`. The theme names its narrator, its publication and its form of output there, and no identity line sits in code (a source scan in `lib/__tests__/theme-rules.test.js` holds it). A writer's or a judge's line is a whole sentence. A rework's line opens its rework rules, and code completes it with the rework's task (`": the director sent it back, ..."`, `" after an automatic check ..."`), so it is a clause that ends on a word: `identityLineOf` refuses anything else, naming the theme and the call (`RUNS_ON_INTO_ITS_TASK`). `lib/__tests__/theme-config.test.js` runs every call of every theme that names a rules folder.
4. **Its templates** in `templates/{theme}/` (layouts and partials), its assets in `.claude/skills/{theme}-report/assets/`, and its image calls' prompt files in `.claude/skills/{theme}-report/references/prompts/`.

Its schemas come from these: the map's is `lib/schemas/outline.schema.json` with the theme's slots, built in code (`mapSchemaFor(theme)`, and `directorMapSchemaFor` from it), while the weave's (`WEAVE_SCHEMA`) and the article's (`content-bundle.schema.json`) serve every theme.

A second theme still edits code in four places today (the Themes known item): `VALID_THEMES` in `server.js`; the image calls' lists in `lib/theme-loader.js` (`ALL_PROMPTS`, `PHASE_REQUIREMENTS`); `rosterWithPronounsSection` (`lib/prompt-builder.js`), which builds the roster for `'journalist'`; and the article instruction's byline (`_journalistArticleUserSections`), which names Nova and NovaNews. Code from before phase 4 names Nova in more places, such as the fact check's messages, the truth questions' wording and the parse schemas.

The parked detective (R1) keeps its config and the 11 prompt files `ALL_PROMPTS.detective` lists as the worked example of a second theme. It names no rules folder and no identity line, so every call of the new stages fails loud for it, naming the theme, and `/start` refuses it with its line in `PARKED_THEMES` (`server.js`).

### Prompt Architecture

**The rule set (phase 3, tasks 3.1 and 3.8).** The journalist's rules are model-facing Markdown files in `.claude/skills/journalist-report/references/rules/`, written from the rule-set spec (`docs/superpowers/specs/2026-09-30-rule-set.md`): `world.md` (the article's purpose, the world, how a memory moves through the game), `truth-rules.md` (T1 to T15: the floor), eight `craft-*.md` files (C1 to C19: the engine, the craft rebuilt around the article's form in spec round 7) and the two mode files. The craft files group the items by the writer's job: `craft-story` (C1, C3, C16), `craft-form` (C2, C5, C6, C17, C18, C19, C14), `craft-material` (C8, C7, C10, C11), `craft-voice` (C12), `craft-judgement` (C13), `craft-telling` (C4), `craft-cards` (C9) and `craft-questions` (C15); task 3.8 regrouped the craft into them and deleted five of the ten files it had been split into. Each call reads the craft files `RULE_SET_CALLS` gives it, every list in one order, story, form, material, judgement, cards, questions, telling, voice, so the two that say how the prose reads sit last, before `<DIRECTOR_GUIDANCE>` (phase 17, R2; `docs/superpowers/specs/2026-10-18-the-writing-design.md` sections 3 and 4; the phase 4 spec's section 11 set the lists before): the arc writer, which writes the weave, story, form, material, judgement, questions and voice; the map writer every file but questions (`OUTLINE_CRAFT`; phase 4, brief 4.6); the article writer all eight; the story meeting's fact check (`judge-arc`) and the article judge (`judge-article`, brief 4.7a) none, the world and the truth rules alone. The arc writer and the map writer read the voice since phase 17, for the lines the article prints that they write: an angle's headline, the map's deck and its headings. An item is its heading (`## C16. …`, `## T8, remote: …`), stated once across the files (T8 once in the truth rules and once in each mode file), and a body may point at another item ("(T1)", "as T5 sets out"). `lib/__tests__/rule-set.test.js` lints the files: each item once, every pointer naming an item the set states, no em-dash, no gendered Nova, nothing on `lib/__tests__/fixtures/removed-phrases.js`, no old example accounts or sums. `lib/rule-set.js` is synchronous (readFileSync, cached for the process, so an edited rule file reaches the prompts on the next server start), and reads the rules folder of the theme the caller holds (`rulesFolderOf(theme)`, the folder `THEME_CONFIGS[theme].rules` names; R14, brief 4.13): `loadRuleSet(call, {theme})` for `arc`, `outline`, `article`, `judge-arc` or `judge-article` returns `{core, craft}`, the world then the truth rules and the call's craft files (`RULE_SET_CALLS`), each wrapped in one tag named after its file; a reworker passes its writer's call; a missing or empty file throws, named. `loadModeBlock(mode, {theme})` returns the mode file in one tag named after it (`<mode-remote>`), as `loadRuleSet` wraps each file, so the system prompt's text after the block is not read as part of its "## T8" section. Tests pass `{root}`, and the pinned renders point every theme's folder at the one-line stubs in `lib/__tests__/fixtures/rules/` (`setDefaultRulesRoot`), so a rule-text edit never moves a pin. A theme whose config names no rules folder, such as the parked detective, throws, named. Since 3.2 the outline and article writers and their reworkers read it, placed by the integrator's ruling: `core` (the world, the truth rules) in the system prompt right after the mode block, and `craft` last in the user prompt, after the data and before `<DIRECTOR_GUIDANCE>`. The inline text the rule set states or contradicted went with it (the old financial block's "Blake now possesses all buried memories", the agency rule that kept Blake out of the room, the fixed section table, every arc in every section, pull quotes, the voice self-check, and the JSON shape restated in the outline prompt's own words, M27), and the schema descriptions are shape only. The map writer embeds the map's schema for its theme (`mapSchemaFor`, `lib/map.js`) as `<SCHEMA>`, before the craft files, as the article writer embeds the content-bundle schema (fix 3.2b); the detective has no map (R1).

**Prompt Loading (ThemeLoader):**
- Prompts stored in `.claude/skills/{theme}-report/references/prompts/`
- `PHASE_REQUIREMENTS` and `ALL_PROMPTS` are keyed by theme (phase 3, 3.2). The journalist's prompts folder holds only the three image calls' files (its eight craft files are deleted; its writers read the rule set); the parked detective keeps its 11 files and its article phase list (its outline phase went with its outline stage, R1)
- Cached at startup, loaded per-phase via `lib/theme-loader.js`

**Prompt Assembly (PromptBuilder):**
- `lib/prompt-builder.js` assembles complete prompts per theme
- Uses **XML tag format** for prompt sections (Commit ba3f534)
- `labelPromptSection()` wraps content in `<tag>content</tag>` format
- Token savings: ~560 tokens per article generation
- Cross-references name an item and the tag of the file that states it: "as C16 (`<craft-story>`) sets them out"
- Methods: `buildOutlinePrompt()`, `buildArticlePrompt()` (arc generation lives in `arc-specialist-nodes.js`, not in PromptBuilder; the dead `buildValidationPrompt` and `buildRevisionPrompt` went in phase 3, M25). Since phase 2 (2.3) each writer is `build{Outline,Article}SystemPrompt()` + `build{Outline,Article}UserSections(...)` + its `<DIRECTOR_GUIDANCE>` tail; the reworkers call the first two

For XML format details, see `PIPELINE_DEEP_DIVE.md#xml-tag-format-migration-commit-ba3f534`.

**Recency Bias Pattern:** Rules placed LAST in user prompt for maximum salience (for the journalist, the craft files; the world and the truth rules are in the system prompt), with only the director's standing notes after them. The article writer's user prompt (brief 4.7b):
```
<SETTLED_WEAVE>...</SETTLED_WEAVE> <STORY_MAP>...</STORY_MAP>  ← the task's inputs, first, then the task
<DATA_CONTEXT>...</DATA_CONTEXT>
<GENERATION_INSTRUCTION>...</GENERATION_INSTRUCTION>
<craft-story>...</craft-story> ... <craft-questions>...</craft-questions>  ← Most recent rules = highest weight
<DIRECTOR_GUIDANCE>...</DIRECTOR_GUIDANCE>  ← the standing notes, last of all
```

### SDK vs LangGraph Responsibilities

| Aspect | Claude Agent SDK | LangGraph |
|--------|-----------------|-----------|
| AI Calls | `sdkQuery()` makes all Claude requests | Routes between nodes |
| Structured Output | JSON schemas via `jsonSchema` param | N/A |
| State Management | N/A | 88 state fields with reducers |
| Checkpointing | N/A | MemorySaver/SqliteSaver |
| Human Approval | N/A | Native `interrupt()` pattern |
| Revision Loops | N/A | Conditional edges with caps |
| Timeouts | AbortController per call | N/A |

**Data Flow:**
```
State → Node extracts context → PromptBuilder assembles prompt
→ sdkQuery() calls Claude → Returns structured output → Node updates state
→ LangGraph routes to next node (or checkpoint)
```

**Data Wiring (Commit 6ffeef8):**
- Memory tokens use `fullDescription` field (rich second-person narrative)
- Fallback chain: `fullDescription` → `content` → `description` → `summary`
- `extractFullContent()` helper ensures full quotable content (not summaries)
- Fixed in 3 locations: preprocessor, token routing, arc evidence packages (the packages went in phase 4, brief 4.6; R5)

**The record view (phase 2 slice 2.1):** `lib/prompt-renderers/record-view.js` renders the evidence bundle as one `<RECORD>` section. Each exposed document is `<document id kind name owner layer="exposed">` with its full text as the body; the buried memories follow only as sales on the investigation's timeline, `<investigation-timeline>` (phase 3, brief 3.5, in place of the old `<buried-transactions>`; `<morning-timeline>` until phases 14 and 15, brief E, R8, since a session played before 5 PM runs in the afternoon; the function names `buildMorningTimeline` and `renderMorningTimeline` stay): `buildMorningTimeline(bundle, sessionConfig)` merges the bundle's sales (account, amount and time and nothing else; a memory no one sold has no line), the evidence log (`sessionConfig.exposures`, only for memories the bundle holds as exposed: the document id and the name on the turn-in) and the classified adjustments (`sessionConfig.adjustments`: the first-burial bonus, transfers) in time order, every logged time on the session clock (`lib/prompt-renderers/session-clock.js`: the parse stamps `sessionConfig.sessionClock`, decided on the first exposure or sale, never a setup row; at 5 PM or later every time shows AM for PM; a thread from before phase 3 decides from what it holds). **The time of day** (phases 14 and 15, brief E; spec section 10, R7): one line, `session-clock.js` `timeOfDayLine(sessionConfig, evidenceBundle)`, says when the investigation ran, "The investigation ran this morning, from 9:20 to 10:23 AM." for an evening session (the evening clock), "... this afternoon, from 3:50 to 5:18 PM." for an earlier one (as logged), its ends the session's span (`sessionSpanOf` over the exposures and the bundle's sales, the times the clock decision reads, never an adjustment), the meridiem once unless the span crosses noon, one time for a session with one event, and null with no sale and no exposure. It is the session's facts T7 points at: `buildSessionFacts` carries it as `timeOfDayLine`, which opens SESSION_FACTS (the map and article writers and their reworks) and the article judge's session roster (`renderJudgeSessionRoster`), and the weave writer (after the Session Roster in SECTION 1) and the story meeting's fact check (before the roster) print it themselves. No code-built label names the morning (R8): the timeline's introduction (`TIMELINE_INTRO`, "The investigation in time order"), the view's introduction, the Sources gloss and FINANCIAL_SUMMARY's total. The ledger's shift reads the same span through `session-clock.js` `placeInSpan` and `minutesOutsideSpan`. Events go in order from the first of them, the adjustments included (`firstEventTime`), so a bonus logged before the first sale opens the timeline; the clock decision still reads only exposures and sales. Events in the same minute sit under that minute, the ledger's before the evidence log's, in no claimed order; each event's `minute` is its minute on the session clock in one format (`printClockMinute`, "07:50 AM"), which the group breaks on and its heading prints, so a minute the session report writes two ways ("07:50 PM", "07:51PM") is still one group. `renderRecordView(bundle, {buried, sessionConfig})`: the callers that print the timeline pass the session config (`prompt-builder.js` from `this.sessionConfig`, the weave writer, the story meeting's fact check and the article judge). The id is `id`, else `tokenId`, else `notionId`, the order the fact check's source map keys on, so a rescued item (no `id`) is named by its Notion id, and `buildValidEvidenceIds` accepts a paper `notionId` for that reason. The owner is the record's own `owners[]`, never the bundle's `owner` (the preprocessor's guess); the text is the record's `fullDescription` or `description`, never a summary; an attribute with no value is left out. A player's character sheet is never in the record (the director's ruling, 2026-10-10: a sheet is the player's private instructions, handed out before the game, never an in-world document, never cited and never printed). The paper fetch leaves every sheet out (`fetch-nodes.js` `fetchPaperEvidence`), and the view (`renderRecordDocuments`), `lib/evidence.js` `documentTextsOf` and `documentResolverOf`, and the weave writer's Sources list (`extractEvidenceSummary`) skip one a thread fetched before still holds, by one rule, `lib/evidence.js` `isCharacterSheet`: a paper document whose name ends " Character Sheet", in any case. Phase 15's marking and trimming of a sheet, and its card failures, went with that ruling. Only character extraction takes the documents alone (`renderRecordView(bundle, {buried:false})`); which sale rows the timeline prints is one rule, `isBuriedTransactionRow`, exported by the view. The weave writer, the story meeting's fact check, the map writer and the article writer take the whole view once, in the data part, before the rules. `buildOutlinePrompt` and `buildArticlePrompt` read it from `options.evidenceBundle` (`scripts/render-prompts.js` and the content-bundle probe pass it too). The outline's five-per-arc cap is gone, and since phase 4 (brief 4.6; R5) so are the per-arc lists (the outline's `<arc-evidence>`/`<evidence-context>` and the article's ARC EVIDENCE PACKAGES) that named each arc's documents and kept code-cut excerpts: the record is the writers' one evidence section, and the fact check's card sources come from it alone (`lib/evidence.js` `documentTextsOf(evidenceBundle)`, which was the fact check's `buildSourceMap`, and which the weave's evidence check reads too; phase 4b, brief 1B). An instruction that sends a writer to a document's text uses `DOCUMENT_POINTER` ("the document with that id in <RECORD>"). Upstream, the preprocessor sends an exposed memory's `fullDescription` to Haiku, and never sends a buried memory at all: its item is made in code from the sale (`buriedMemoryItem`: the input's id, the account, amount and time, and a summary of the sale), because a memory's id and name name its owner (final fix wave). Every item a batched model call returns is keyed to its input item, never to the id the model echoed (`pairRepliesWithBatch`, exported by the preprocessor: by id, else by position when the model kept the batch's order, else by elimination, else the reply is rejected). On 092026 curation's Sonnet paper scoring (`scorePaperEvidence`) echoed a rescued email's Notion id with `583f-` missing, and its find-by-echoed-id merge kept the model's id and dropped `rawData` and `fullContent`, so every `<RECORD>` printed the email with no text. That merge now uses the rule and takes only the scoring fields from a reply (`scoredPaperItem`). An item it cannot place is kept, not dropped, as not scored (`notScored`, `excludeReason: 'scoringError'`, rescuable), so the evidence stop shows it as "never evaluated". The rescue cache is keyed on the input's own name. The preprocessor's merge uses the same rule as hardening (an input it cannot place keeps a fallback summary), so an input's id, record and disposition always survive, and its items keep their input order. And `extractCharacterData` reads `selectedPaperEvidence` and every exposed memory, in full, through the view. Machine-made material carries a label from `lib/prompt-renderers/derived-labels.js` saying who made it and that the record decides where they differ: the character context (arc writer, article roster section), the narrative tensions (arc writer, article; since the 3.6 fix batch their label says the gathered sentences are the director's own and record, and only the gathering is code's), and the director-notes indexes `<QUOTE_BANK>` and `<TRANSACTION_LINKS>` wherever the notes are rendered. The enricher links an observation to a buried sale by an opaque row key (`tx-1`, …) that `resolveTransactionLinks` maps back to the row, so neither its prompt nor the stored links carry a memory id, and `<TRANSACTION_LINKS>` prints each linked sale through the record view's transaction formatter (`buriedTransactionFields`: account, amount and time, the time on the session clock from the `sessionConfig` the block is given). Its three callers (the map and article writers' `_buildInvestigationObservations`, the weave writer, the judges' `renderJudgeDirectorNotes`) pass the session config through `withSessionClock(sessionConfig, evidenceBundle)`, so a thread with no stamped clock and no exposures (092026's shape) prints its links on the clock its timeline decides from the bundle's sales. `lib/__tests__/buried-memory-sentinel.test.js` plants one buried memory everywhere one can enter and checks every prompt for its id, owner and text.
