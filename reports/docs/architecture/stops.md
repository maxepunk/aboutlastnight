# The stops

The pipeline's eleven stops: what each is for, the payload keys the server adds to each, the approval payloads it takes, the input review's corrections, and rolling back a finished session.

Moved verbatim from `reports/CLAUDE.md` on 2026-10-11, when CLAUDE.md became a map. A part named in bold elsewhere in this text, such as **The map**, may now sit in another file in `docs/architecture/`; CLAUDE.md lists which file holds which part.

### LangGraph Workflow (6 Phases, 44 Nodes)

```
Phase 0: Input Parsing (conditional) → Phase 1: Data Acquisition → Phase 1.6-1.8: Processing
→ Phase 2: The Weave and the Story Meeting
→ Phase 3: The Map (outline) → Phase 4: Article → Phase 5: Assembly
```

*See lib/workflow/graph.js for complete node list*

**Approval payloads** (`buildResumePayload`): `{inputReview: true}` approves the parse; `{inputReview: false, inputFeedback}` rejects it with prose corrections: `checkpointInputReview` stores the round's correction as `_inputCorrections` (the trigger the re-parse consumes and clears) and appends it to `inputReviewCorrections`, the whole list in order, and `routeAfterInputReview` routes back to `parseRawInput`. Every parse prompt gets the whole list: steps 1 and 2, the enrichment and the whiteboard parse (see **The director's words as record**). At the character-IDs stop, `{characterIdsRaw | characterIds, photoDescriptions?, leftOutPhotos?}` carries the director's `{filename: text}` descriptions and the filenames whose leave-out box is ticked beside the ids (the stop's Skip sends `{characterIds: {}, leftOutPhotos}`); `buildResumePayload` refuses a malformed map, a leave-out list that names a photo the stop did not show, and a structured `characterIds` that is not an object of one mapping object per photo, naming the key at fault (the Skip's empty `{}` is taken; task 4.3c). The structured form also writes `characterIdsRaw: null`, so the parse reads only the current round's text: that channel survives a rollback, and a Skip after one runs no parse, so the boxes decide (brief 4.2b). At the story meeting, `{meeting: 'approve' | 'reweave' | 'send-back', weave, note?}` (see **The story meeting**); the arc selection's `selectedArcs`, `outlineGuidance` and `arcFeedback` are refused by name. At the map, `{outline: 'approve' | 'send-back', map, note?}` (see **The map**); the old outline payload (`outline: true | false`, `outlineEdits`, `outlineFeedback`, `outlineNote`) is refused by name. An article rejection may carry the director's edited object — `{article:false, articleFeedback, articleEdits?}` (spec `docs/superpowers/specs/2026-09-19-director-steering-design.md`). It is validated exactly like an approval, becomes the version the reviser starts from (`incrementArticleRevision` copies it into `_previousContentBundle`), and its changes join the director's standing edits at that stop (see **The director's edits are final** below), which the reviser renders as a `<HAND_EDITS>` block between HUMAN FEEDBACK and the revision instructions. A photo the director deleted at the desk (a photo block of the bundle the stop showed whose filename appears nowhere in `articleEdits`, `deskDeletedPhotos` in `server.js`) joins the leave-out list at the approve or send-back that carries the delete, through 4.2's `leavePhotosOut` (brief 4.7b), so after a send-back it stays out of the rework's PHOTOS and the map it reads, the judge's photo check and publish. The revisers never clear the edits (an evaluator-driven second pass must still see them), and the article checkpoint clears the edits and the report on approve; the map's edits, like the meeting's, stand past approve. Every note the director sends is appended to `directorGateNotes` with its kind: `rejection` for the note sent with a send-back, `approval` for a note sent with an approve (`articleNote`, and the map's and the meeting's `note`) (phase 1, 2026-09-20). It is a REPLACE channel the server appends to by writing the full array; `round` counts per stop and kind. Each note also records the round of its stop it was sent in (`stopRound`, one more than the stop's `human*RevisionCount`), and `appendGateNote` appends no note whose gate, kind and text match a note already standing from that round, so a director who retries a round whose rework did not run, with its note, files the note once; the same words in a later round file again (brief 4.5c). At the story meeting the note of a round that did not run stands only if the director's next action sends it again: a round with the same words keeps it as filed, Approve with it in the box files it as an approval note in its place, and an approve that clears it, or an action with another note or none, leaves it out (`withdrawUnrunRoundNote`; `lib/meeting.js` `unrunRoundNoteIndex` finds the note; brief 4.5c, fix round 1). `pruneGateNotes` drops the invalidated stops' REJECTION notes on a rollback to `arc-selection`/`photos`/`character-ids`/`outline`/`article` and keeps their approval notes, which are forward guidance for the writer the rollback creates; the stops each point invalidates are a table of their own, `STOPS_INVALIDATED_BY` (`lib/api-helpers.js`; brief 4.5), apart from the evaluation stubs' `PHASES_INVALIDATED_BY`, and the rollback handler writes the pruned notes through `rollbackNotesUpdate`; points above `arc-selection` clear the channel. Notes render as standing notes inside `<DIRECTOR_GUIDANCE>` for every later writer and reviser, and both judges read every one, the note a rework is acting on included, in `<DIRECTOR_STOP_NOTES>` (see **The notes at the stops**); `filterGateNotes(notes, currentFeedback, gate)` keeps the note a rework is acting on (already its HUMAN FEEDBACK) out of that list, and throws without a gate. The arc selection's guidance channel, `_outlineGuidance`, went with its last readers, the article writer and its rework (brief 4.7b; R4): a note sent with the story meeting's approve is a standing note of kind `approval`, and the standing notes are the whole of `<DIRECTOR_GUIDANCE>`. Since brief 4.7c the builders take the notes alone: `buildDirectorGuidanceSection(gateNotes)` and `_buildDirectorGuidance(gateNotes)`, the first throwing on the old guidance-first call.

## The input review and rolling back

### Input-review reject flow (re-parse, not rollback)

`InputReview` is not approve-only. Approve sends `{ inputReview: true }`; Reject with Corrections sends `{ inputReview: false, inputFeedback: '<prose>' }`. `buildResumePayload` turns that into `{approved: false, feedback}`, and `checkpointInputReview` stores it as `_inputCorrections`, appends it to `inputReviewCorrections` (every correction of the session, in order), nulls `sessionConfig`/`directorNotes`/`playerFocus` so `parseRawInput` re-runs, and routes the graph back — `parseRawInput` appends every kept correction to every parse prompt, the whiteboard parse included, and the writers read them after the director's notes (see "The director's words as record"). A mis-parsed accusation, exposure, sale or quote is therefore fixed with a note, not with a rollback and a full re-collection. The roster, its pronouns, the reporting mode and the reporter's name are not: code stamps them from where the director entered them (the roster stop, the start form), no parse returns them, and a note leaves them as they are (phase 3, brief 3.5; spec D15). The parse's correction block says only that the corrections apply to what the parse reads from the source text. There is no `inputEdits` path (the key wrote a state channel nothing declared or read).

### Rolling back a COMPLETE session

A finished thread has no checkpoint (`GET /checkpoint` returns `checkpoint: null`), so neither rollback opener could be reached for it. `SessionStart`'s `'complete'` branch therefore loads the completion instead of resuming (resuming re-runs the whole paid pipeline): `SET_THEME` → `SET_SESSION` → `SESSION_COMPLETE_LOADED`, whose payload comes from `sessionStartLogic.completedResultFrom(checkpointResponse)`. That action sets `completedResult` plus `completedStepper`, and `app.js` renders `PipelineProgress` with `completedCheckpoints: CHECKPOINT_ORDER` above `CompletionView`, so every step is a rollback target and the existing `RollbackPanel` flow applies. Nothing is POSTed until Confirm. `CHECKPOINT_RECEIVED` clears `completedResult`/`completedStepper`, because App renders the completion branch BEFORE the checkpoint branch and a stale completion would hide the checkpoint the rollback just produced.
