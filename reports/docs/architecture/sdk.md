# The Agent SDK

The wrapper around the Claude Agent SDK: structured output, isolation, tool gating, call limits, effort and thinking, model pins, the SDK version, no fallback, model substitution and refusals.

Moved verbatim from `reports/CLAUDE.md` on 2026-10-11, when CLAUDE.md became a map. A part named in bold elsewhere in this text, such as **The map**, may now sit in another file in `docs/architecture/`; CLAUDE.md lists which file holds which part.

### Claude Agent SDK Usage

```javascript
const { sdkQuery } = require('./lib/llm');

// Standard call with structured output
const result = await sdkQuery({
  prompt: 'Analyze this evidence...',
  systemPrompt: '...',
  model: 'sonnet',  // 'haiku' | 'sonnet' | 'opus'
  jsonSchema: { type: 'object', properties: {...} },
  // timeoutMs: omitted — inherits the 15-min IDLE/stall default (re-armed on every streamed
  // message, NOT a total-duration cap). Pass a smaller idle window only with data (see Model Call Limits below).
  onProgress: (msg) => console.log(msg.type, msg.elapsed),  // Optional streaming
  // every message carries `callId` (one UUID per call)
  tools: ['Read'],  // Optional: RESTRICTS the tool set (omit + no disableTools = full set incl. Bash/Write)
  allowedTools: ['Read'],  // Optional: permission auto-allow only; NOT a restriction
  label: 'Evidence analysis',  // For timeout error messages
  loadProjectSettings: true  // Optional: default false; true loads project .claude/skills/ + project CLAUDE.md
});
```

**Structured Output Contract:** When `jsonSchema` is provided, the call returns a schema-valid object or throws `StructuredOutputExtractionError`. The wrapper sends the schema to the SDK's `structured_output` channel and validates the result; if the SDK channel ever skips (see #277 below), it falls back to extracting JSON from the `result` text and validating it against the schema.

**SDK #277 channel skip — root cause is the `format` keyword (FIXED 2026-06-23, branch `fix/sdk-format-channel-skip`).** [anthropics/claude-agent-sdk-typescript#277](https://github.com/anthropics/claude-agent-sdk-typescript/issues/277) (OPEN, `bug` label): the SDK's constrained-decoding subsystem (triggered by `outputFormat: { type: 'json_schema' }`) can fail silently — returning `subtype: 'success'` with `structured_output: undefined` and `stop_reason: end_turn`, so the model emits JSON as `result` text instead of via the tool channel. We long attributed this to schema *shape* (nested `additionalProperties:false` + `oneOf` + `$ref`), but a single-variable opus probe proved the actual trigger in this SDK build is the JSON-Schema **`format` keyword** (e.g. `format:"date-time"`) — NOT `oneOf`/nesting/`additionalProperties`, all of which keep the channel engaged. `content-bundle.schema.json` carried one `format:"date-time"` on `metadata.generatedAt`; removing it re-engages the channel for content-bundle generation AND revision (both themes), verified live on session 062126. (Note: the claude-api structured-outputs doc lists `format:date-time` as *supported* — this SDK build empirically chokes on it.)

**The fix (two layers, both in place):**
- `format` removed from the two schema files that had it (`content-bundle.schema.json` metadata.generatedAt, `preprocessed-evidence.schema.json` preprocessedAt) — both validated server-stamped timestamps, so zero validation lost.
- **Guardrail** — `lib/llm/client.js#sanitizeSchemaForSdk` strips `format` (only string-valued, so a data property *named* `format` survives) plus `$id`/`$schema` from any schema before it reaches `outputFormat`, memoized per original object and fed to BOTH the SDK channel AND the extractor. So a future `format:` can't silently regress the channel, and the SDK constraint can't disagree with post-hoc validation. The memo + `$id`-strip also avert an ajv `"schema with key or id 'content-bundle' already exists"` collision across generation→revision in one process (the extractor's module-level ajv registers `$id` globally). **Never re-add `format` to a schema passed to the SDK** — the guardrail strips it, but keep the schema files clean.

**Retained as defense-in-depth** (the SDK channel is the normal path now; these are backstops if it ever skips again):
- The embedded `<SCHEMA>` text in `lib/prompt-builder.js#buildArticlePrompt` / `lib/workflow/nodes/ai-nodes.js#buildArticleRevisionPrompt` (gives the model the shape contract directly), and the map writer's and its rework's `<SCHEMA>` (the theme's map schema, `mapSchemaFor`; the outline's since phase 3, fix 3.2b).
- `lib/llm/structured-output-extractor.js` path 2 — text extraction + ajv validation.
- The `channel` field on `llm_complete`/`llm_error` tells you which path fired (`structured_output` = SDK tool channel, the normal path now; `text_fallback` = channel skipped, we extracted from text — should no longer occur for content-bundle).

**`loadProjectSettings` flag:** Controls filesystem-settings scope:
- `false` (**default**, flipped 2026-09-18 for H22) → `settingSources: []` — pure SDK isolation
- `true` → `settingSources: ['project']` — loads project `.claude/skills/` and project `CLAUDE.md` only

We never load user-level (`~/.claude/`) or local sources. A probe found those contribute ~86K tokens of irrelevant context (superpowers meta-skill, MEMORY.md, MCP server instructions, two `CLAUDE.md` files) that none of our SDK calls use. **Project scope is not free either (H22):** this `CLAUDE.md` (~9.4K tokens), `.claude/settings.json` `enabledPlugins`, skill frontmatter and the nine agent descriptions come to ~15.5K tokens per call and ~75K per session, and nothing in the pipeline reads any of it (`ThemeLoader` loads its prompt files with `fs`). Hence the default is OFF; a call that genuinely wants the project skill asks for it. This is pure context hygiene — it does NOT prevent the channel skip described above; that's a separate SDK bug.

**Tool gating (H21):** `allowedTools` is a permission AUTO-ALLOW list in this SDK, not a restriction (0.3.282 `sdk.d.ts`: "To restrict which tools are available, use the `tools` option instead"), and it is a no-op under `permissionMode: 'bypassPermissions'`. A call with neither `tools` nor `disableTools` runs with the full set, **Bash/Write/Edit included** (and the default set changed across the 0.3 line). Every pipeline call now declares one: `disableTools: true` for pure text/structured output, `tools: ['Read']` for the two image calls. The server-start health call (`isClaudeAvailable`) passes `disableTools: true` as well. **MCP servers are gated separately:** `settingSources: []` does not stop the SDK loading the user's `~/.claude.json` MCP servers (the claude.ai connectors — a `tools: []` call still reported 103 `mcp__` tools, Gmail included, at `init`), so `client.js` always passes `mcpServers: {}` + `strictMcpConfig: true` (pinned by `lib/__tests__/sdk-mcp-isolation.test.js`). The tool names `init` reports on a pipeline call must be exactly the tools the call declared, plus `StructuredOutput` when the call has a schema: CLI 2.1.282 counts its own structured-output tool (at the 2026-09-25 gate an Opus call with `disableTools` and a schema reported `StructuredOutput` alone, a Haiku image call `Read` and `StructuredOutput`), which the 2026-09-19 probes on the old CLI did not. Any other tool, or a missing one, fails the isolation probe by name (`scripts/lib/probe-verdicts.js#isolationVerdict`). **Auto-memory is gated the same way:** the subprocess loads the operator's `~/.claude/projects/<cwd>/memory/` regardless of `settingSources` (a probe showed the model reading MEMORY.md's 33 entries), so `client.js` passes `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` through `options.env`; `init.memory_paths` must be absent (`lib/__tests__/sdk-memory-isolation.test.js`). Both are checked live by `scripts/probe-sdk-isolation.js`.

**Model Call Limits (idle timeout + cost ceiling):** SDK calls use a **15-min IDLE/stall timeout**, not a total-duration cap — the timer is re-armed on every streamed message (including the token-level `includePartialMessages` deltas emitted as `llm_delta`), so a legitimately long call (big prompt + extended thinking) survives as long as it keeps producing; only a genuine stall (no streamed activity for 15 min) aborts. A stall throws `SDK timeout after … idle … with no streamed activity`, which `isSdkTimeoutError` recognizes and `isTransientError` (`lib/llm/retry.js`) classifies **transient** (the node-level `retryPolicy` consumes this to auto-retry transient SDK failures). A runaway call is bounded separately by a **per-call `maxBudgetUsd` ceiling** (`MODEL_BUDGETS` in `lib/llm/client.js`: opus $100, sonnet $50, haiku $10). The pipeline runs on the director's subscription, so the figure is not a cost: the SDK derives it from token volume at list prices, and it exists only to stop a stuck loop before it burns the rate limit unattended. An overrun throws a labeled **non-transient** `error_max_budget_usd` that is never auto-retried (the budget is per-CALL, so N node-retries can cost up to N× the ceiling). Steady-state latency is still captured per-call via `duration_api_ms` on the `llm_complete` event (`lib/observability/progress-bridge.js`).

**Effort and thinking (operator gate 2026-09-19; Opus 5.5 since 2026-09-25; Sonnet 5.5 and Haiku 5.5 since 2026-10-11):** `EFFORT_LEVELS` sends each model's level explicitly on every call, so no call runs on a default the SDK, the CLI or the API chooses: `xhigh` for opus, `high` for sonnet, `medium` for haiku. A call site passes its own `effort` where its job calls for another level, with the reason beside it: the director-notes enrichment `medium` (Opus, below), the verdict parse (`parseRawInput`'s group-statement parse) and character extraction `high` (Haiku 5.5's guide gives `high` for strict instruction following and knowledge work), and the server-start health call `low`. The Sonnet and Haiku levels are the API's defaults and the docs' starting points (https://platform.claude.com/docs/en/build-with-claude/effort): Sonnet 5.5's levels are recalibrated from Sonnet 5's, so Sonnet 5's `xhigh` does not carry over, and the docs keep `xhigh` and `max` for work where an eval shows a gain; Haiku 5.5 is the first Haiku with effort (Haiku 4.5 took none, and the CLI gave it a thinking budget: on five sessions 50% to 92% of its output tokens were thinking). No eval stands behind these levels: each session's call log records every call's duration and thinking tokens, the read that moves a level. Opus's levels are decided in roadmap phase 16. The levels did not move with the Opus 5.5 pin; the 2.0 gate records every call's duration next to session 092026's first. On Opus 4.8, `xhigh` was a cliff for extraction-shaped prompts: the director-notes enrichment ended its first turn after thinking alone (~320s, no output), the SDK's structured-output enforcement re-requested, and the call cycled for 20 minutes without completing while re-arming the idle timer (it looked like a stall). `lib/director-enricher.js` therefore passes `effort: 'medium'` (165s; `high` 375s; both complete). The client sets `thinking: { type: 'adaptive', display: 'summarized' }` on every call: Opus 5.5, Sonnet 5.5 and Haiku 5.5 all think adaptively with display "omitted" by default (Haiku 4.5 returned summarized thinking; the Haiku 5.5 migration guide), which streams thinking as EMPTY blocks, so a long think is a silent stream and the console's THINKING stage shows nothing. Opus 5.5 cannot run with thinking off (`disabled` and `budget_tokens` are both a 400), and Sonnet 5.5 rejects `disabled` too (its lowest setting is `between_tools`), so the summarized text is also what keeps the idle timer fed. Arc analysis (286s) and outline/article generation completed at xhigh in the same run; if one of them ever shows the empty-thinking → `status: requesting` cycle, lower its effort per call.

**Model Pins** (see `MODEL_IDS` in `lib/llm/client.js`; `sonnet` is also the wrapper's default alias):
- `opus` → `claude-opus-5-5` (since phase 2 slice 2.0, 2026-09-25; was `claude-opus-4-8`): the director-notes enrichment, the weave writer (`generateWeave`) and its rework (`reviseArcs`), the two evaluators (the story meeting's fact check, the article judge), the map writer (`generateOutline`) and its rework (`reviseOutline`), `generateContent`, `reviseContent`
- `sonnet` → `claude-sonnet-5-5` (since 2026-10-11; was `claude-sonnet-5`): the session-report parse, the whiteboard parse (image), the character-ID parse, paper-evidence scoring at curation
- `haiku` → `claude-haiku-5-5` (since 2026-10-11; was `claude-haiku-4-5`): the session-config parse, photo analysis (image) and photo enrichment, evidence preprocessing, character-data extraction, the server-start health call

**Agent SDK version:** `@anthropic-ai/claude-agent-sdk` 0.3.296, bundled CLI 2.1.296 (since 2026-10-11; 0.3.282 and CLI 2.1.282 from phase 2 slice 2.0). The move to 0.3.296 was forced by the 5.5 pins: Claude Code added Sonnet 5.5 in 2.1.284 and Haiku 5.5 in 2.1.293, and between them 2.1.290 fixed a headless structured-output run that exited with an error after its output was delivered, and an SDK host using partial messages whose reply stayed open after its stream was cut. Its peer dependencies are unchanged. The move from 0.2.119 was forced by the pin: CLI 2.1.119 answers `claude-opus-5-5` with "version 2.1.280 or newer is required". From 0.3.143 `@anthropic-ai/sdk` (>=0.93.0; a direct dependency at ^0.128.0, though nothing imports it) and `@modelcontextprotocol/sdk` are peer dependencies. The entry is still the ESM-only `sdk.mjs`, loaded with `require()` on Node 24. The CLI binary ships in the optional platform package `@anthropic-ai/claude-agent-sdk-<platform>` (`win32-x64` on the director's machine): an install that skips optional dependencies, or one run from WSL, leaves no CLI for Windows. Reinstall with `npm ci --os=win32 --cpu=x64`: the director's `~/.npmrc` sets `os=linux`, and a plain install fetches Linux builds with no `sharp` binary and no CLI binary. The isolation options (`mcpServers: {}`, `strictMcpConfig`, `settingSources: []`, the env with `CLAUDE_CODE_DISABLE_AUTO_MEMORY`) and thinking `{adaptive, summarized}` are unchanged across the bump; the env has two new keys, `CLAUDE_CODE_NO_MODEL_FALLBACK` and `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK` (next two paragraphs).

**No model fallback:** the pipeline's calls are always served by their pinned model, never a substitute (integrator ruling, 2026-09-25). `client.js` sets `CLAUDE_CODE_NO_MODEL_FALLBACK=1` in `options.env` (pinned by `lib/__tests__/sdk-memory-isolation.test.js`, which holds the env to `process.env` plus exactly the three switches). In CLI 2.1.282 this is "the no-fallback guarantee": it turns the refusal fallback off (that lane's gate reads both this and `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK`), builds the availability fallback chain as the primary model alone, blocks model substitution, and makes a compaction that would need another model an error instead of a swap. An overload the CLI can then route nowhere ends the call as an `is_error` result whose assistant error is `server_error` ("API Error: Repeated 529 Overloaded errors…"). `isTransientError` treats the assistant errors `server_error` and `overloaded` as transient, as the CLI's own classifier does, so the node retry policy retries the call on the same model (`retry.test.js`, `client-contract.test.js`). A numeric status decides first: every 5xx is transient (a gateway's 502 or 504 too), 429 is the one transient 4xx, and every other explicit 4xx is permanent, whatever the assistant error.

**A model that wrote part of the answer and is not the pinned one fails the call** (integrator ruling, 2026-09-25; corrected 2026-09-26). The models that wrote the answer are the ones named on the call's own assistant frames (`message.model` on frames with no `parent_tool_use_id`; `answerModels` in `client.js`). When any of them fails `servedModelMatches` against the model the call resolved to, the wrapper throws `SdkModelSubstitutionError` (`lib/llm/model-substitution.js`; "SDK model substitution: requested claude-opus-5-5, served by claude-opus-4-8 - <label>; the result is not used", `sdkSubtype: 'model_substitution'`, with `requestedModel`, `servedModels` (the answer's models) and `substituteModels`). It emits one `llm_error` carrying both lists, `servedModels` (the result's modelUsage) and `answerModels`; a schema failure the result also has rides along as `cause`, with its `schemaErrors` on the `llm_error`. `isTransientError` classifies it permanent, through `.cause` and the message marker. **The result's modelUsage is recorded, not judged:** it also lists the CLI's own helper requests. On 2026-09-26 (session 092626) a Sonnet session-report parse listed `claude-haiku-4-5` beside `claude-sonnet-5` there while every frame of its answer was Sonnet's; the first version of this rule judged modelUsage and threw the correct answer away. A call with no frame naming a model has nothing to judge and returns. A subagent's frames (a `parent_tool_use_id`) are not the call's answer; pipeline calls run none. A substitute after a refusal signal is a declined request instead (next paragraph). The isolation probe and `check-model-freshness.js` judge `answerModels` the same way.

**Declined requests (refusals):** since 0.3.162 a declined request ends with `stop_reason: "refusal"` and `stop_details: {category, explanation}`. The category is `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms` or null (the installed `@anthropic-ai/sdk` 0.128.0 types; the CLI treats it as an open string). `lib/llm/refusal.js` reads every place the 0.3.282 types allow: the result's `stop_reason`, the assistant frame's `message.stop_reason`/`stop_details`, a `message_delta` stream event, and the CLI's `system/model_refusal_no_fallback` notice. No live refusal has been captured through this SDK, so each source is optional and pinned by mock (`client-contract.test.js`). The wrapper throws `SdkRefusalError` ("SDK refusal (category: bio): claude-opus-5-5 declined the request - <label>", `sdkSubtype: 'refusal'`) before any result branch, and emits one `llm_error` carrying `refusal` (and `schemaErrors`: the extraction failure's when the refusal names one, else null). `isTransientError` checks a refusal FIRST, through `.cause` and the message marker, so it is never retried. The four nodes that re-wrap SDK errors (arc analysis, character data, the whiteboard, photos) keep the original as `cause`. The paths that swallow errors into state keep the message: the evaluators (`evaluationHistory._error`, `errors`), `reviseArcs` (which never takes a refusal for its free timeout retry) and the enricher (`_enrichmentFallback.reason`). **A declined request is never answered by another model** (integrator ruling, 2026-09-25). The bundled CLI has refusal fallback routes of its own, keyed on the requested model and independent of the `fallbackModel` option: for `claude-opus-5-5` it retries `bio` and `frontier_llm` on `claude-opus-5` and `cyber` on `claude-opus-4-8`. `client.js` turns them off with `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` in `options.env`, and `CLAUDE_CODE_NO_MODEL_FALLBACK=1` turns them off as well (both pinned by `lib/__tests__/sdk-memory-isolation.test.js`). A main-thread fallback that runs anyway (a `system/model_refusal_fallback` whose `scope` is not `local`, or an assistant frame that `supersedes` the refused frames) throws `SdkRefusalError` at once, naming the category and the fallback model, and the `llm_error` carries it as `refusalFallback`. Any other failure after a refusal signal (a schema failure, an iterator throw, no result, an idle abort) is thrown as `SdkRefusalError` with the original failure as `cause`, so a stall after a refusal is never retried as a transient `SDK timeout`. A refusal signal followed by a clean, schema-valid finish on another stop reason returns the result, and `llm_complete` carries the signal as `refusalSignal` (in `diagnosticsOf`, so the call log has it). The exception: when the result's `modelUsage` names a model that is not the one the call resolved to under `servedModelMatches` (`lib/llm/sdk-fields.js`, shared with the probe scripts; a `[1m]` or dated suffix is the same model), another model finished the declined request, and the wrapper throws `SdkRefusalError` naming that model (a schema failure, if there is one, rides along as its `cause`). A result with no `modelUsage` has no other model to name and returns. Without a refusal signal, the same `modelUsage` is a model substitution (previous paragraph).

**What the 2.0 gate reads:** the `init` forward carries `effort` and `memoryPaths` as well as `model`/`betas`/`toolCount`/`toolNames`/`permissionMode` (the isolation probe prints the names on every init line, with the expected set above them). Neither is typed for `query()` calls in 0.3.282 (`memory_paths` is absent from the public `SDKSystemMessage`; `effort` is documented for Remote Control frames), so both are forwarded raw and absent is normal. A loaded memory path prints as an error line. Every result envelope carries `servedModels`, read from the result's `modelUsage` (`canonicalModel` preferred) because the call log otherwise records only the alias and 0.3.174 added silent model fallbacks. A served model other than the pinned one fails the call (above), so the `answerModels` of a completed call name only the pinned model; its `servedModels` (the result's modelUsage) can also name a CLI helper model such as `claude-haiku-4-5`, or be null or empty (a zero-turn result carries an empty `modelUsage`). It reaches the per-call record, both SSE envelopes, `index.jsonl` and the console completion line (`served=`). One builder (`llm-call-log.js#diagnosticsOf`) makes the record's and both SSE envelopes' diagnostics. Open at the gate: whether the `context-1m-2025-08-07` beta, still sent to every non-Haiku call, is accepted, ignored or rejected on Opus 5.5 (1M native).
