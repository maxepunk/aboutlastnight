# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**ALN Director Console** - AI-powered investigative article generator for "About Last Night" using Claude Agent SDK with LangGraph workflow.

Generates journalist-style investigative articles by:
1. Fetching memory tokens and paper evidence from Notion database
2. Curating evidence bundle using three-layer model (exposed/buried/context)
3. Writing the weave, the one story the article will tell, which the director settles at the story meeting
4. Laying the settled weave across the article's sections as the story map, which the director settles, then writing the article from both, which the director finishes at the desk, and publishing the HTML report

**Production URL:** `https://console.aboutlastnightgame.com` (via Cloudflare Tunnel)

**Deep Dive:** For business context, game mechanics, phase-by-phase breakdown, and detailed debugging scenarios, see `docs/PIPELINE_DEEP_DIVE.md`.

## Architecture

### LangGraph Workflow (6 Phases, 44 Nodes)

```
Phase 0: Input Parsing (conditional) → Phase 1: Data Acquisition → Phase 1.6-1.8: Processing
→ Phase 2: The Weave and the Story Meeting
→ Phase 3: The Map (outline) → Phase 4: Article → Phase 5: Assembly
```

*See lib/workflow/graph.js for complete node list*

Every parse prompt gets the whole list: steps 1 and 2, the enrichment and the whiteboard parse (see **The director's words as record**). At the character-IDs stop, `{characterIdsRaw | characterIds, photoDescriptions?, leftOutPhotos?}` carries the director's `{filename: text}` descriptions and the filenames whose leave-out box is ticked beside the ids (the stop's Skip sends `{characterIds: {}, leftOutPhotos}`); `buildResumePayload` refuses a malformed map, a leave-out list that names a photo the stop did not show, and a structured `characterIds` that is not an object of one mapping object per photo, naming the key at fault (the Skip's empty `{}` is taken; task 4.3c). The structured form also writes `characterIdsRaw: null`, so the parse reads only the current round's text: that channel survives a rollback, and a Skip after one runs no parse, so the boxes decide (brief 4.2b). At the story meeting, `{meeting: 'approve' | 'reweave' | 'send-back', weave, note?}` (see **The story meeting**); the arc selection's `selectedArcs`, `outlineGuidance` and `arcFeedback` are refused by name. At the map, `{outline: 'approve' | 'send-back', map, note?}` (see **The map**); the old outline payload (`outline: true | false`, `outlineEdits`, `outlineFeedback`, `outlineNote`) is refused by name. An article rejection may carry the director's edited object — `{article:false, articleFeedback, articleEdits?}` (spec `docs/superpowers/specs/2026-09-19-director-steering-design.md`). It is validated exactly like an approval, becomes the version the reviser starts from (`incrementArticleRevision` copies it into `_previousContentBundle`), and its changes join the director's standing edits at that stop (see **The director's edits are final** below), which the reviser renders as a `<HAND_EDITS>` block between HUMAN FEEDBACK and the revision instructions. A photo the director deleted at the desk (a photo block of the bundle the stop showed whose filename appears nowhere in `articleEdits`, `deskDeletedPhotos` in `server.js`) joins the leave-out list at the approve or send-back that carries the delete, through 4.2's `leavePhotosOut` (brief 4.7b), so after a send-back it stays out of the rework's PHOTOS and the map it reads, the judge's photo check and publish. The revisers never clear the edits (an evaluator-driven second pass must still see them), and the article checkpoint clears the edits and the report on approve; the map's edits, like the meeting's, stand past approve. Every note the director sends is appended to `directorGateNotes` with its kind: `rejection` for the note sent with a send-back, `approval` for a note sent with an approve (`articleNote`, and the map's and the meeting's `note`) (phase 1, 2026-09-20). It is a REPLACE channel the server appends to by writing the full array; `round` counts per stop and kind. Each note also records the round of its stop it was sent in (`stopRound`, one more than the stop's `human*RevisionCount`), and `appendGateNote` appends no note whose gate, kind and text match a note already standing from that round, so a director who retries a round whose rework did not run, with its note, files the note once; the same words in a later round file again (brief 4.5c). At the story meeting the note of a round that did not run stands only if the director's next action sends it again: a round with the same words keeps it as filed, Approve with it in the box files it as an approval note in its place, and an approve that clears it, or an action with another note or none, leaves it out (`withdrawUnrunRoundNote`; `lib/meeting.js` `unrunRoundNoteIndex` finds the note; brief 4.5c, fix round 1). `pruneGateNotes` drops the invalidated stops' REJECTION notes on a rollback to `arc-selection`/`photos`/`character-ids`/`outline`/`article` and keeps their approval notes, which are forward guidance for the writer the rollback creates; the stops each point invalidates are a table of their own, `STOPS_INVALIDATED_BY` (`lib/api-helpers.js`; brief 4.5), apart from the evaluation stubs' `PHASES_INVALIDATED_BY`, and the rollback handler writes the pruned notes through `rollbackNotesUpdate`; points above `arc-selection` clear the channel. Notes render as standing notes inside `<DIRECTOR_GUIDANCE>` for every later writer and reviser; `filterGateNotes(notes, currentFeedback, gate)` keeps the note a rework is acting on (already its HUMAN FEEDBACK) out of that list, and throws without a gate. The arc selection's guidance channel, `_outlineGuidance`, went with its last readers, the article writer and its rework (brief 4.7b; R4): a note sent with the story meeting's approve is a standing note of kind `approval`, and the standing notes are the whole of `<DIRECTOR_GUIDANCE>`. Since brief 4.7c the builders take the notes alone: `buildDirectorGuidanceSection(gateNotes)` and `_buildDirectorGuidance(gateNotes)`, the first throwing on the old guidance-first call.

**The director's edits are final** (before phase 4, F1 and FA; spec `docs/superpowers/specs/2026-10-02-story-meeting-and-map.md` section 7). An automatic pass never changes a line the director wrote: a judge that disagrees with one lists it for the director, and code puts back what a pass changed anyway. A send-back's changes are the director's edits, one per field the director changed (`lib/hand-edit-diff.js`), `{id, scope, path, at, before, after}`: `at` is the steps to the field, each element of a collection found by what names it (a section's id, or on the map its slot, a card's tokenId, a beat's, a thread's or a connection's id, a block's type with its text, filename or tokenId), and `path` the same place for reading (`sections[#closing].content[0].text`, `sections[#closing].beats[#b6].move` on the map, `financialTracker.entries[1].amount`). A card's headline, a beat's move, one tracker entry's amount and a photo's caption apart from its filename are each one edit, so the writer's untouched text beside them stays the writer's (FA, requirement 2); an element the director added whole is one edit whose `after` is the element. On the map, the director's order of a section is one edit of the section, its beat ids in their order, which owns no text and names at least two beats; it stands while the section holds every beat it names in that order, and code puts it back after an automatic pass that changes it or takes one of those beats out of the section, as it puts back every edit (fix A: the spec's section 17), and a beat's summary (its `synopsis`) is a line like any other, named in every place as the summary of its move (`section "closing", the summary of beat "b6"`), never by the field's name (phase 4b, piece 4, R3 and R11; see **The map**). A section's blocks pair only with blocks of their own type, so a block retyped (only the JSON editor retypes one) is a cut and an addition (task 4.3c), and a photo, a card or a reference only with one of its own filename or tokenId (`pairSectionBlocks`), so one renamed is a cut and an addition too, and two the director swapped are two moves, each keeping its own caption or text (task 4.5d). A null `after` is a cut, whose `before` is the text removed and whose `pieces` are each of its sentences of three words or more that the director's version no longer held. A rewritten text field also records `removed`: each sentence of its old text the director's version no longer holds, as written (requirement 3). A block that left one section and arrived unchanged in another is one edit, a move, whose `from` names the section it left (requirement 4); a block the director moved within its section is a move too, whose `between` names the blocks it follows and precedes (task 4.3, the desk). A Key Evidence entry (the sidebar's `evidenceCards`) the director deleted at the desk is a cut, and one they moved within the sidebar is a move whose `from` is `evidenceCards` and whose `between` names the entries it follows and precedes by their tokenIds, the desk's naming rule deciding which entries moved, beside an edit of any field they changed on it (`diffSidebar`, task 4.14c). A move is the block's place only: the director changed none of its fields, so its text is still the writer's, which the judges, the guard and the fact check read as the writer's (fix round 1, finding 2). Given the session roster's names (both send-back arms of `buildResumePayload`), a cut or a rewrite records `names`: the names its text held that the director's version no longer names (requirement 9). An edit's id (`E1`, `E2`, ...) is stable within its stop. The edits stand at their stop across every send-back (`standingAfterSendBack`): `_outlineHandEdits` / `_articleHandEdits` hold `{kind, issued, edits}`; an earlier edit stands while the version the stop showed and the version sent back carry it (a field edit, while the element it belongs to holds the director's value, a section's block found in any section; a move, while a block of its identity (its type with its filename, tokenId or text) sits in the director's section, whatever its other fields, and a move within the section while it also keeps the director's order there, or, where the director's own move of a neighbour broke that order at a send-back, while it sits among the blocks that kept their order in it, re-anchored to its neighbours there (task 4.3b), and a Key Evidence entry's move the same way within the sidebar (task 4.14c); a cut, while none of its pieces is back, and a Key Evidence entry the director deleted, while the sidebar holds no entry of its tokenId, in any words (`deletedEntryOf`, task 4.14f)), a removed sentence that came back drops from its edit, and so does a deleted Key Evidence entry's piece that either version prints outside every entry of its tokenId, which is the director's to keep or cut (`stillRemoved`, task 4.14f, fix round 1), and the send-back's own edits join with the next ids after `issued`. Text is read from the fields the page prints (`PRINTED_FIELDS`, which the article judge's `printedBundle` reads too; known item 6), and a piece under six words is back only as a whole sentence (known item 4). A diff stored before F1, or an edit stored before FA, reads as the same field-level edits. At the article stop, approve, a rollback and a fresh start clear them (the map's and the meeting's stand past approve and through the rollback to their own stop, R9), and approve-with-edits runs no rework. Every reader takes the edits the version in hand carries (`carriedEdits`):
- The reworks' `<HAND_EDITS>` block (`buildRevisionContext`) lists them by id and place with the director's text (`formatEditLines`: text quoted, an element by its fields, never JSON; a move by its place, and a block its text names by the words it begins with), each removed sentence on a `removed:` line under its edit, after `EDIT_LINES_GUIDE` (an edit covers only the place its line names, and a moved block's text is still the writer's), in one of two wordings. On an automatic pass each edit stays exactly as written, each removed sentence stays out, and each block the director cut stays out, with what it said not said again anywhere in the article, since the cut check finds only a cut's own sentences coming back (brief 4.7f; the send-back's exception is stated first, as the map's and the meeting's are). On a send-back the same holds unless the structural change the note asks for means an edit no longer fits, and the rework returns each edit it changed, removed or brought back in `changedDirectorEdits`, with one sentence on why. That list exists only in the rework call: its schema is built in code from the stored one on a send-back that carries edits (`reworkSchemaWithChangedEdits`, `ai-nodes.js`; `lib/schemas/*.json` are unchanged), and the node takes the list out before it stores the output (`takeChangedEdits`). A rework never reads a finding located in the director's text (`withoutDirectorsFindings`, requirement 7): the issues, suggestions and criterion notes and fixes that quote a standing edit are left out of its context, and so are the judge's guidance and the notes and fix of a criterion under the rule ids of an issue left out (the verdict's `criteriaRules`, which `createEvaluator` writes; requirement 5). At a send-back that verdict is the one the stop showed, which no judge wrote with the director's newest edits in view.

Its words come from the notes, or from the correction that gives the wording; `context` is the director's words around it, one unbroken passage copied from the notes (the quote's sentence through the sentence that names the speaker, with every sentence between), because only a passage the notes hold in one piece survives the check; `correction` is the input-review correction that changed its speaker, addressee or wording. `groundQuotes` (`lib/director-enricher.js`) keeps the words, the context and the correction only when the notes or the corrections hold them word for word (`isVerbatimIn`, `lib/grounding.js`, which the renderer shares), and keeps the speaker and the addressee only when the kept context or correction names them outside the quoted words (`namedOutsideQuote`, also in `lib/grounding.js`). It leaves both out, counted as `unrecordedSpeakers`, when the quote carries a correction the corrections do not hold. A verified correction is about the line when the corrections hold the attached one, or when one of them quotes the line (task 3.11: a passage the correction puts in quotation marks holds a whole sentence of three or more words of the quote's words or of the passage its context quotes, as `isVerbatimIn` reads them and on word boundaries; corrections quote names, vote words and charges as often as lines, and those sit inside a sentence or are shorter, so they never decide); since the final fix the speaker is then the name that correction gives and the notes' account of the line does not, attached or not, because a correction names the old speaker as well as the new, and with no such name both are left out. A quote whose speaker is left out has the confidence `low`. The confidence bands are one wording, `QUOTE_CONFIDENCE_BANDS`, in the schema and the rules (M5). The enricher's rules (`ENRICHMENT_RULES`: verbatim, roster, link, quote, epilogue, empty) are stated once per call, each with its reason, in `<ENRICHMENT_RULES>` after the notes in the user prompt (the corrections block, when there is one, follows it); the system prompt points there by the tag alone. The link rule joins an observation to a ledger row only when the notes describe that sale (someone seen selling, or a deal with Blake) and its time and amount converge; an account's name matching a character never makes a link (T4). `<QUOTE_BANK>` prints each quote with its speaker or `(speaker not recorded)` (a stored `unknown` too), then an `In the notes:` line and a `The director's correction:` line, each only when the renderer finds it verbatim; a stored speaker or addressee prints only under the rule the enricher uses, `groundQuote` (`lib/grounding.js`, the final fix): with no correction about the line, a name the verified context gives; with a verified correction about the line, attached or not, only a name that correction gives and the notes' account of the line (the context and the notes' paragraph holding it) does not, so a line the director re-attributed never stays in the old speaker's mouth; a correction's quoted passage matches in single or double quotation marks and in any case (task 3.11: a thread enriched before phase 3 (before 3.6's enricher) stores speakers with no support, such as 092626's "Mel" for a thought in Mel's memory, so its quotes print `(speaker not recorded)` wherever nothing verified names one); it no longer says "prefer these" or prints the confidence, and it has no em-dash.
- **The epilogue.** An item is `{detail, subjects?, proseOffset?}`: `detail` is one unbroken passage of the director's words (a development the notes report in two places is two items), kept only when the notes hold it (`groundEpilogue`), and `subjects` is an index no prompt prints. The enricher's headline and "why this matters" are gone. The renderer prints `<EPILOGUE>` (it was `<POST_INVESTIGATION_NEWS>`) with each item's verbatim `detail` alone, so a stored item with a headline prints as the director's sentence and one with only a headline prints nothing. The stored field keeps its name, `postInvestigationDevelopments`.
- **Labels.** `<TRANSACTION_LINKS>` carries `DERIVED_LABELS.transactionLinks` (a link is the model's pairing of an observation with ledger sales, never something the notes state; `groundLinkExcerpts` keeps a link only when the notes hold its observation word for word, so the label's "quoted from the director's notes" holds; the renderer re-checks each stored link the same way, `linksInTheNotes` in `director-notes-renderer.js`, and prints nothing of one whose observation the notes do not hold, so a thread enriched before that check reads the same) and `<EPILOGUE>` `DERIVED_LABELS.epilogue` (the model picked the sentences; each is copied as written). `<QUOTE_BANK>` keeps `directorNotesIndex`.
- **Character extraction** requires no role, lists a relationship only where a document states it and a group only where a document names the character a member, and gives Marcus and Blake by the canon lines (T15). That document-only rule is stated once, last in the prompt, with its reason; the schema and the system prompt only name the fields, and the field list asks for "each relationship a document states between them and another character", so the list itself asks for nothing inferred.
- **The tensions.** `surfaceContradictions` no longer reads an account named after a roster character as that character's (T4): the named-account and transparency tensions are gone. Its one tension prints the director's sentences that name Blake or the Valet, and `DERIVED_LABELS.narrativeTensions` says those sentences are record and only their gathering is code's (from wave 2 the print sites drop stored old-type tensions, so every printed tension is the director's sentences); `proseSentences` does not end a sentence at a full stop inside the director's quotation marks, and ends one at a blank line with LF or CRLF line endings.
- New `_enrichmentWarnings` keys: `droppedContexts`, `droppedCorrections`, `unrecordedSpeakers`, `droppedEpilogueItems`, `droppedExcerpts` (links dropped because the notes do not hold their observation). The input review shows `droppedQuotes`, and through `ENRICHMENT_WARNING_LABELS` in `console/input-review-logic.js` `unrecordedSpeakers`, `droppedContexts` and `droppedEpilogueItems` (since 3.5) and `droppedCorrections` and `droppedExcerpts` (since the 3.6b fix batch), each as a count with a short label.

**Revision Loops:** the automated budget, PER ROUND of the director's, is one check rework and one fact-check fix at the story meeting, counted apart (R6; `REVISION_CAPS.ARCS` is 1: the check rework on `arcRevisionCount`, the fix on the fact check's mark on the weave; see **Arc Validation Routing**), one check rework at the map (`REVISION_CAPS.OUTLINE` is 1; brief 4.6), and 2 reworks for the article. A send back (at the story meeting, a reweave or a send-back, by its round mark) opens a new round (`humanArcRevisionCount` / `humanOutlineRevisionCount` / `humanArticleRevisionCount`) and starts the budget over. The director's rounds are never capped, and the story meeting goes forward only on the director's approval. See `PIPELINE_DEEP_DIVE.md#evaluation--revision-architecture` for the judges' one truth-only contract and the revision loops.

**A rework that fails** (task 4.14e; the final review's ruling 5) keeps the version it started from as its stop's output, at the map and the desk, as the story meeting's does (**A round that times out**). The increments leave `outline` / `contentBundle` in place while the rework runs, the rework reading its copy in `_previousOutline` / `_previousContentBundle`, and open the rework's record, `_outlineRework` / `_articleRework` (`lib/workflow/state.js` `reworkOpened`: the director's send-back with its note, or none for an automatic pass, and the counts the rework started from). A call that fails on a transient error (`isTransientError`) with calls left changes only the record (`REWORK_STATUS.RETRYING`), and the route after the rework runs the call again (`routeAfterMapRework`, `routeAfterArticleRework`), up to `REWORK_CALLS` (3) calls, spending no automated budget. Any other failure, or the last call's, gives the rework up (`REWORK_STATUS.DID_NOT_RUN`; `ai-nodes.js` `mapReworkFailed`, `articleReworkFailed`):
- **The director's send-back does not run.** The stop reopens with the director's version, its counts as they were before the round and the note's slot empty, and its payload's `roundDidNotRun` (`roundDidNotRunAt`) says so. The rework also withdraws the round's note from `directorGateNotes` (`roundGivenBack`, `withoutRoundNote`). Every later writer reads a rejection note as applied, and no rework applied this one. The note it withdraws is the rejection note at the stop with the round's text, filed in the round the given-back counts reopen. The stop gives the note back instead, in the note box or quoted by its line. The director's next action files it or leaves it out, as at the story meeting: a send-back with it files it as a rejection note again, Approve with it as an approval note, and any other action leaves it out. The meeting withdraws its own at that next action (`withdrawUnrunRoundNote`), with the same outcomes. The map checks' route opens the stop on the record (`routeMapChecks`); the desk's rework states again the verdict the desk opened on (`verdictAfterFailedRework`), so a replay skips the judge.
- **An automatic pass** ends the run in an error, as the meeting's does, with the version it started from kept and its trace entry dropped. At the desk the verdict it was fixing is escalated to the director, which `routeArticleEvaluation` takes to the stop below the cap. Retry opens the stop with no call, and so does going back to the map (R9).

A rework that completes clears its record, and each record clears at the rollback points that clear its stop's note. Getting the director's version back calls no writer (`__tests__/integration/rework-failure-graph.test.js`).

**Photo spacing** (spec 2026-10-02 section 9): the page never prints two photos in a row, except when the photos outnumber the blocks that can separate them. `TemplateAssembler.buildContext` passes the sections through `spacePhotos` (`lib/photo-spacing.js`, whose header states the whole rule) before it maps them and builds the section nav, for both themes, so the publish step, the article stop's `htmlPreview` and `scripts/assemble-article.js` print one order. **Publishing** (`assembleHtml`, after the article stop; the fixes before phase 4, F2 and FB).
```javascript
const { sdkQuery } = require('./lib/llm');
```

**Structured Output Contract:** When `jsonSchema` is provided, the call returns a schema-valid object or throws `StructuredOutputExtractionError`. The wrapper sends the schema to the SDK's `structured_output` channel and validates the result; if the SDK channel ever skips (see #277 below), it falls back to extracting JSON from the `result` text and validating it against the schema.

**SDK #277 channel skip — root cause is the `format` keyword (FIXED 2026-06-23, branch `fix/sdk-format-channel-skip`).** [anthropics/claude-agent-sdk-typescript#277](https://github.com/anthropics/claude-agent-sdk-typescript/issues/277) (OPEN, `bug` label): the SDK's constrained-decoding subsystem (triggered by `outputFormat: { type: 'json_schema' }`) can fail silently — returning `subtype: 'success'` with `structured_output: undefined` and `stop_reason: end_turn`, so the model emits JSON as `result` text instead of via the tool channel. We long attributed this to schema *shape* (nested `additionalProperties:false` + `oneOf` + `$ref`), but a single-variable opus probe proved the actual trigger in this SDK build is the JSON-Schema **`format` keyword** (e.g. `format:"date-time"`) — NOT `oneOf`/nesting/`additionalProperties`, all of which keep the channel engaged. `content-bundle.schema.json` carried one `format:"date-time"` on `metadata.generatedAt`; removing it re-engages the channel for content-bundle generation AND revision (both themes), verified live on session 062126. (Note: the claude-api structured-outputs doc lists `format:date-time` as *supported* — this SDK build empirically chokes on it.)

**The fix (two layers, both in place):**
- `format` removed from the two schema files that had it (`content-bundle.schema.json` metadata.generatedAt, `preprocessed-evidence.schema.json` preprocessedAt) — both validated server-stamped timestamps, so zero validation lost.
- **Guardrail** — `lib/llm/client.js#sanitizeSchemaForSdk` strips `format` (only string-valued, so a data property *named* `format` survives) plus `$id`/`$schema` from any schema before it reaches `outputFormat`, memoized per original object and fed to BOTH the SDK channel AND the extractor. So a future `format:` can't silently regress the channel, and the SDK constraint can't disagree with post-hoc validation. The memo + `$id`-strip also avert an ajv `"schema with key or id 'content-bundle' already exists"` collision across generation→revision in one process (the extractor's module-level ajv registers `$id` globally). **Never re-add `format` to a schema passed to the SDK** — the guardrail strips it, but keep the schema files clean.

**Retained as defense-in-depth** (the SDK channel is the normal path now; these are backstops if it ever skips again):
- The embedded `<SCHEMA>` text in `lib/prompt-builder.js#buildArticlePrompt` / `lib/workflow/nodes/ai-nodes.js#buildArticleRevisionPrompt` (gives the model the shape contract directly), and the map writer's and its rework's `<SCHEMA>` (the theme's map schema, `mapSchemaFor`; the outline's since phase 3, fix 3.2b).
- `lib/llm/structured-output-extractor.js` path 2 — text extraction + ajv validation.
- The `channel` field on `llm_complete`/`llm_error` tells you which path fired (`structured_output` = SDK tool channel, the normal path now; `text_fallback` = channel skipped, we extracted from text — should no longer occur for content-bundle).

**`loadProjectSettings` flag:** Controls filesystem-settings scope:
- `false` (**default**, flipped 2026-09-18 for H22) → `settingSources: []` — pure SDK isolation
- `true` → `settingSources: ['project']` — loads project `.claude/skills/` and project `CLAUDE.md` only

We never load user-level (`~/.claude/`) or local sources. A probe found those contribute ~86K tokens of irrelevant context (superpowers meta-skill, MEMORY.md, MCP server instructions, two `CLAUDE.md` files) that none of our SDK calls use. **Project scope is not free either (H22):** this `CLAUDE.md` (~9.4K tokens), `.claude/settings.json` `enabledPlugins`, skill frontmatter and the nine agent descriptions come to ~15.5K tokens per call and ~75K per session, and nothing in the pipeline reads any of it (`ThemeLoader` loads its prompt files with `fs`). Hence the default is OFF; a call that genuinely wants the project skill asks for it. This is pure context hygiene — it does NOT prevent the channel skip described above; that's a separate SDK bug.

**Tool gating (H21):** `allowedTools` is a permission AUTO-ALLOW list in this SDK, not a restriction (0.3.282 `sdk.d.ts`: "To restrict which tools are available, use the `tools` option instead"), and it is a no-op under `permissionMode: 'bypassPermissions'`. A call with neither `tools` nor `disableTools` runs with the full set, **Bash/Write/Edit included** (and the default set changed across the 0.3 line). Every pipeline call now declares one: `disableTools: true` for pure text/structured output, `tools: ['Read']` for the two image calls. The server-start health call (`isClaudeAvailable`) passes `disableTools: true` as well. **MCP servers are gated separately:** `settingSources: []` does not stop the SDK loading the user's `~/.claude.json` MCP servers (the claude.ai connectors — a `tools: []` call still reported 103 `mcp__` tools, Gmail included, at `init`), so `client.js` always passes `mcpServers: {}` + `strictMcpConfig: true` (pinned by `lib/__tests__/sdk-mcp-isolation.test.js`). The tool names `init` reports on a pipeline call must be exactly the tools the call declared, plus `StructuredOutput` when the call has a schema: CLI 2.1.282 counts its own structured-output tool (at the 2026-09-25 gate an Opus call with `disableTools` and a schema reported `StructuredOutput` alone, a Haiku image call `Read` and `StructuredOutput`), which the 2026-09-19 probes on the old CLI did not. Any other tool, or a missing one, fails the isolation probe by name (`scripts/lib/probe-verdicts.js#isolationVerdict`). **Auto-memory is gated the same way:** the subprocess loads the operator's `~/.claude/projects/<cwd>/memory/` regardless of `settingSources` (a probe showed the model reading MEMORY.md's 33 entries), so `client.js` passes `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` through `options.env`; `init.memory_paths` must be absent (`lib/__tests__/sdk-memory-isolation.test.js`). Both are checked live by `scripts/probe-sdk-isolation.js`.

**Model Call Limits (idle timeout + cost ceiling):** SDK calls use a **15-min IDLE/stall timeout**, not a total-duration cap — the timer is re-armed on every streamed message (including the token-level `includePartialMessages` deltas emitted as `llm_delta`), so a legitimately long call (big prompt + extended thinking) survives as long as it keeps producing; only a genuine stall (no streamed activity for 15 min) aborts. A stall throws `SDK timeout after … idle … with no streamed activity`, which `isSdkTimeoutError` recognizes and `isTransientError` (`lib/llm/retry.js`) classifies **transient** (the node-level `retryPolicy` consumes this to auto-retry transient SDK failures). A runaway call is bounded separately by a **per-call `maxBudgetUsd` ceiling** (`MODEL_BUDGETS` in `lib/llm/client.js`: opus $100, sonnet $50, haiku $10). The pipeline runs on the director's subscription, so the figure is not a cost: the SDK derives it from token volume at list prices, and it exists only to stop a stuck loop before it burns the rate limit unattended. An overrun throws a labeled **non-transient** `error_max_budget_usd` that is never auto-retried (the budget is per-CALL, so N node-retries can cost up to N× the ceiling). Steady-state latency is still captured per-call via `duration_api_ms` on the `llm_complete` event (`lib/observability/progress-bridge.js`).

**Effort and thinking (operator gate 2026-09-19; Opus 5.5 since 2026-09-25):** `EFFORT_LEVELS` sets `xhigh` for opus and sonnet, sent explicitly on every call (Opus 5.5 defaults to `medium` when none is sent). The levels did not move with the Opus 5.5 pin; the 2.0 gate records every call's duration next to session 092026's first. On Opus 4.8, `xhigh` was a cliff for extraction-shaped prompts: the director-notes enrichment ended its first turn after thinking alone (~320s, no output), the SDK's structured-output enforcement re-requested, and the call cycled for 20 minutes without completing while re-arming the idle timer (it looked like a stall). `lib/director-enricher.js` therefore passes `effort: 'medium'` (165s; `high` 375s; both complete). The client also sets `thinking: { type: 'adaptive', display: 'summarized' }` for opus/sonnet — the default display on Opus 4.8 / Opus 5.5 / Sonnet 5 is "omitted", which streams thinking as EMPTY blocks, so a long think is a silent stream and the console's THINKING stage shows nothing. Opus 5.5 cannot run with thinking off (`disabled` and `budget_tokens` are both a 400), so on Opus the summarized text is also what keeps the idle timer fed. Arc analysis (286s) and outline/article generation completed at xhigh in the same run; if one of them ever shows the empty-thinking → `status: requesting` cycle, lower its effort per call.

**No model fallback:** the pipeline's calls are always served by their pinned model, never a substitute (integrator ruling, 2026-09-25). `client.js` sets `CLAUDE_CODE_NO_MODEL_FALLBACK=1` in `options.env` (pinned by `lib/__tests__/sdk-memory-isolation.test.js`, which holds the env to `process.env` plus exactly the three switches). In CLI 2.1.282 this is "the no-fallback guarantee": it turns the refusal fallback off (that lane's gate reads both this and `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK`), builds the availability fallback chain as the primary model alone, blocks model substitution, and makes a compaction that would need another model an error instead of a swap. An overload the CLI can then route nowhere ends the call as an `is_error` result whose assistant error is `server_error` ("API Error: Repeated 529 Overloaded errors…"). `isTransientError` treats the assistant errors `server_error` and `overloaded` as transient, as the CLI's own classifier does, so the node retry policy retries the call on the same model (`retry.test.js`, `client-contract.test.js`). A numeric status decides first: every 5xx is transient (a gateway's 502 or 504 too), 429 is the one transient 4xx, and every other explicit 4xx is permanent, whatever the assistant error.

**A model that wrote part of the answer and is not the pinned one fails the call** (integrator ruling, 2026-09-25; corrected 2026-09-26). The models that wrote the answer are the ones named on the call's own assistant frames (`message.model` on frames with no `parent_tool_use_id`; `answerModels` in `client.js`). When any of them fails `servedModelMatches` against the model the call resolved to, the wrapper throws `SdkModelSubstitutionError` (`lib/llm/model-substitution.js`; "SDK model substitution: requested claude-opus-5-5, served by claude-opus-4-8 - <label>; the result is not used", `sdkSubtype: 'model_substitution'`, with `requestedModel`, `servedModels` (the answer's models) and `substituteModels`). It emits one `llm_error` carrying both lists, `servedModels` (the result's modelUsage) and `answerModels`; a schema failure the result also has rides along as `cause`, with its `schemaErrors` on the `llm_error`. `isTransientError` classifies it permanent, through `.cause` and the message marker. **The result's modelUsage is recorded, not judged:** it also lists the CLI's own helper requests. On 2026-09-26 (session 092626) a Sonnet session-report parse listed `claude-haiku-4-5` beside `claude-sonnet-5` there while every frame of its answer was Sonnet's; the first version of this rule judged modelUsage and threw the correct answer away. A call with no frame naming a model has nothing to judge and returns. A subagent's frames (a `parent_tool_use_id`) are not the call's answer; pipeline calls run none. A substitute after a refusal signal is a declined request instead (next paragraph). The isolation probe and `check-model-freshness.js` judge `answerModels` the same way.

**Declined requests (refusals):** since 0.3.162 a declined request ends with `stop_reason: "refusal"` and `stop_details: {category, explanation}`. The category is `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms` or null (the installed `@anthropic-ai/sdk` 0.128.0 types; the CLI treats it as an open string). `lib/llm/refusal.js` reads every place the 0.3.282 types allow: the result's `stop_reason`, the assistant frame's `message.stop_reason`/`stop_details`, a `message_delta` stream event, and the CLI's `system/model_refusal_no_fallback` notice. No live refusal has been captured through this SDK, so each source is optional and pinned by mock (`client-contract.test.js`). The wrapper throws `SdkRefusalError` ("SDK refusal (category: bio): claude-opus-5-5 declined the request - <label>", `sdkSubtype: 'refusal'`) before any result branch, and emits one `llm_error` carrying `refusal` (and `schemaErrors`: the extraction failure's when the refusal names one, else null). `isTransientError` checks a refusal FIRST, through `.cause` and the message marker, so it is never retried. The four nodes that re-wrap SDK errors (arc analysis, character data, the whiteboard, photos) keep the original as `cause`. The paths that swallow errors into state keep the message: the evaluators (`evaluationHistory._error`, `errors`), `reviseArcs` (which never takes a refusal for its free timeout retry) and the enricher (`_enrichmentFallback.reason`). **A declined request is never answered by another model** (integrator ruling, 2026-09-25). The bundled CLI has refusal fallback routes of its own, keyed on the requested model and independent of the `fallbackModel` option: for `claude-opus-5-5` it retries `bio` and `frontier_llm` on `claude-opus-5` and `cyber` on `claude-opus-4-8`. `client.js` turns them off with `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` in `options.env`, and `CLAUDE_CODE_NO_MODEL_FALLBACK=1` turns them off as well (both pinned by `lib/__tests__/sdk-memory-isolation.test.js`). A main-thread fallback that runs anyway (a `system/model_refusal_fallback` whose `scope` is not `local`, or an assistant frame that `supersedes` the refused frames) throws `SdkRefusalError` at once, naming the category and the fallback model, and the `llm_error` carries it as `refusalFallback`. Any other failure after a refusal signal (a schema failure, an iterator throw, no result, an idle abort) is thrown as `SdkRefusalError` with the original failure as `cause`, so a stall after a refusal is never retried as a transient `SDK timeout`. A refusal signal followed by a clean, schema-valid finish on another stop reason returns the result, and `llm_complete` carries the signal as `refusalSignal` (in `diagnosticsOf`, so the call log has it). The exception: when the result's `modelUsage` names a model that is not the one the call resolved to under `servedModelMatches` (`lib/llm/sdk-fields.js`, shared with the probe scripts; a `[1m]` or dated suffix is the same model), another model finished the declined request, and the wrapper throws `SdkRefusalError` naming that model (a schema failure, if there is one, rides along as its `cause`). A result with no `modelUsage` has no other model to name and returns. Without a refusal signal, the same `modelUsage` is a model substitution (previous paragraph).

**What the 2.0 gate reads:** the `init` forward carries `effort` and `memoryPaths` as well as `model`/`betas`/`toolCount`/`toolNames`/`permissionMode` (the isolation probe prints the names on every init line, with the expected set above them). Neither is typed for `query()` calls in 0.3.282 (`memory_paths` is absent from the public `SDKSystemMessage`; `effort` is documented for Remote Control frames), so both are forwarded raw and absent is normal. ### Arc Analysis Architecture (Commit 8.15+; the weave since phase 4)

The arc writer writes **one weave** in one call (phase 4, brief 4.4; phase 4b, piece 3, brief 3B; spec 2026-10-06 sections 4 and 17; `lib/weave.js` holds its shape and the rules its readers share): two or three angles over one shared set of threads, which the director picks from and settles at the story meeting.
- the angles, each `{id, headline, gist, story, question, lands, ends, threads}` (`ANGLE_FIELDS` are the printed ones): a story the article could tell, its headline, its card's one sentence, the story in two or three sentences, the question it carries, why it lands with the players, where it ends up (its convergence), and the ids of the threads it tells, in the order it tells them, the verdict's thread among them (C1, C16);
- "from your notes" (`fromYourNotes`): the director's own words angle 1 rests on, copied exactly, present only when the notes end with the director's read. When the notes end without one, every angle is the writer's, the strongest first;
- the threads, `{id, name, line, verdict?, evidence}` (phase 4b, brief 1B): one shared set, each named for what happened with its people and said in one line at the level of the story; `verdict: true` marks the thread that carries the room's verdict. A thread has no role and no reason, and a thread no angle uses may stay, for the director to bring in;
- the connections, `{id, joins, line, kind, evidence}`, each one line where two threads touch, its kind (a person, a moment, a document or a line, `CONNECTION_KINDS`) underneath and unprinted; an angle uses the connections between its own threads;
- under each thread and each connection, its evidence (`lib/evidence.js` `EVIDENCE_PIECE_SCHEMA`), the pieces of the record that tell it, each `{sources, shows, stance}`: its sources (a document in the record by its id, `ledger`, `evidence-log` or `notes`, `EVIDENCE_SOURCES`), what it shows with the words or figures that matter, and whether it supports the line or cuts against it. The record's quotations, figures, times and ids sit there, never in the lines (C16), and the article writer cites from them;
- the questions (C15; see **The writers' questions**), each beside the thread its answer changes or by the pitch.

The single story, its question, headline and convergence, the roles (`WEAVE_ROLES`), the left-out reasons and the stronger main thread went with piece 3. The page the director reads at the meeting, with the labels code prints beside the writer's lines, comes to at most 450 words with any angle open (`MEETING_WORD_BOUND`, floor `MEETING_WORD_FLOOR` 350), and the writer's task asks for about 325 words of its own; the checks hold the writer's own words to their allowance (see **Arc Validation Routing**). The writer reads what it read before: the record and the morning timeline, the director's notes and corrections, the accusation word for word, the whiteboard reading, the roster with pronouns and the rule set. The lens work (C16) reaches the weave as the angles, each a different way the threads make a story, and as evidence marked supporting its thread or cutting against it. A theme supplies:
1. **Its config entry** in `THEME_CONFIGS` (`lib/theme-config.js`): its NPCs; `display.printsHero`, which `printedHero` throws without; its map slots (`map.slots`, each with its key, its label on the screen and its default heading), without which it has no story map; and `rules` and `identities` (below).
2. **Its rules folder**, the folder `rules` names, relative to `reports/`: `world.md`, `truth-rules.md`, the eight craft files `RULE_SET_CALLS` names (`lib/rule-set.js`), and the two mode files, `mode-on-site.md` and `mode-remote.md`. 3. **Its identity lines**, `identities` in its config, read through `identityLineOf(theme, call)`: one line for each call `IDENTITY_CALLS` lists. `IDENTITY_CALLS` derives from `RULE_SET_CALLS`: each call, and each writer's `-rework` beside it, while a judge's call opens `judge-` and has no rework (`arc` is the weave writer, `outline` the map writer, `judge-arc` the story meeting's fact check). The theme names its narrator, its publication and its form of output there, and no identity line sits in code (a source scan in `lib/__tests__/theme-rules.test.js` holds it). A writer's or a judge's line is a whole sentence. A rework's line opens its rework rules, and code completes it with the rework's task (`": the director sent it back, ..."`, `" after an automatic check ..."`), so it is a clause that ends on a word: `identityLineOf` refuses anything else, naming the theme and the call (`RUNS_ON_INTO_ITS_TASK`). `lib/__tests__/theme-config.test.js` runs every call of every theme that names a rules folder.
4. **Its templates** in `templates/{theme}/` (layouts and partials), its assets in `.claude/skills/{theme}-report/assets/`, and its image calls' prompt files in `.claude/skills/{theme}-report/references/prompts/`.

### Modifying Checkpoint Components

Each checkpoint component follows the same pattern:
1. Registers on `window.Console.checkpoints`
2. Receives `{ data, sessionId, theme, onApprove, onReject, onRollback, dispatch, revisionCache, pendingEdits, pendingNote }` props (`pendingNote`: the stop's note box, restored beside its edits after a remount)
3. Renders checkpoint-specific UI from `data`
4. Calls `onApprove(payload)` / `onReject(payload)` with the checkpoint-specific payload, or `onRollback(checkpointType)` to open the rollback modal

**Conventions:** `const` not `var`, direct destructured imports (no aliasing), `safeStringify` instead of `JSON.stringify`, CSS utility classes over inline styles, aria-labels on interactive elements, functional state updaters for Set manipulation, `useEffect` reset on data change.

`Article.js` validates the bundle on the desk through ONE local `gateEdits` helper that both the approve and the send-back call (the send-back passes `verb: 'send'`, so its message reads "Cannot send …"); a new path that sends edits goes through it too. Its gate is the desk's (task 4.3): it runs on every approve and every send-back, edited or not, on the bundle on the desk, with the desk's checks (`articleDeskLogic.deskProblems`) beside `validateBundleShape`, and its JSON path routes through it too. The map (`Outline.js`, task 4.9) has one send path, `send(action)`, which Approve and Send back both take: it holds the map on screen to `mapProblems`, the gate's decisions, then builds `mapPayload`; the map has no JSON editor. `__tests__/unit/console-edit-gates.test.js` pins both.

**An open editor or an unadded line holds the stop's actions** (task 4.14d). Text in an editor's form, the map's add line, the story meeting's add-a-thread line or the desk's JSON editor is in no payload until the director saves or adds it; before this task the stop's buttons sent without it, and no screen warned. `console/unsaved-input-logic.js` `unsavedInputLine(stop, open)` is the one rule. Each stop asks it once per render for each set of buttons that sends one thing, with what it has open: the meeting, about its add line holding text; the map, about an open editor (a move's named in the line by its words, never its id) or an add line holding text (Outline.js's `adding`, `{slot, move, players}`; brief 1F); the desk twice, since it sends two things. The desk's Approve and Send back (`'article'`, answer `held`) send the bundle on the desk, so they wait for any open editor and for JSON typed in the JSON editor (its text against `jsonSeed`, the text it opened with). The JSON editor's Save & Approve (`'article-json'`, answer `jsonHeld`) sends that JSON, so it waits for any open editor and for any change made on the desk after the JSON editor opened (`jsonSeededAt` against `deskVersion`); its line says to close the JSON editor and open it again. With an editor open too, its line names every step in order (task 4.14g): cancel the edit, or save it and then close the JSON editor and open it again, since a save changes the desk and a cancel does not; once the desk has changed since the JSON editor opened, either step is followed by closing and opening it again. `applyDesk` counts each change to the desk in `deskVersion`; a new way of putting a bundle on the desk counts it too, or this hold misses the change. While an answer holds, its buttons are disabled (Approve, Reweave, Send back, the two answers to `meetingApproveAsk`, the desk's JSON Save & Approve), its line shows beside them, and every function that sends a payload returns before building one (the meeting's and the map's `send`; the desk's `handleApprove` and `handleReject` on `held`, `handleJsonApprove` on `jsonHeld`). A new path that sends a payload checks its answer the same way, and new input that reaches a payload only through its own button goes to the rule with the rest. The desk's actions are one list, `checkpoint-view-logic.js` `DESK_ACTIONS`, which `reviewPayload`'s guard, this line and the harness's `STOP_ACTIONS` read, as the meeting's and the map's are `MEETING_ACTIONS` and `MAP_ACTIONS` (task 4.14g).

**Nor does any other control drop what was typed** (task 4.14g). A control that would close or replace an open editor, or an add line holding text, waits for it as the actions do: the component asks `unsavedInputLine(stop, open, control)` once per render for each kind, about the same `open` its actions are asked about. At the desk a pencil opens its editor in place of the open one (`startBlockEdit`, `startHeadingEdit`, `startSidebarEdit`, `startHeadlineEdit`), and a move, a delete or an insert puts a new bundle on the desk through `applyDesk`, which closes it, so each waits for any open editor (`'edit'`, `'move'`, `'delete'`, `'insert'`; answers `editHeld`, `moveHeld`, `deleteHeld`, `insertHeld`). None of them closes the JSON editor, so typed JSON holds none of them. On the map a pencil (`open`), Edit the words on a selected card among them, waits for an open editor (`'edit'`, `editHeld`), and "+ Add a move" (`openAddLine`) for an add line holding text (`'add'`, `addHeld`). On the board (piece 4, R9) selecting something else (`select`, `'select'`, `selectHeld`) and every other control on the selected card, the selected move in the tray or the selected photo (each through `whenFree`, `'move'`, `moveHeld`: Move up, Move down, Move to another section, Put a photo beside it, Leave it out, Take it out, Bring it back, a photo's places) wait for both, an open editor and a typed add line, so the board never changes under what the director typed. Closing what is selected waits for nothing, and neither does a drop: an editor is keyed by its line, and a card whose editor is open does not drag. The story meeting has no such control. A held control is disabled with the line as its tooltip (`utils.js` `editBtn(onClick, held)`, `deskButton`'s `held` option), its handler returns first, and the line shows under the open editor (at the desk through `withMarks`, which every desk editor renders through) or the add line; on the board a held click shows the line on the card or photo it reached (`heldAt`, `heldHere`), and a selected card's line sits under its controls. A new control that would close or replace what is open joins the rule's `CONTROLS` and checks its answer the same way. A hold is not an error: each held line is rendered by the stop's `heldLine` (the meeting writes its one out) with the class `.held-line`, never `.validation-error`'s red, which stays for a real refusal. `__tests__/unit/console-held-actions.test.js` pins the wiring, and `console/__tests__/unsaved-input-logic.test.js` the rule.

**`onRollback` is the only way a checkpoint may open the rollback modal.** It is the same `setRollbackTarget` callback the stepper uses, so Confirm goes through the existing streaming rollback. A component must NOT dispatch its own rollback action — ArcSelection's zero-arc dead end dispatched `SHOW_ROLLBACK`, which no reducer handles, so the only offered recovery logged `[state] Unknown action` and did nothing.

### Input-review reject flow (re-parse, not rollback)

`InputReview` is not approve-only. Approve sends `{ inputReview: true }`; Reject with Corrections sends `{ inputReview: false, inputFeedback: '<prose>' }`. `buildResumePayload` turns that into `{approved: false, feedback}`, and `checkpointInputReview` stores it as `_inputCorrections`, appends it to `inputReviewCorrections` (every correction of the session, in order), nulls `sessionConfig`/`directorNotes`/`playerFocus` so `parseRawInput` re-runs, and routes the graph back — `parseRawInput` appends every kept correction to every parse prompt, the whiteboard parse included, and the writers read them after the director's notes (see "The director's words as record"). A mis-parsed accusation, exposure, sale or quote is therefore fixed with a note, not with a rollback and a full re-collection. The roster, its pronouns, the reporting mode and the reporter's name are not: code stamps them from where the director entered them (the roster stop, the start form), no parse returns them, and a note leaves them as they are (phase 3, brief 3.5; spec D15). The parse's correction block says only that the corrections apply to what the parse reads from the source text. There is no `inputEdits` path (the key wrote a state channel nothing declared or read).

### Rolling back a COMPLETE session

A finished thread has no checkpoint (`GET /checkpoint` returns `checkpoint: null`), so neither rollback opener could be reached for it. `SessionStart`'s `'complete'` branch therefore loads the completion instead of resuming (resuming re-runs the whole paid pipeline): `SET_THEME` → `SET_SESSION` → `SESSION_COMPLETE_LOADED`, whose payload comes from `sessionStartLogic.completedResultFrom(checkpointResponse)`. That action sets `completedResult` plus `completedStepper`, and `app.js` renders `PipelineProgress` with `completedCheckpoints: CHECKPOINT_ORDER` above `CompletionView`, so every step is a rollback target and the existing `RollbackPanel` flow applies. Nothing is POSTed until Confirm. `CHECKPOINT_RECEIVED` clears `completedResult`/`completedStepper`, because App renders the completion branch BEFORE the checkpoint branch and a stale completion would hide the checkpoint the rollback just produced.

  - the naming rule (task 4.3b): `pairSectionBlocks` pairs a section's blocks across two versions, and `stayingInSection` keeps the longest run that kept its order; every other pair is a block the director moved, a move when unchanged and a cut and an addition when changed; a photo, a card or a reference pairs only with a block of its own name, so two the director swapped are two moves, each with its own caption or text (task 4.5d);
  - `deskChanges(opened, current)`: for each section, the blocks inserted, deleted, moved or edited since the stop opened, named by that rule, with `unchanged`, how many of its first blocks kept their place; the desk's marks anchor on it (`untouchedThrough`);
  - the pieces a mark sits beside (task 4.10): `printedPlaces(bundle)`, the headline, the byline, the hero, each section's heading and block and each sidebar card, with the words each prints (`PRINTED_TEXT_FIELDS`, which a test holds to `lib/hand-edit-diff.js` `PRINTED_BLOCK_FIELDS`), and `paragraphBlockIndex`, a paragraph's block from the fact check's ordinal;
  - what prints: the byline line by the header partial's rule (`bylineLabel`: the title and the guest reporter print only with an author), and the writer's money tracker (`writerTrackerState`, `writerTrackerDisplay`; see the `htmlPreview` row).

  `diffBundle` records a block the director moved as a move, within its section (with `between`, the blocks it follows and precedes) as across sections, and a Key Evidence entry they moved as a move within the sidebar (`diffSidebar`; task 4.14c), so the desk's moves and deletes are standing edits at a send-back. The desk and the diff name moved blocks by one rule: `lib/hand-edit-diff.js` requires the desk module, as `server.js` requires `outline-edit-logic.js`, and its `matchBlocks`, `stayingInSection` and `sectionKey` are the desk's own functions. Approve and Send back send exactly the bundle on the desk, edited or not. The desk shows what prints, field by field: it edits and labels only the fields a journalist template reads (`__tests__/unit/console-desk-prints.test.js` holds the fields it lists to the templates: a photo's and the hero's characters, a sidebar entry's placement, owner and layer, and a tracker row's category and date print nowhere, and the desk neither edits nor labels them), and each editor saves only the fields the director changed (`DeskLogic.changedFields`; the sidebar card's since task 4.3c), so a field the page does not print keeps its value.
- **The desk's marks** (task 4.10; spec 6.2 and 6.3). Nothing sits in front of the article. `checkpoint-view-logic.js` `deskView(data, current)` gives `Article.js`, and the harness, the echo of the settled story above the headline (`deskEcho`); each mark beside its piece (`deskMarks`, read per piece with `deskMarksAt`, keyed by `deskAnchorKey`), shown under it in the piece's row or under its open editor; the marks with no piece (`apart`), one line each beside the approve button, whose count stays the fact check's structural issues (`approveLabel`); and the folds below the article: the marks possibly resolved, the fact check's list, the round's `RevisionDiff`, and the trace through `traceView`. No score, no evaluation bar and no questions panel. A mark is `{key, tone, label, text, where, anchor}`; its tone is `judge` (an escalated evaluation's structural issue), `structural` or `advisory` (a fact-check finding), `concern` (a finding under one of the director's edit ids, or the judge's concern) or `changed` (an entry `changedEditsToShow` keeps). A fact-check mark's text is its finding's `line` (brief 4.10b; `findingLine`): what is wrong in the article at that place, in the director's words, never the message the rework reads; where the line holds `DOCUMENT_SLOT` (a copy of the fact check's, which a test holds equal), the card's document is named by its name and owner through the payload's `evidenceIndex`, as the story meeting names a piece's document (`receiptView`), and as "the document it cites" when the stop does not name it (the article stop's payload carries the index since brief 4.10c). A judge's mark, an issue left at the cap or a concern, reads past its leading rule ids, since the director reads the line, not the rule (`judgeMarkText`, after `concernFindingOf`; `LEADING_RULE_IDS` reads the ids as `lib/workflow/nodes/node-helpers.js` `leadingRuleIds` does, with the colon after them, and a test holds the two equal; brief 4.10c). Where it sits:
  - a paragraph finding by its section and ordinal while `untouchedThrough` holds, otherwise by its excerpt in a paragraph, its own section first, and a quote block's by its excerpt in a quote (brief 4.10b: its line names the piece it is about, and a card, a caption or a quote can hold the same words);
  - a headline, kicker or deck finding beside the headline while the field is as the stop opened it or holds the excerpt;
  - a card or a photo by its id or filename (the integrator's ruling 4): beside it, wherever it sits, while it is unchanged, and possibly resolved once the director changed or deleted it; its excerpt decides nothing;
  - the length on the heading of each section it counts;
  - a judge's issue or concern by a passage it quotes, read as the server's guard reads one (`locatingPassages`: split at an elision, three words or more, never a heading; a test holds it to `lib/hand-edit-diff.js` `locateQuotedText` on a corpus of findings, and `quotedPassagesOf` and `groundingText` to `lib/grounding.js`'s);
  - a changed edit beside what the director's text became, its section first; an entry about a whole section, whose text no one piece prints, such as a section the director put in whole that code put back without a photo the article cannot print, on that section's heading (`wholeSectionKey`; brief 4.10e).

  A mark whose text only the article as the stop opened it held folds below as possibly resolved, and one with no piece at all is apart. The marks follow the bundle on the desk: each move, edit or delete moves them.
- **Edited ARTICLES have two gates:** client-side, on every approve and send-back, the desk's checks and `EditLogic.validateBundleShape(bundle)` (the inline editors and the JSON editor alike); server-side, the `content-bundle` schema, which stays the last word on shape. `validateBundleShape` is deliberately never STRICTER than `content-bundle.schema.json` — `heading` stays optional, `metadata.generatedAt` is not required — because a false block on a bundle the server would accept is a dead end the director cannot clear. A test pins that direction. The empty-block check is the desk's, apart from it, because it is stricter by design: a blank paragraph passes the schema, and `validateContentBundle` would drop it without a word after the approve.
- **The pencil has two reveal modes** (pinned by `__tests__/unit/console-editable-pencils.test.js`):
  - `article-block--editable` alone → hidden until `:hover` / `:focus-within`, for a full-width host whose own first line reaches the top-right corner (an always-on corner button landed on the article's prose at 19 of 54 rendered blocks).
  - `+ article-block--editable-always` → rendered at low opacity, full opacity on hover/focus. **The map's hosts only** (each line at the host's left and its controls under it, so the corner is free) plus a `padding-right` gutter, which the hosts' own rules keep by setting their padding with the longhands. `Outline.js` routes every host through its `ALWAYS` constant: the headline and deck, the gap note, each column's head and the length. A move is a card, whose words open from Edit the words on its selected card, so it is no pencil host (brief 4D).

  The **article** desk uses neither: each piece of the article is a `deskRow` whose pencil and block controls (move, delete, insert) sit in `.desk-rail`, a grid column of its own beside it, so every editor is visible and none covers the prose. The old outline's screen emitted neither class at any of its 13 call sites, so its whole editor layer was `display: none` forever. The always-visible rule is a **descendant** selector: a host may hold its button at any depth, and a child selector misses every button that is not a direct child.
- **Reset effect** is keyed on `EditLogic.computeResetKey` (collision-resistant): the map's through its version (`mapVersion`), `Article.js`'s on `(data, revisionCount)`. Do NOT revert to a truncated `safeStringify(...).slice(0, N)` — it collides across revisions and leaks stale edits.

## API Reference

### Session REST API

**Step-by-step Pipeline Control:**
- `/api/session/:id/start` (POST) - Start new session with raw input. **The session ID must be the session date as MMDDYY** (`091826`), optionally with one extra digit for a second session the same day (`0918262`); anything else is a 400 (B1: the emailer builds each player's report link from this id, and `data/<id>/` + `outputs/report-<id>.html` are named after it). `ALLOW_NONSTANDARD_SESSION_ID=true` in the server's env opts out for throwaway harness runs. **A session id whose thread already exists returns 409** `{currentPhase}` unless the body carries `{force:true}` (C1). A forced start seeds `buildFreshStartState()` (`lib/api-helpers.js`), which clears EVERY state channel except `theme`, `sessionId` and the new `rawSessionInput` — including the photo channels (`sessionPhotos`, `preprocessStats`, `photoAnalyses`), the raw full-context inputs and the parse. Fresh start is its OWN list (`FRESH_START_CLEARS` in `lib/workflow/state.js`), never a rollback target: `buildRollbackState('input-review')` deliberately preserves everything upstream of the parse, so seeding a start from it kept the old photos, roster and parse and paused once on them.
- `/api/session/:id/resume` (POST) - Resume existing workflow (re-invoke at current state). NON-BLOCKING: returns `{status:'processing'}` immediately, runs the graph in the background, and delivers the result via the `/progress` SSE `complete` event (same contract as `/approve`). Clients MUST use SSE-before-POST. (A long re-invoke would otherwise exceed undici's 5-min `headersTimeout` / Cloudflare's ~100s edge timeout on a held-open POST.) **A COMPLETE thread returns 409** `{currentPhase:'complete'}` unless the body carries `{force:true}` — re-invoking a finished thread replays it from START, and every skip condition is already satisfied, so the whole paid pipeline re-runs unattended and overwrites the session's inputs and published report (B9). A thread from before the story meeting, or one on an earlier shape (phase 4's, or piece 1's weave with no angles), returns 409 `{oldThread}` first, `force` or not (task 4.11, briefs 1G and 3E; see **Threads from before the story meeting**).
- `/api/session/:id/approve` (POST) - Submit checkpoint approval. A thread from before the story meeting, or one on an earlier shape (phase 4's, or piece 1's weave with no angles), returns 409 `{oldThread}` (task 4.11, briefs 1G and 3E).
- `/api/session/:id/rollback` (POST) - Roll back to checkpoint. NON-BLOCKING (same contract as resume/approve); the SSE completion payload carries `rolledBackTo` + `fieldsCleared`, the channels the rollback's seed cleared (`rollbackSeedClears`: the point's list, and on an old-shape thread's rollback to the meeting the weave's channels too; fix round 3). **A rollback also invalidates the evaluations it makes stale** (I1): `buildRollbackState` appends `{phase, ready:false, reason:'rollback-invalidated', source:'rollback'}` for `article` when rolling back to `article`, `outline`, `photos` or `character-ids` (the outline's stub went with the outline judge, brief 4.6; see `PHASES_INVALIDATED_BY` in `lib/api-helpers.js`), because those four points preserve `evaluationHistory` and `evaluatePhase`'s skip logic returns early on a most-recent entry that is `ready:true` or (since 3.9) escalated to the director — so without the stub the regenerated article skipped both the Opus evaluation and the programmatic fact-check and the gate opened on the PREVIOUS article's verdict. `arc-selection` and everything upstream clear the history outright, so they need no stub. A rollback to `arc-selection` reopens the story meeting with no model call, the weave kept as the director left it (R9; see **The story meeting**), and a rollback to `outline` reopens the map the same way (see **The map**). A thread from before the story meeting, or one on an earlier shape (phase 4's, or piece 1's weave with no angles), may roll back only to `arc-selection` or a point before it, and every later point returns 409 `{oldThread}` (task 4.11, briefs 1G and 3E); on an earlier shape the rollback to `arc-selection` clears the weave too, so it is written fresh.
- `/api/session/:id/state` (GET) - Get current state
- `/api/session/:id/state/:field` (GET) - Get single state field
- `/api/session/:id/evidence`, `/arcs`, `/outline`, `/article` (GET) - One resource each (`RESOURCE_ENDPOINTS` in `server.js`), `{sessionId, available, ...}`: the evidence bundle; the weave as the director last left it (brief 4.5); the map (brief 4.6); the article with its HTML. `available` holds once the run has reached the resource's phase and holds it.
- `/api/session/:id/article/preview` (POST) - The desk's preview (task 4.3): the body `{contentBundle}` is the bundle on the desk, rendered by `lib/article-preview.js` with the session's theme, photo paths and ledger, as `htmlPreview` is, and the answer is `{html, writerTrackerPrints}`; 400 without a bundle, 404 for a session with no thread, 422 with the reason for a bundle the page cannot print. Read-only: nothing is stored and no graph runs.
- `/api/session/:id/checkpoint` (GET) - Get checkpoint info: `{sessionId, currentPhase, interrupted, checkpointType, checkpoint, theme, inProgress, lastOutcome, oldThread}`. `checkpoint` is the SAME merged payload the SSE/approve path delivers (`buildCompleteCheckpointData`, so state extras like `sessionPhotos` are included), or null when not interrupted. `inProgress` is `isSessionLocked(id)` and `lastOutcome` the persisted outcome, so a client can reattach to a run instead of blind-POSTing into a 409 (H1, H2, H8). `oldThread` flags a thread from before the story meeting, whose stop is sent as `{type, oldThread}` alone; one at no stop has the flag and a null `checkpoint` (task 4.11; see **Threads from before the story meeting**).
- `/api/session/:id/progress` (GET, SSE) - Stream pipeline progress events

**Utility:**
- `/api/health` (GET) - Health check
- `/api/config` (GET) - Client configuration: `{notionConfigured, allowNonstandardSessionId, parkedThemes}`. The console validates the session ID against the same MMDDYY contract `/start` enforces, so it needs the `ALLOW_NONSTANDARD_SESSION_ID` opt-out. `parkedThemes` is `PARKED_THEMES` (R1): each theme `/start` refuses, with the line it refuses it with, which the start form shows beside that theme's choice (task 4.8).
- `/api/browse` (GET) - List session data files
- `/api/file` (GET) - Read session data file

See `server.js` for detailed usage and request/response shapes.

**Non-blocking endpoints** (`/start` excepted — it interrupts in seconds): `/approve`, `/resume`, `/rollback` all run their `graph.invoke` in the background via `lib/api-background-runner.js#runGraphInBackground` (one source of truth for the CONC-1 lock + DUR-2 drain + DEL-1 outcome + the stops log's lines + SSE `emitComplete`). The sessionId-keyed lock gives mutual exclusion across all three; a concurrent second call gets a 409.

```bash
cp .env.example .env
# Required:
```

## Troubleshooting

**SDK not available:** `claude /login` then `npm ci --os=win32 --cpu=x64`. "Claude Code native binary not found" means the optional platform package (`@anthropic-ai/claude-agent-sdk-win32-x64`) is missing: reinstall on the machine that runs the server with `npm ci --os=win32 --cpu=x64`, not from WSL. The director's `~/.npmrc` sets `os=linux`, and a plain install fetches Linux builds with no `sharp` binary and no CLI binary.
**Workflow errors:** Check logs for missing input files, expired Notion token, or SDK timeouts
**Resume behavior:** State persists via `MemorySaver` checkpointer
**Photos directory not found after arc selection with a start-time path:** the failure card now offers a rollback to `photos` (free); the API form is `POST /rollback {rollbackTo:'photos'}` / harness `--session <id> --resume --rollback photos`; do not roll back to `arc-selection`: it reopens the story meeting with no model call (R9) but keeps the path, so the same failure comes back after the meeting's approve.

See `PIPELINE_DEEP_DIVE.md#common-debugging-scenarios` for detailed debugging guides.

## Refining Generated Reports

Pipeline-generated reports contain systematic factual errors that read as plausible. The repo has a structured **two-pass refinement workflow** driven by the user-level `refining-aln-reports` skill (auto-loads when you mention reviewing/editing a session report).

**Working-file convention** (in `outputs/`, all prefixed `report-MMDDYY-`):

| Suffix | Pass | Purpose |
|--------|------|---------|
| `-refsheet.md` | Pre-read | Ground truth built from source data (`data/{id}/`) BEFORE reading the article. Roster, pronouns, accounts, transactions, accusation. |
| `-findings.md` | Pass 1 (fact-check) | Claim-by-claim verification against refsheet. Flags fabrications, evidence-boundary violations, pronoun errors. |
| `-editplan.md` | Pass 1 (fact-check) | Section-by-section rewrite plan addressing findings. |
| `-draft.md` | Pass 1 output | Revised prose (Markdown, not HTML) after applying editplan. |
| `-findings-copyedit.md` | Pass 2 (copy-edit) | Examines the **fact-corrected** article (not the original) for pacing, redundancy, throat-clearing, abstract→specific. |
| `-editplan-copyedit.md` | Pass 2 (copy-edit) | Structural and sentence-level polish plan. |

**Two-pass discipline:** Fact-check and copy-edit are separate cycles. Copy-edit always operates on the fact-corrected article, never the original. Don't pattern-match em-dashes from older reference reports (they predate the no-em-dash rule).

**Final HTML output:** Published as `outputs/report-MMDDYY.html`. The matching `assets/images/MMDDYY/` directory must exist before publishing.

**Editorial intent fetch:** If the pipeline server is running, the refinement skill pulls the director's checkpoint feedback from `/api/session/:id/state/:field` to inform the refsheet: `directorGateNotes`, every note the director sent at a stop, each with its gate, its kind (`approval` or `rejection`) and the round of its stop (`stopRound`); `weave`, the story as the director left it at the story meeting; `outline`, the map as they left it; and `_rescuedItems`. The `_arcFeedback`, `_outlineFeedback` and `_articleFeedback` slots hold a note only until its rework runs, which clears them before the stop opens (task 4.12e), and `selectedArcs` went with the arc selection (R4). The approved versions are on disk too: `analysis/weave.approved.json`, `analysis/map.approved.json` and `output/content-bundle.approved.json`.
