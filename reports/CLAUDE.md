# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**ALN Director Console** - AI-powered investigative article generator for "About Last Night" using Claude Agent SDK with LangGraph workflow.

Generates journalist-style investigative articles by:
1. Fetching memory tokens and paper evidence from Notion database
2. Curating evidence bundle using three-layer model (exposed/buried/context)
3. Analyzing narrative arcs via single SDK call with player-focus guidance
4. Generating the story map (the article's outline) and the final HTML report with human-in-the-loop checkpoints

**Production URL:** `https://console.aboutlastnightgame.com` (via Cloudflare Tunnel)

**Deep Dive:** For business context, game mechanics, phase-by-phase breakdown, and detailed debugging scenarios, see `docs/PIPELINE_DEEP_DIVE.md`.

## Architecture

### LangGraph Workflow (6 Phases, 44 Nodes)

```
Phase 0: Input Parsing (conditional) → Phase 1: Data Acquisition → Phase 1.6-1.8: Processing
→ Phase 2: Arc Analysis (player-focus-guided)
→ Phase 3: The Map (outline) → Phase 4: Article → Phase 5: Assembly
```

*See lib/workflow/graph.js for complete node list*

**Human Checkpoints (11 total - workflow pauses for approval via native `interrupt()`; `photos` is conditional):**

For data flow at each checkpoint, see `PIPELINE_DEEP_DIVE.md#phase-by-phase-breakdown`.

|------------|-------|---------|

**Approval payloads** (`buildResumePayload`): `{inputReview: true}` approves the parse; `{inputReview: false, inputFeedback}` rejects it with prose corrections: `checkpointInputReview` stores the round's correction as `_inputCorrections` (the trigger the re-parse consumes and clears) and appends it to `inputReviewCorrections`, the whole list in order, and `routeAfterInputReview` routes back to `parseRawInput`. Every parse prompt gets the whole list: steps 1 and 2, the enrichment and the whiteboard parse (see **The director's words as record**). At the character-IDs stop, `{characterIdsRaw | characterIds, photoDescriptions?, leftOutPhotos?}` carries the director's `{filename: text}` descriptions and the filenames whose leave-out box is ticked beside the ids (the stop's Skip sends `{characterIds: {}, leftOutPhotos}`); `buildResumePayload` refuses a malformed map, a leave-out list that names a photo the stop did not show, and a structured `characterIds` that is not an object of one mapping object per photo, naming the key at fault (the Skip's empty `{}` is taken; task 4.3c). The structured form also writes `characterIdsRaw: null`, so the parse reads only the current round's text: that channel survives a rollback, and a Skip after one runs no parse, so the boxes decide (brief 4.2b). At the story meeting, `{meeting: 'approve' | 'reweave' | 'send-back', weave, note?}` (see **The story meeting**); the arc selection's `selectedArcs`, `outlineGuidance` and `arcFeedback` are refused by name. At the map, `{outline: 'approve' | 'send-back', map, note?}` (see **The map**); the old outline payload (`outline: true | false`, `outlineEdits`, `outlineFeedback`, `outlineNote`) is refused by name. An article rejection may carry the director's edited object — `{article:false, articleFeedback, articleEdits?}` (spec `docs/superpowers/specs/2026-09-19-director-steering-design.md`). It is validated exactly like an approval, becomes the version the reviser starts from (`incrementArticleRevision` copies it into `_previousContentBundle`), and its changes join the director's standing edits at that stop (see **The director's edits are final** below), which the reviser renders as a `<HAND_EDITS>` block between HUMAN FEEDBACK and the revision instructions. A photo the director deleted at the desk (a photo block of the bundle the stop showed whose filename appears nowhere in `articleEdits`, `deskDeletedPhotos` in `server.js`) joins the leave-out list at the approve or send-back that carries the delete, through 4.2's `leavePhotosOut` (brief 4.7b), so after a send-back it stays out of the rework's PHOTOS and the map it reads, the judge's photo check and publish. The revisers never clear the edits (an evaluator-driven second pass must still see them), and the article checkpoint clears the edits and the report on approve; the map's edits, like the meeting's, stand past approve. Every note the director sends is appended to `directorGateNotes` with its kind: `rejection` for the note sent with a send-back, `approval` for a note sent with an approve (`articleNote`, and the map's and the meeting's `note`) (phase 1, 2026-09-20). It is a REPLACE channel the server appends to by writing the full array; `round` counts per stop and kind. Each note also records the round of its stop it was sent in (`stopRound`, one more than the stop's `human*RevisionCount`), and `appendGateNote` appends no note whose gate, kind and text match a note already standing from that round, so a director who retries a round whose rework did not run, with its note, files the note once; the same words in a later round file again (brief 4.5c). At the story meeting the note of a round that did not run stands only if the director's next action sends it again: a round with the same words keeps it as filed, Approve with it in the box files it as an approval note in its place, and an approve that clears it, or an action with another note or none, leaves it out (`withdrawUnrunRoundNote`; `lib/meeting.js` `unrunRoundNoteIndex` finds the note; brief 4.5c, fix round 1). `pruneGateNotes` drops the invalidated stops' REJECTION notes on a rollback to `arc-selection`/`photos`/`character-ids`/`outline`/`article` and keeps their approval notes, which are forward guidance for the writer the rollback creates; the stops each point invalidates are a table of their own, `STOPS_INVALIDATED_BY` (`lib/api-helpers.js`; brief 4.5), apart from the evaluation stubs' `PHASES_INVALIDATED_BY`, and the rollback handler writes the pruned notes through `rollbackNotesUpdate`; points above `arc-selection` clear the channel. Notes render as standing notes inside `<DIRECTOR_GUIDANCE>` for every later writer and reviser; `filterGateNotes(notes, currentFeedback, gate)` keeps the note a rework is acting on (already its HUMAN FEEDBACK) out of that list, and throws without a gate. The arc selection's guidance channel, `_outlineGuidance`, went with its last readers, the article writer and its rework (brief 4.7b; R4): a note sent with the story meeting's approve is a standing note of kind `approval`, and the standing notes are the whole of `<DIRECTOR_GUIDANCE>`. Since brief 4.7c the builders take the notes alone: `buildDirectorGuidanceSection(gateNotes)` and `_buildDirectorGuidance(gateNotes)`, the first throwing on the old guidance-first call.

**The director's edits are final** (before phase 4, F1 and FA; spec `docs/superpowers/specs/2026-10-02-story-meeting-and-map.md` section 7). An automatic pass never changes a line the director wrote: a judge that disagrees with one lists it for the director, and code puts back what a pass changed anyway. A send-back's changes are the director's edits, one per field the director changed (`lib/hand-edit-diff.js`), `{id, scope, path, at, before, after}`: `at` is the steps to the field, each element of a collection found by what names it (a section's id, a card's tokenId, an arc's name, a block's type with its text, filename or tokenId), and `path` the same place for reading (`sections[#closing].content[0].text`, `theStory.arcs[0].photoPlacement.purpose`, `financialTracker.entries[1].amount`). A card's headline, one arc's photo placement, one tracker entry's amount and a photo's caption apart from its filename are each one edit, so the writer's untouched text beside them stays the writer's (FA, requirement 2); an element the director added whole is one edit whose `after` is the element. A section's blocks pair only with blocks of their own type, so a block retyped (only the JSON editor retypes one) is a cut and an addition (task 4.3c), and a photo, a card or a reference only with one of its own filename or tokenId (`pairSectionBlocks`), so one renamed is a cut and an addition too, and two the director swapped are two moves, each keeping its own caption or text (task 4.5d). A null `after` is a cut, whose `before` is the text removed and whose `pieces` are each of its sentences of three words or more that the director's version no longer held. A rewritten text field also records `removed`: each sentence of its old text the director's version no longer holds, as written (requirement 3). A block that left one section and arrived unchanged in another is one edit, a move, whose `from` names the section it left (requirement 4); a block the director moved within its section is a move too, whose `between` names the blocks it follows and precedes (task 4.3, the desk). A move is the block's place only: the director changed none of its fields, so its text is still the writer's, which the judges, the guard and the fact check read as the writer's (fix round 1, finding 2). Given the session roster's names (both send-back arms of `buildResumePayload`), a cut or a rewrite records `names`: the names its text held that the director's version no longer names (requirement 9). An edit's id (`E1`, `E2`, ...) is stable within its stop. The edits stand at their stop across every send-back (`standingAfterSendBack`): `_outlineHandEdits` / `_articleHandEdits` hold `{kind, issued, edits}`; an earlier edit stands while the version the stop showed and the version sent back carry it (a field edit, while the element it belongs to holds the director's value, a section's block found in any section; a move, while a block of its identity (its type with its filename, tokenId or text) sits in the director's section, whatever its other fields, and a move within the section while it also keeps the director's order there, or, where the director's own move of a neighbour broke that order at a send-back, while it sits among the blocks that kept their order in it, re-anchored to its neighbours there (task 4.3b); a cut, while none of its pieces is back), a removed sentence that came back drops from its edit, and the send-back's own edits join with the next ids after `issued`. Text is read from the fields the page prints (`PRINTED_FIELDS`, which the article judge's `printedBundle` reads too; known item 6), and a piece under six words is back only as a whole sentence (known item 4). A diff stored before F1, or an edit stored before FA, reads as the same field-level edits. At the article stop, approve, a rollback and a fresh start clear them (the map's and the meeting's stand past approve and through the rollback to their own stop, R9), and approve-with-edits runs no rework. Every reader takes the edits the version in hand carries (`carriedEdits`):
- The reworks' `<HAND_EDITS>` block (`buildRevisionContext`) lists them by id and place with the director's text (`formatEditLines`: text quoted, an element by its fields, never JSON; a move by its place, and a block its text names by the words it begins with), each removed sentence on a `removed:` line under its edit, after `EDIT_LINES_GUIDE` (an edit covers only the place its line names, and a moved block's text is still the writer's), in one of two wordings. On an automatic pass each edit stays exactly as written, and each cut and each removed sentence stays out. On a send-back the same holds unless the structural change the note asks for means an edit no longer fits, and the rework returns each edit it changed, removed or brought back in `changedDirectorEdits`, with one sentence on why. That list exists only in the rework call: its schema is built in code from the stored one on a send-back that carries edits (`reworkSchemaWithChangedEdits`, `ai-nodes.js`; `lib/schemas/*.json` are unchanged), and the node takes the list out before it stores the output (`takeChangedEdits`). A rework never reads a finding located in the director's text (`withoutDirectorsFindings`, requirement 7): the issues, suggestions and criterion notes and fixes that quote a standing edit are left out of its context, and so are the judge's guidance and the notes and fix of a criterion under the rule ids of an issue left out (the verdict's `criteriaRules`, which `createEvaluator` writes; requirement 5). At a send-back that verdict is the one the stop showed, which no judge wrote with the director's newest edits in view.
- The article judge reads them right after the output it judges (the outline judge left in phase 4, brief 4.6, and the detective's article judge in brief 4.7a, R1) (`renderJudgeDirectorEdits`, from `judgedEdits`, which `createEvaluator` and `scripts/lib/render-calls.js` both pass as `directorEdits`), with the same `EDIT_LINES_GUIDE`: the director's text is record, the judge scores the writer's text, and a disagreement with an edit, or a cut or removed sentence it would bring back, goes in `advisoryWarnings`, opening with `DIRECTOR_EDIT_PREFIX` (`"Director's edit "`) and the edit's id, then the rule.
- The verdict guard (`guardDirectorEdits`, in `createEvaluator` before readiness is decided). A structural issue that quotes the director's text (an edit's, a cut's or a removed sentence's) moves to `advisoryWarnings` as `Director's edit <id>: <the issue>`, whatever else it quotes, since a quote of the writer's text in such an issue is usually where the problem sits or where a fix would go (requirement 1); so does an issue the judge filed under the prefix and a standing edit that owns text, and a judge's advisory that quotes the director's text is a concern in its own place (requirement 6). A finding the judge filed under the prefix and edits that own no text alone (`hand-edit-diff.js` `ownsNoText`: a block moved at the desk, a connection brought back at the meeting) is read by its quotes, as one with no prefix is, since a place holds only the writer's text: a quote of the director's text makes it a concern under the edits it quotes, and otherwise it is the writer's must-fix, whichever list the judge filed it in (task 4.5e). The quote match is `locateQuotedText`: `grounding.js` `quotedPassages`, split at an elision, passages of three words or more, `isVerbatimIn` in any case; a passage equal to a section heading is a location and locates nothing (known item 3); a passage the writer's printed text holds is the writer's, a moved block's text included (and at the story meeting the words of a connection the director brought back, task 4.5d), unless it sits only in the content of a writer's evidence card and the record holds it too (`recordTexts`), which is the record cited (known item 5). A criterion whose notes or fix quote the director's text keeps them from the rework, and one that failed joins the concerns as `Director's edit <id>: <rule ids or name>: <notes> <fix>` unless a concern already covers it. A criterion a concern covers (one under its rule ids or its name, or, for a criterion with no rule ids, one about the same edit) keeps its notes and fix from the rework and holds the output only while a structural issue under its rule ids remains (requirement 5); a failed truth criterion that no finding names and no concern covers is a must-fix line (`truthIssueLines`). The judge's guidance is left out when an issue moved or it quotes the director's text. The output is ready when no structural issue remains and every structural criterion that failed is one a concern covers; the judge's own `structuralPassed` does not hold an output with nothing left to fix. With no edits nothing changes. The concerns ride in the history entry, for the stop, and never in `validationResults`, so no rework reads them.
- The fact check (`directorEdits`, from `buildFactCheckArgs`), field by field (`editLocator`): a card's content that is not verbatim is an advisory under the edit's id when the director wrote the content, and stays structural on a card whose headline alone the director changed. An unknown source on a card the director edited, inline or in the sidebar (requirement 10), a reporter-mode phrase in a paragraph's text the director wrote, a photo whose filename the director set, and a roster player whose last mention the director's version dropped (the names the edit recorded; an edit stored without names, by whether its cut text names the player) are advisories too, each with its existing message after the prefix. The photo check and roster coverage's hero caption read the photos the page prints (`lib/publish-photos.js` `printedPhotos`), so a detective hero, which never prints, is not checked (requirement 12). The same hit in the writer's text keeps its status, a block the director only moved included; `cardFidelity` marks a director's card with `directorEdit`, and `missing`, `invalid` and `violations` list the structural hits only. A section's key is `hand-edit-diff.js` `sectionKey`, one rule for both modules (known item 7).

**The story meeting** (phase 4, brief 4.5; spec 4.3, 4.4 and section 7; R9, R11, R12). The arc stop is the meeting where the director settles the weave before anything is planned. `lib/meeting.js` holds its payloads and what its stop shows; `lib/weave.js`, `lib/hand-edit-diff.js` and `lib/writer-questions.js` hold the rules its readers share.
- **The director-side schema** (`DIRECTOR_WEAVE_SCHEMA`): the writer's `WEAVE_SCHEMA`, derived in code, with an `answer` on a question and `struck: true` on a connection; like the writer's, it lets a thread have no receipt and no reason. The payload gate validates against it (Ajv, strict) and refuses a malformed weave with the reason. **Photo spacing** (spec 2026-10-02 section 9): the page never prints two photos in a row, except when the photos outnumber the blocks that can separate them. `TemplateAssembler.buildContext` passes the sections through `spacePhotos` (`lib/photo-spacing.js`, whose header states the whole rule) before it maps them and builds the section nav, for both themes, so the publish step, the article stop's `htmlPreview` and `scripts/assemble-article.js` print one order. **Structured Output Contract:** When `jsonSchema` is provided, the call returns a schema-valid object or throws `StructuredOutputExtractionError`. The wrapper sends the schema to the SDK's `structured_output` channel and validates the result; if the SDK channel ever skips (see #277 below), it falls back to extracting JSON from the `result` text and validating it against the schema.

**SDK #277 channel skip — root cause is the `format` keyword (FIXED 2026-06-23, branch `fix/sdk-format-channel-skip`).** [anthropics/claude-agent-sdk-typescript#277](https://github.com/anthropics/claude-agent-sdk-typescript/issues/277) (OPEN, `bug` label): the SDK's constrained-decoding subsystem (triggered by `outputFormat: { type: 'json_schema' }`) can fail silently — returning `subtype: 'success'` with `structured_output: undefined` and `stop_reason: end_turn`, so the model emits JSON as `result` text instead of via the tool channel. We long attributed this to schema *shape* (nested `additionalProperties:false` + `oneOf` + `$ref`), but a single-variable opus probe proved the actual trigger in this SDK build is the JSON-Schema **`format` keyword** (e.g. `format:"date-time"`) — NOT `oneOf`/nesting/`additionalProperties`, all of which keep the channel engaged. `content-bundle.schema.json` carried one `format:"date-time"` on `metadata.generatedAt`; removing it re-engages the channel for content-bundle generation AND revision (both themes), verified live on session 062126. (Note: the claude-api structured-outputs doc lists `format:date-time` as *supported* — this SDK build empirically chokes on it.)

**The fix (two layers, both in place):**
- `format` removed from the two schema files that had it (`content-bundle.schema.json` metadata.generatedAt, `preprocessed-evidence.schema.json` preprocessedAt) — both validated server-stamped timestamps, so zero validation lost.
- **Guardrail** — `lib/llm/client.js#sanitizeSchemaForSdk` strips `format` (only string-valued, so a data property *named* `format` survives) plus `$id`/`$schema` from any schema before it reaches `outputFormat`, memoized per original object and fed to BOTH the SDK channel AND the extractor. So a future `format:` can't silently regress the channel, and the SDK constraint can't disagree with post-hoc validation. The memo + `$id`-strip also avert an ajv `"schema with key or id 'content-bundle' already exists"` collision across generation→revision in one process (the extractor's module-level ajv registers `$id` globally). **Never re-add `format` to a schema passed to the SDK** — the guardrail strips it, but keep the schema files clean.

**Retained as defense-in-depth** (the SDK channel is the normal path now; these are backstops if it ever skips again):
- The embedded `<SCHEMA>` text in `lib/prompt-builder.js#buildArticlePrompt` / `lib/workflow/nodes/ai-nodes.js#buildArticleRevisionPrompt` (gives the model the shape contract directly), and the map writer's and its rework's `<SCHEMA>` (the theme's map schema, `mapSchemaFor`; the outline's since phase 3, fix 3.2b).
- `lib/llm/structured-output-extractor.js` path 2 — text extraction + ajv validation.
- The `channel` field on `llm_complete`/`llm_error` tells you which path fired (`structured_output` = SDK tool channel, the normal path now; `text_fallback` = channel skipped, we extracted from text — should no longer occur for content-bundle).

**`loadProjectSettings` flag:** Controls filesystem-settings scope:
- `false` (**default**, flipped 2026-09-18 for H22) → `settingSources: []` — pure SDK isolation
- `true` → `settingSources: ['project']` — loads project `.claude/skills/` and project `CLAUDE.md` only

We never load user-level (`~/.claude/`) or local sources. A probe found those contribute ~86K tokens of irrelevant context (superpowers meta-skill, MEMORY.md, MCP server instructions, two `CLAUDE.md` files) that none of our SDK calls use. **Project scope is not free either (H22):** this `CLAUDE.md` (~9.4K tokens), `.claude/settings.json` `enabledPlugins`, skill frontmatter and the nine agent descriptions come to ~15.5K tokens per call and ~75K per session, and nothing in the pipeline reads any of it (`ThemeLoader` loads its prompt files with `fs`). Hence the default is OFF; a call that genuinely wants the project skill asks for it. This is pure context hygiene — it does NOT prevent the channel skip described above; that's a separate SDK bug.

**Tool gating (H21):** `allowedTools` is a permission AUTO-ALLOW list in this SDK, not a restriction (0.3.282 `sdk.d.ts`: "To restrict which tools are available, use the `tools` option instead"), and it is a no-op under `permissionMode: 'bypassPermissions'`. A call with neither `tools` nor `disableTools` runs with the full set, **Bash/Write/Edit included** (and the default set changed across the 0.3 line). Every pipeline call now declares one: `disableTools: true` for pure text/structured output, `tools: ['Read']` for the two image calls. The server-start health call (`isClaudeAvailable`) passes `disableTools: true` as well. **MCP servers are gated separately:** `settingSources: []` does not stop the SDK loading the user's `~/.claude.json` MCP servers (the claude.ai connectors — a `tools: []` call still reported 103 `mcp__` tools, Gmail included, at `init`), so `client.js` always passes `mcpServers: {}` + `strictMcpConfig: true` (pinned by `lib/__tests__/sdk-mcp-isolation.test.js`). The tool names `init` reports on a pipeline call must be exactly the tools the call declared, plus `StructuredOutput` when the call has a schema: CLI 2.1.282 counts its own structured-output tool (at the 2026-09-25 gate an Opus call with `disableTools` and a schema reported `StructuredOutput` alone, a Haiku image call `Read` and `StructuredOutput`), which the 2026-09-19 probes on the old CLI did not. Any other tool, or a missing one, fails the isolation probe by name (`scripts/lib/probe-verdicts.js#isolationVerdict`). **Auto-memory is gated the same way:** the subprocess loads the operator's `~/.claude/projects/<cwd>/memory/` regardless of `settingSources` (a probe showed the model reading MEMORY.md's 33 entries), so `client.js` passes `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` through `options.env`; `init.memory_paths` must be absent (`lib/__tests__/sdk-memory-isolation.test.js`). Both are checked live by `scripts/probe-sdk-isolation.js`.

**Model Call Limits (idle timeout + cost ceiling):** SDK calls use a **15-min IDLE/stall timeout**, not a total-duration cap — the timer is re-armed on every streamed message (including the token-level `includePartialMessages` deltas emitted as `llm_delta`), so a legitimately long call (big prompt + extended thinking) survives as long as it keeps producing; only a genuine stall (no streamed activity for 15 min) aborts. A stall throws `SDK timeout after … idle … with no streamed activity`, which `isSdkTimeoutError` recognizes and `isTransientError` (`lib/llm/retry.js`) classifies **transient** (the node-level `retryPolicy` consumes this to auto-retry transient SDK failures). A runaway call is bounded separately by a **per-call `maxBudgetUsd` ceiling** (`MODEL_BUDGETS` in `lib/llm/client.js`: opus $100, sonnet $50, haiku $10). The pipeline runs on the director's subscription, so the figure is not a cost: the SDK derives it from token volume at list prices, and it exists only to stop a stuck loop before it burns the rate limit unattended. An overrun throws a labeled **non-transient** `error_max_budget_usd` that is never auto-retried (the budget is per-CALL, so N node-retries can cost up to N× the ceiling). Steady-state latency is still captured per-call via `duration_api_ms` on the `llm_complete` event (`lib/observability/progress-bridge.js`).

**Effort and thinking (operator gate 2026-09-19; Opus 5.5 since 2026-09-25):** `EFFORT_LEVELS` sets `xhigh` for opus and sonnet, sent explicitly on every call (Opus 5.5 defaults to `medium` when none is sent). The levels did not move with the Opus 5.5 pin; the 2.0 gate records every call's duration next to session 092026's first. On Opus 4.8, `xhigh` was a cliff for extraction-shaped prompts: the director-notes enrichment ended its first turn after thinking alone (~320s, no output), the SDK's structured-output enforcement re-requested, and the call cycled for 20 minutes without completing while re-arming the idle timer (it looked like a stall). `lib/director-enricher.js` therefore passes `effort: 'medium'` (165s; `high` 375s; both complete). The client also sets `thinking: { type: 'adaptive', display: 'summarized' }` for opus/sonnet — the default display on Opus 4.8 / Opus 5.5 / Sonnet 5 is "omitted", which streams thinking as EMPTY blocks, so a long think is a silent stream and the console's THINKING stage shows nothing. Opus 5.5 cannot run with thinking off (`disabled` and `budget_tokens` are both a 400), so on Opus the summarized text is also what keeps the idle timer fed. Arc analysis (286s) and outline/article generation completed at xhigh in the same run; if one of them ever shows the empty-thinking → `status: requesting` cycle, lower its effort per call.

**No model fallback:** the pipeline's calls are always served by their pinned model, never a substitute (integrator ruling, 2026-09-25). `client.js` sets `CLAUDE_CODE_NO_MODEL_FALLBACK=1` in `options.env` (pinned by `lib/__tests__/sdk-memory-isolation.test.js`, which holds the env to `process.env` plus exactly the three switches). In CLI 2.1.282 this is "the no-fallback guarantee": it turns the refusal fallback off (that lane's gate reads both this and `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK`), builds the availability fallback chain as the primary model alone, blocks model substitution, and makes a compaction that would need another model an error instead of a swap. An overload the CLI can then route nowhere ends the call as an `is_error` result whose assistant error is `server_error` ("API Error: Repeated 529 Overloaded errors…"). `isTransientError` treats the assistant errors `server_error` and `overloaded` as transient, as the CLI's own classifier does, so the node retry policy retries the call on the same model (`retry.test.js`, `client-contract.test.js`). A numeric status decides first: every 5xx is transient (a gateway's 502 or 504 too), 429 is the one transient 4xx, and every other explicit 4xx is permanent, whatever the assistant error.

**A model that wrote part of the answer and is not the pinned one fails the call** (integrator ruling, 2026-09-25; corrected 2026-09-26). The models that wrote the answer are the ones named on the call's own assistant frames (`message.model` on frames with no `parent_tool_use_id`; `answerModels` in `client.js`). When any of them fails `servedModelMatches` against the model the call resolved to, the wrapper throws `SdkModelSubstitutionError` (`lib/llm/model-substitution.js`; "SDK model substitution: requested claude-opus-5-5, served by claude-opus-4-8 - <label>; the result is not used", `sdkSubtype: 'model_substitution'`, with `requestedModel`, `servedModels` (the answer's models) and `substituteModels`). It emits one `llm_error` carrying both lists, `servedModels` (the result's modelUsage) and `answerModels`; a schema failure the result also has rides along as `cause`, with its `schemaErrors` on the `llm_error`. `isTransientError` classifies it permanent, through `.cause` and the message marker. **The result's modelUsage is recorded, not judged:** it also lists the CLI's own helper requests. On 2026-09-26 (session 092626) a Sonnet session-report parse listed `claude-haiku-4-5` beside `claude-sonnet-5` there while every frame of its answer was Sonnet's; the first version of this rule judged modelUsage and threw the correct answer away. A call with no frame naming a model has nothing to judge and returns. A subagent's frames (a `parent_tool_use_id`) are not the call's answer; pipeline calls run none. A substitute after a refusal signal is a declined request instead (next paragraph). The isolation probe and `check-model-freshness.js` judge `answerModels` the same way.

**Declined requests (refusals):** since 0.3.162 a declined request ends with `stop_reason: "refusal"` and `stop_details: {category, explanation}`. The category is `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms` or null (the installed `@anthropic-ai/sdk` 0.128.0 types; the CLI treats it as an open string). `lib/llm/refusal.js` reads every place the 0.3.282 types allow: the result's `stop_reason`, the assistant frame's `message.stop_reason`/`stop_details`, a `message_delta` stream event, and the CLI's `system/model_refusal_no_fallback` notice. No live refusal has been captured through this SDK, so each source is optional and pinned by mock (`client-contract.test.js`). The wrapper throws `SdkRefusalError` ("SDK refusal (category: bio): claude-opus-5-5 declined the request - <label>", `sdkSubtype: 'refusal'`) before any result branch, and emits one `llm_error` carrying `refusal` (and `schemaErrors`: the extraction failure's when the refusal names one, else null). `isTransientError` checks a refusal FIRST, through `.cause` and the message marker, so it is never retried. The four nodes that re-wrap SDK errors (arc analysis, character data, the whiteboard, photos) keep the original as `cause`. The paths that swallow errors into state keep the message: the evaluators (`evaluationHistory._error`, `errors`), `reviseArcs` (which never takes a refusal for its free timeout retry) and the enricher (`_enrichmentFallback.reason`). **A declined request is never answered by another model** (integrator ruling, 2026-09-25). The bundled CLI has refusal fallback routes of its own, keyed on the requested model and independent of the `fallbackModel` option: for `claude-opus-5-5` it retries `bio` and `frontier_llm` on `claude-opus-5` and `cyber` on `claude-opus-4-8`. `client.js` turns them off with `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` in `options.env`, and `CLAUDE_CODE_NO_MODEL_FALLBACK=1` turns them off as well (both pinned by `lib/__tests__/sdk-memory-isolation.test.js`). A main-thread fallback that runs anyway (a `system/model_refusal_fallback` whose `scope` is not `local`, or an assistant frame that `supersedes` the refused frames) throws `SdkRefusalError` at once, naming the category and the fallback model, and the `llm_error` carries it as `refusalFallback`. Any other failure after a refusal signal (a schema failure, an iterator throw, no result, an idle abort) is thrown as `SdkRefusalError` with the original failure as `cause`, so a stall after a refusal is never retried as a transient `SDK timeout`. A refusal signal followed by a clean, schema-valid finish on another stop reason returns the result, and `llm_complete` carries the signal as `refusalSignal` (in `diagnosticsOf`, so the call log has it). The exception: when the result's `modelUsage` names a model that is not the one the call resolved to under `servedModelMatches` (`lib/llm/sdk-fields.js`, shared with the probe scripts; a `[1m]` or dated suffix is the same model), another model finished the declined request, and the wrapper throws `SdkRefusalError` naming that model (a schema failure, if there is one, rides along as its `cause`). A result with no `modelUsage` has no other model to name and returns. Without a refusal signal, the same `modelUsage` is a model substitution (previous paragraph).

**What the 2.0 gate reads:** the `init` forward carries `effort` and `memoryPaths` as well as `model`/`betas`/`toolCount`/`toolNames`/`permissionMode` (the isolation probe prints the names on every init line, with the expected set above them). Neither is typed for `query()` calls in 0.3.282 (`memory_paths` is absent from the public `SDKSystemMessage`; `effort` is documented for Remote Control frames), so both are forwarded raw and absent is normal. A loaded memory path prints as an error line. Every result envelope carries `servedModels`, read from the result's `modelUsage` (`canonicalModel` preferred) because the call log otherwise records only the alias and 0.3.174 added silent model fallbacks. A served model other than the pinned one fails the call (above), so the `answerModels` of a completed call name only the pinned model; its `servedModels` (the result's modelUsage) can also name a CLI helper model such as `claude-haiku-4-5`, or be null or empty (a zero-turn result carries an empty `modelUsage`). It reaches the per-call record, both SSE envelopes, `index.jsonl` and the console completion line (`served=`). One builder (`llm-call-log.js#diagnosticsOf`) makes the record's and both SSE envelopes' diagnostics. Open at the gate: whether the `context-1m-2025-08-07` beta, still sent to every non-Haiku call, is accepted, ignored or rejected on Opus 5.5 (1M native).

The arc writer writes **one weave** in one call (phase 4, brief 4.4; spec 4.1, 4.2; `lib/weave.js` holds its shape and the rules its readers share):
- the story in one to three sentences, the question it carries, and a working headline;
- "from your notes" (`fromYourNotes`): the director's own words the story rests on, copied exactly, present only when the notes end with the director's read. When the notes end without one, the story is the writer's proposal from the record;
- the threads, `{id, claim, role, receipt, reason?, verdict?}`: the role is main thread, grounds it, complicates it, mirrors it, carries it forward, or left out with a one-line reason (`WEAVE_ROLES`); the receipt is the id of the thread's strongest document in the record, or `ledger`; `verdict: true` marks the thread that carries the room's verdict;
- the connections, `{id, kind, joins, detail}`, each a person, a moment, a document or a line (`CONNECTION_KINDS`), joining two threads;
- the convergence, an optional `strongerMainThread` (`{thread, reason}`), and the questions (C15; see **The writers' questions**).

About 400 words: the checks bound the writer's words at 500 (`WEAVE_WORD_BOUND`). The writer reads what it read before: the record and the morning timeline, the director's notes and corrections, the accusation word for word, the whiteboard reading, the roster with pronouns and the rule set. The lens work (C16) stays in its reasoning. One schema, `WEAVE_SCHEMA` (`subagents.js`), serves the writer and its rework; it lets a thread omit its receipt or its reason, so a thread the director adds stays valid, and the checks require both on the writer's threads. The weave lives in its own channel, `weave`; the arc analysis no longer writes `narrativeArcs` or `_arcAnalysisCache` (they went with their last readers in 4.6), and the dead `specialistAnalyses` went. `disableTools: true` (pure structured output).

**The rule set in the arc calls** (phase 3, briefs 3.3 and 3.10; phase 4, brief 4.4). The arc writer and its rework read `loadRuleSet('arc')`: the world and the truth rules after the mode block in the system prompt (`weaveSystemPrompt`), the craft files last in the user prompt, before `<DIRECTOR_GUIDANCE>`. The story meeting's fact check reads the world, the truth rules and the mode block alone (`RULE_SET_CALLS['judge-arc']` is core only); the phase 4 spec's section 11 says which files each call reads. The writer's user prompt (`buildWeaveSections`) opens on the weave's OUTPUT FORMAT, then SECTION 1, what the room concluded (the accusation, the whiteboard reading, the director's notes and corrections under `ARC_NOTES_LABEL`, their sentences about Blake and the Valet from the stored `blake-proximity` tension through `directorTensionSentences`, the investigation focus, the session roster, the character categories, the roster with pronouns and the character context); SECTION 2, the whole record view with its morning timeline, then the receipts a thread may give (the record's document ids, by the view's id rule, and `ledger`); SECTION 3, the weave's task (`WEAVE_TASK`); SECTION 4, the craft files. **Each rule is stated once** (spec section 8): the task points at C1 (`<craft-story>`) for the story and the question, C16 for the threads, the connections and the convergence, and C15 (`<craft-questions>`) for the questions, and restates none of them; the story and each claim are asked for in plain sentences in the third person, in their OUTPUT FORMAT placeholders. The every-player lines went from the system prompt and the ROSTER PCs line. The interweaving call, `INTERWEAVING_PRINCIPLES` and `RULE_SET_CALLS['interweaving']` went (spec section 10): the weave names its connections itself. The notes label, `ARC_NOTES_LABEL`, reads "the record for the room, under T1" and adds only that backstory in the notes is what Nova knows but the record cannot back, T1's third point (3.10); `arc-specialist-nodes.js` exports it, so the fact check prints the arc writer's own label. **The roster with pronouns** (3.10; T9): the arc writer and the outline writer print the roster section the article writer and the judges print (`rosterWithPronounsSection`, built without the character data: the roster lines with their pronouns and the NPCs' canon lines), so each player's pronoun reaches them once. `arc-specialist-prompts.test.js` holds each C16 term to as many occurrences as the rule files carry. The arc stage's detective branches went (R1): `/start` refuses the detective theme with a message, and its skill folder, templates and theme config stay.

**Architecture Evolution**: See `lib/workflow/nodes/arc-specialist-nodes.js` header for history (8.12 parallel → 8.15 single → 8.28 split → phase 4, one weave in one call).

**Three-Category Character Model** (Commit 4193772):
- **Roster PCs**: The players. Since phase 4 the map places every one (spec 4.5); the arc stage checks no coverage
- **NPCs**: Valid but don't count (Marcus, Nova, Blake/Valet)
- **Non-Roster PCs**: Evidence-based mentions only (valid game characters not in session)
- **Canonical Name Preservation**: Accepts both "Sarah" and "Sarah Blackwood" as valid

For details, see `PIPELINE_DEEP_DIVE.md#three-category-character-model`.

**Arc Validation Routing (Commit 8.27; the weave checks since phase 4, brief 4.4):** before the fact check, `validateArcStructure` runs the **weave checks** in code (`lib/weave.js` `checkWeave`, on the writer's text alone since brief 4.5: see **The story meeting**), each failure one line that names the defect and its fix: each writer's thread has a receipt, and every receipt names a document in the record (`buildValidEvidenceIds`) or the ledger; the room's verdict is one of the threads (`verdict: true`, not left out); every live connection joins two threads the weave holds; each left-out thread has its reason; every thread, connection and question has an id of its own, and a stronger main thread names a thread the weave holds (brief 4.5, ruling 3); "from your notes" is word for word in the director's notes or corrections (`lib/grounding.js` `isVerbatimIn`); the writer's words come to no more than `WEAVE_WORD_BOUND`. The checks write `_arcValidation` and `validationResults` on every outcome, stamped for the weave they checked (`weaveKey`; source `weave-checks`). A failed check sends a weave the fact check has not judged back for one rework in the round (`routeArcValidation`), which reads the lines under their own label, `WEAVE CHECK FAILURES` (`CODE_CHECKS` in `node-helpers.js`), in place of ISSUES TO ADDRESS; a check still failing after it goes on to the fact check and is kept for the meeting to show. The fact check (`evaluateArcs`) marks the weave it judged (`_factCheck: {at, ready, fixes}`); a breach gets one automatic fix through `reviseArcs`, which keeps the mark and counts the fix, the checks run again on the fix, and the stop opens with no second judge call (`routeArcEvaluation` reads the mark). A marked weave is never judged again, so a replay from START pays for nothing at the arc stage; a director's round writes its weave without the mark, so the checks and the fact check run again. Every automatic pass keeps what its findings do not name word for word (R23), through `buildRevisionContext` (`outputName: 'weave'`). A rework that times out keeps the weave and records the timeout in `_arcReworkTimeout` (`{consecutive, attempt, at}`, with the `round` and its `note` for a director's round), giving back only the count its pass raised (brief 4.5, ruling 5): an automatic pass is retried free, and a director's round does not run, so the meeting reopens with the director's version; the third timeout in a row is an error.

**Three-Layer Evidence Model:**
| Layer | Contains | Journalist Can |
|-------|----------|----------------|
| **EXPOSED** | Full memory content, paper evidence | Quote, describe, draw conclusions |
| **BURIED** | Transaction data ONLY (amounts, accounts) | Report patterns, NOT content |
| **DIRECTOR** | The director's notes; the whiteboard | Report the room's events and lines from the notes; read the whiteboard as context, never cite it |

What Nova can do with each layer is the rule set's: `world.md` ("What each memory became") and `truth-rules.md` (T1, T3 to T6, T13). `PIPELINE_DEEP_DIVE.md#three-layer-evidence-model` points at each layer's rules.

### Prompt Architecture

**The rule set (phase 3, tasks 3.1 and 3.8).** The journalist's rules are model-facing Markdown files in `.claude/skills/journalist-report/references/rules/`, written from the rule-set spec (`docs/superpowers/specs/2026-09-30-rule-set.md`): `world.md` (the article's purpose, the world, how a memory moves through the game), `truth-rules.md` (T1 to T15: the floor), eight `craft-*.md` files (C1 to C19: the engine, the craft rebuilt around the article's form in spec round 7) and the two mode files. The craft files group the items by the writer's job: `craft-story` (C1, C3, C16), `craft-form` (C2, C5, C6, C17, C18, C19, C14), `craft-material` (C8, C7, C10, C11), `craft-voice` (C12), `craft-judgement` (C13), `craft-telling` (C4), `craft-cards` (C9) and `craft-questions` (C15); task 3.8 regrouped the craft into them and deleted five of the ten files it had been split into. Each call reads the craft files `RULE_SET_CALLS` gives it, every list in one order (the phase 4 spec's section 11, which was the rule-set spec's section 8): the arc writer, which writes the weave, story, form, material, judgement and questions; the map writer every file but voice and questions (`OUTLINE_CRAFT`; phase 4, brief 4.6); the article writer all eight; the story meeting's fact check (`judge-arc`) and the article judge (`judge-article`, brief 4.7a) none, the world and the truth rules alone. An item is its heading (`## C16. …`, `## T8, remote: …`), stated once across the files (T8 once in the truth rules and once in each mode file), and a body may point at another item ("(T1)", "as T5 sets out"). `lib/__tests__/rule-set.test.js` lints the files: each item once, every pointer naming an item the set states, no em-dash, no gendered Nova, nothing on `lib/__tests__/fixtures/removed-phrases.js`, no old example accounts or sums. `lib/rule-set.js` is synchronous (readFileSync, cached for the process, so an edited rule file reaches the prompts on the next server start): `loadRuleSet(call)` for `arc`, `outline`, `article`, `judge-arc` or `judge-article` returns `{core, craft}`, the world then the truth rules and the call's craft files (`RULE_SET_CALLS`), each wrapped in one tag named after its file; a reworker passes its writer's call; a missing or empty file throws, named. `loadModeBlock(mode)` returns the mode file in one tag named after it (`<mode-remote>`), as `loadRuleSet` wraps each file, so the system prompt's text after the block is not read as part of its "## T8" section. Tests pass `{root}`, and the pinned renders point the default root at the one-line stubs in `lib/__tests__/fixtures/rules/` (`setDefaultRulesRoot`), so a rule-text edit never moves a pin. Journalist only: a detective caller keeps its own text. Since 3.2 the outline and article writers and their reworkers read it, placed by the integrator's ruling: `core` (the world, the truth rules) in the system prompt right after the mode block, and `craft` last in the user prompt, after the data and before `<DIRECTOR_GUIDANCE>`. The inline text the rule set states or contradicted went with it (the old financial block's "Blake now possesses all buried memories", the agency rule that kept Blake out of the room, the fixed section table, every arc in every section, pull quotes, the voice self-check, and the JSON shape restated in the outline prompt's own words, M27), and the schema descriptions are shape only. The map writer embeds the map's schema for its theme (`mapSchemaFor`, `lib/map.js`) as `<SCHEMA>`, before the craft files, as the article writer embeds the content-bundle schema (fix 3.2b); the detective has no map (R1).


**Data Wiring (Commit 6ffeef8):**
- Memory tokens use `fullDescription` field (rich second-person narrative)
- Fallback chain: `fullDescription` → `content` → `description` → `summary`
- `extractFullContent()` helper ensures full quotable content (not summaries)
- Fixed in 3 locations: preprocessor, token routing, arc evidence packages (the packages went in phase 4, brief 4.6; R5)

**The record view (phase 2 slice 2.1):** `lib/prompt-renderers/record-view.js` renders the evidence bundle as one `<RECORD>` section. Each exposed document is `<document id kind name owner layer="exposed">` with its full text as the body; the buried memories follow only as sales on the morning timeline, `<morning-timeline>` (phase 3, brief 3.5, in place of the old `<buried-transactions>`): `buildMorningTimeline(bundle, sessionConfig)` merges the bundle's sales (account, amount and time and nothing else; a memory no one sold has no line), the evidence log (`sessionConfig.exposures`, only for memories the bundle holds as exposed: the document id and the name on the turn-in) and the classified adjustments (`sessionConfig.adjustments`: the first-burial bonus, transfers) in time order, every logged time on the session clock (`lib/prompt-renderers/session-clock.js`: the parse stamps `sessionConfig.sessionClock`, decided on the first exposure or sale, never a setup row; at 5 PM or later every time shows AM for PM; a thread from before phase 3 decides from what it holds). Events go in order from the first of them, the adjustments included (`firstEventTime`), so a bonus logged before the first sale opens the timeline; the clock decision still reads only exposures and sales. Events in the same minute sit under that minute, the ledger's before the evidence log's, in no claimed order; each event's `minute` is its minute on the session clock in one format (`printClockMinute`, "07:50 AM"), which the group breaks on and its heading prints, so a minute the session report writes two ways ("07:50 PM", "07:51PM") is still one group. `renderRecordView(bundle, {buried, sessionConfig})`: the callers that print the timeline pass the session config (`prompt-builder.js` from `this.sessionConfig`, the weave writer, the story meeting's fact check, and the outline and article judges). The id is `id`, else `tokenId`, else `notionId`, the order the fact check's source map keys on, so a rescued item (no `id`) is named by its Notion id, and `buildValidEvidenceIds` accepts a paper `notionId` for that reason. The owner is the record's own `owners[]`, never the bundle's `owner` (the preprocessor's guess); the text is the record's `fullDescription` or `description`, never a summary; an attribute with no value is left out. Only character extraction takes the documents alone (`renderRecordView(bundle, {buried:false})`); which sale rows the timeline prints is one rule, `isBuriedTransactionRow`, exported by the view. The arc writer (the weave writer since phase 4) and the story meeting's fact check, and the outline and article writers (both themes), take the whole view once, in the data part, before the rules. `buildOutlinePrompt` and `buildArticlePrompt` read it from `options.evidenceBundle` (`scripts/render-prompts.js` and the content-bundle probe pass it too). The outline's five-per-arc cap is gone, and since phase 4 (brief 4.6; R5) so are the per-arc lists (the outline's `<arc-evidence>`/`<evidence-context>` and the article's ARC EVIDENCE PACKAGES) that named each arc's documents and kept code-cut excerpts: the record is the writers' one evidence section, and the fact check's card sources come from it alone (`buildSourceMap(evidenceBundle)`). An instruction that sends a writer to a document's text uses `DOCUMENT_POINTER` ("the document with that id in <RECORD>"). Upstream, the preprocessor sends an exposed memory's `fullDescription` to Haiku, and never sends a buried memory at all: its item is made in code from the sale (`buriedMemoryItem`: the input's id, the account, amount and time, and a summary of the sale), because a memory's id and name name its owner (final fix wave). Every item a batched model call returns is keyed to its input item, never to the id the model echoed (`pairRepliesWithBatch`, exported by the preprocessor: by id, else by position when the model kept the batch's order, else by elimination, else the reply is rejected). On 092026 curation's Sonnet paper scoring (`scorePaperEvidence`) echoed a rescued email's Notion id with `583f-` missing, and its find-by-echoed-id merge kept the model's id and dropped `rawData` and `fullContent`, so every `<RECORD>` printed the email with no text. That merge now uses the rule and takes only the scoring fields from a reply (`scoredPaperItem`). An item it cannot place is kept, not dropped, as not scored (`notScored`, `excludeReason: 'scoringError'`, rescuable), so the evidence stop shows it as "never evaluated". The rescue cache is keyed on the input's own name. The preprocessor's merge uses the same rule as hardening (an input it cannot place keeps a fallback summary), so an input's id, record and disposition always survive, and its items keep their input order. And `extractCharacterData` reads `selectedPaperEvidence` and every exposed memory, in full, through the view. Machine-made material carries a label from `lib/prompt-renderers/derived-labels.js` saying who made it and that the record decides where they differ: the character context (arc writer, article roster section), the narrative tensions (arc writer, article; since the 3.6 fix batch their label says the gathered sentences are the director's own and record, and only the gathering is code's), and the director-notes indexes `<QUOTE_BANK>` and `<TRANSACTION_LINKS>` wherever the notes are rendered. The enricher links an observation to a buried sale by an opaque row key (`tx-1`, …) that `resolveTransactionLinks` maps back to the row, so neither its prompt nor the stored links carry a memory id, and `<TRANSACTION_LINKS>` prints each linked sale through the record view's transaction formatter (`buriedTransactionFields`: account, amount and time, the time on the session clock from the `sessionConfig` the block is given). Its three callers (the outline and article writers' `_buildInvestigationObservations`, the arc writer, the judges' `renderJudgeDirectorNotes`) pass the session config through `withSessionClock(sessionConfig, evidenceBundle)`, so a thread with no stamped clock and no exposures (092026's shape) prints its links on the clock its timeline decides from the bundle's sales. `lib/__tests__/buried-memory-sentinel.test.js` plants one buried memory everywhere one can enter and checks every prompt for its id, owner and text.

### Modifying Checkpoint Components

Each checkpoint component follows the same pattern:
1. Registers on `window.Console.checkpoints`
2. Receives `{ data, sessionId, theme, onApprove, onReject, onRollback, dispatch, revisionCache, pendingEdits }` props
3. Renders checkpoint-specific UI from `data`
4. Calls `onApprove(payload)` / `onReject(payload)` with the checkpoint-specific payload, or `onRollback(checkpointType)` to open the rollback modal

**Conventions:** `const` not `var`, direct destructured imports (no aliasing), `safeStringify` instead of `JSON.stringify`, CSS utility classes over inline styles, aria-labels on interactive elements, functional state updaters for Set manipulation, `useEffect` reset on data change.

`Article.js` validates the bundle on the desk through ONE local `gateEdits` helper that both the approve and the send-back call (the send-back passes `verb: 'send'`, so its message reads "Cannot send …"); a new path that sends edits goes through it too. Its gate is the desk's (task 4.3): it runs on every approve and every send-back, edited or not, on the bundle on the desk, with the desk's checks (`articleDeskLogic.deskProblems`) beside `validateBundleShape`, and its JSON path routes through it too. The map (`Outline.js`, task 4.9) has one send path, `send(action)`, which Approve and Send back both take: it holds the map on screen to `mapProblems`, the gate's decisions, then builds `mapPayload`; the map has no JSON editor. `__tests__/unit/console-edit-gates.test.js` pins both.

**`onRollback` is the only way a checkpoint may open the rollback modal.** It is the same `setRollbackTarget` callback the stepper uses, so Confirm goes through the existing streaming rollback. A component must NOT dispatch its own rollback action — ArcSelection's zero-arc dead end dispatched `SHOW_ROLLBACK`, which no reducer handles, so the only offered recovery logged `[state] Unknown action` and did nothing.

- **The moves** (`outline-edit-logic.js`): a beat moved to another section, a photo beside it going with it; struck into left out, whole, its photos staying in their section by themselves; brought back from left out into a section the director picks; added with its players under the next free `b<n>`, or taken out again at the look that added it, its photos staying in their section by themselves, as a struck beat's do (4.6c), through one helper both moves call (`freePhotosBeside`; 4.6d); a photo moved to another section, by itself, or to the top, where the top photo it replaces takes its place, so every photo stays placed once (no photo is struck on the map). A line under an id the writer repeated, or a photo the writer placed twice, has its controls off. The page and the validator take a beat's id and card, where each beat and photo sits and what the map repeats from `outline-edit-logic.js`'s readers, so the lines the page locks sit under exactly the repeats `mapRepeats` finds in the map shown, which the validator takes as the writer's.
- **Everyone and the counts** are built from the map as edited through `mapTally` (`mapTallyOf`), on the inputs the payload carries (task 4.6c), which sends no count of its own (4.6d): the roster with the canon's full names (`roster`) and the photos kept for the article (`keptPhotos`). So "In no beat" lists the players in roster order after any edit, and a roster name counts whatever it is (`mapTally`'s set of players seen). The cards line says when they leave 3 to 5 (`MAP_CARDS`, held equal to `lib/map.js`'s).
- **The payloads are 4.6's** (`mapPayload(action, map, note)`): `{outline: 'approve' | 'send-back', map, note?}`, with the map on screen, edited or not; a send-back needs its note. Before either, `mapProblems` holds the map to the gate's decisions: `validateOutlineShape(map, theme, mapSlots, shown)`, with the map shown read as `mapView` reads it (`isMapValue`, so a value that is no map is no map shown; 4.6c) and as the gate reads it (4.6d), is the director-side schema, then `lib/map.js` `directorMapProblems`'s rule for a repeat (a beat id the director's changes repeat; one the map shown holds is the writer's), and 4.6b's (a photo the director's changes place more than once). `console/__tests__/checkpoint-view-logic-map.test.js` holds the decisions equal on one corpus, 4.6b's photo repeat included, and on a shown value that is no map (4.6d). `app.js`'s fallback approve is `mapPayload('approve', …)` too.
- **Pending edits.** Every change goes to the map's `pendingEdits` slot as `{version, map}` with the note beside it (`mapPendingSlot`), under the meeting's version rule (`stopVersion`: the map and both round counts). `CHECKPOINT_RECEIVED` keeps that slot and its note only while the stop shows the same version (`pendingEditsAfterCheckpoint`).
- **Thumbnails** load from `/sessionphotos/<id>/<file>` (`mapPhotoUrl`); a photo the console cannot serve shows its filename alone.

### Input-review reject flow (re-parse, not rollback)

`InputReview` is not approve-only. Approve sends `{ inputReview: true }`; Reject with Corrections sends `{ inputReview: false, inputFeedback: '<prose>' }`. `buildResumePayload` turns that into `{approved: false, feedback}`, and `checkpointInputReview` stores it as `_inputCorrections`, appends it to `inputReviewCorrections` (every correction of the session, in order), nulls `sessionConfig`/`directorNotes`/`playerFocus` so `parseRawInput` re-runs, and routes the graph back — `parseRawInput` appends every kept correction to every parse prompt, the whiteboard parse included, and the writers read them after the director's notes (see "The director's words as record"). A mis-parsed accusation, exposure, sale or quote is therefore fixed with a note, not with a rollback and a full re-collection. The roster, its pronouns, the reporting mode and the reporter's name are not: code stamps them from where the director entered them (the roster stop, the start form), no parse returns them, and a note leaves them as they are (phase 3, brief 3.5; spec D15). The parse's correction block says only that the corrections apply to what the parse reads from the source text. There is no `inputEdits` path (the key wrote a state channel nothing declared or read).

### Rolling back a COMPLETE session

A finished thread has no checkpoint (`GET /checkpoint` returns `checkpoint: null`), so neither rollback opener could be reached for it. `SessionStart`'s `'complete'` branch therefore loads the completion instead of resuming (resuming re-runs the whole paid pipeline): `SET_THEME` → `SET_SESSION` → `SESSION_COMPLETE_LOADED`, whose payload comes from `sessionStartLogic.completedResultFrom(checkpointResponse)`. That action sets `completedResult` plus `completedStepper`, and `app.js` renders `PipelineProgress` with `completedCheckpoints: CHECKPOINT_ORDER` above `CompletionView`, so every step is a rollback target and the existing `RollbackPanel` flow applies. Nothing is POSTed until Confirm. `CHECKPOINT_RECEIVED` clears `completedResult`/`completedStepper`, because App renders the completion branch BEFORE the checkpoint branch and a stale completion would hide the checkpoint the rollback just produced.

### Threads from before the story meeting (task 4.11; R2)

A thread started before phase 4 holds no weave, and its outline and article are in the old shapes. Once the old stages have taken it past the arc writer, the new stages would replay it on those shapes and spend paid calls the director never asked for. `lib/old-thread.js` flags it (`oldThreadOf(values, pausedAt)`, by the weave, ruling 1) when it holds no weave and is paused at the meeting's stop or a later one in `CHECKPOINT_ORDER` (`photos`, `character-ids`, the map or the article), is complete, or holds what only a stage past the arc writer writes (`PAST_THE_ARC_WRITER`): an evaluation, a rework's count, an outline or an article. The last covers a thread at no stop, one that stopped on an error or whose run was killed (fix rounds 1 and 2), wherever the old stages left it: the old arc stage evaluated its arcs before the arc stop opened, and every rework counted itself before it ran, so a thread that stopped in the photo branch, the old outline writer or the old outline rework (which emptied the outline first, and whose catch left it empty) is flagged as well as one that holds an outline or an article. Resumed, such a thread reached a fresh meeting and then ran the new stages on the old stages' work: the map's stop opened on the old outline, or on a fresh map with the old outline stage's note, edits, trace and counts, and the old arc stage's counts spent the fresh weave's check rework. A thread of the new code holds none of them without a weave: the arc writer writes the weave or throws, every evaluation and rework after it runs on the weave, the fresh start, every rollback that clears the weave and an old thread's rollback to the meeting clear them all, and the stub a rollback past the meeting writes into the evaluations (`source: 'rollback'`) is no evaluation, which `lib/__tests__/old-thread.test.js` holds. A thread with no weave that holds none of them is resumed, and its resume writes the weave: a new thread before its weave, an old one rolled back to the meeting before its weave is written, or an old one that stopped in its arc writer, before any check rework or evaluation (one that stopped in the old arc check's rework holds that rework's count, so it is flagged).

`server.js` refuses an old thread: `/approve`, `/resume` (`force` included) and every `/rollback` past the meeting answer 409 `{sessionId, error, oldThread}`, the error "This session was started before the story meeting. Roll back to the story meeting to continue." A rollback to the meeting or a point before it proceeds, and writes the weave fresh with its fact check; the meeting's point also starts over the arc counters the old arc stage left (`oldThreadRollbackState`). `GET /checkpoint` carries the flag as `oldThread`, `{message, rollbackTo: 'arc-selection', rollbackPoints}` (null for every other thread), and sends an old thread's stop as `{type, oldThread}` alone, building no stop's payload from the old shapes. The console reads the flag through `oldThreadView` (`checkpoint-view-logic.js`): `app.js` shows the message and a "Roll back to the story meeting" button in place of the stop, whose component never renders, above a loaded completion (`completedResultFrom` carries the flag), and, for a thread at no stop, in place of the resume: the Session screen classifies it `old-thread` (`classifyCheckpointResponse`), loads the flag into the state (`OLD_THREAD_LOADED`, cleared by the rollback's checkpoint) and posts nothing. Each way the stepper opens only `rollbackPoints`. A refused request's 409 shows its message on the banner and is never taken for the session lock's. Tests: `lib/__tests__/old-thread.test.js`, `__tests__/integration/old-thread-guard.test.js` (each stop and request, and threads at no stop), `__tests__/integration/old-thread-graph.test.js` (the real graph: refused at `photos`, after a failed publish and after an error in the old outline rework, each then rolled back to the meeting, and a new thread whose weave writer failed, resumed) and `console/__tests__/checkpoint-view-logic-old-thread.test.js`.

### The map's and the desk's editors (`Outline.js`, `Article.js` + `outline-edit-logic.js`)

The map's editors (`Outline.js`, task 4.9) are **thin wrappers**: each seeds `useState` from `EditLogic.init*(line)`, composes the module-scope `TextField` and `actionsRow`, and on save merges `EditLogic.build*(form, …)` into the map with `EditLogic.merge*`, which writes the line into the map as it is now. `EditLogic` = `window.Console.outlineEditLogic` (aliased at module scope in both `Outline.js` and `Article.js`).

- **All build/merge/validate logic and the map's moves are PURE and live in `outline-edit-logic.js`, not in the React components.** A build starts from a copy of its line and keeps what the director typed as typed; a field left blank leaves no key, so a beat the director added keeps the shape they gave it.
- **Edited maps are held to the gate's decisions before they are sent** (the B7 gate): client-side through `ViewLogic.mapProblems` (`EditLogic.validateOutlineShape(map, theme, slots, shown)`, the map's gate `validateMapShape`: the director-side schema, then the gate's rule for a repeat; dependency-free, blocks both buttons and renders `.validation-error`), and server-side in `buildResumePayload` (`lib/map.js` `mapResume`, against the director-side map schema and `directorMapProblems`; brief 4.6). Distinct from the generation-time `validateOutlineStructure` removed in 8.23: this gates HUMAN edits.
- **The article stop is the director's desk** (phase 4, task 4.3; spec 2026-10-02 section 6.3). `console/article-desk-logic.js` (`window.Console.articleDeskLogic`, dual-export, loaded before `Article.js`) holds every decision behind it, pure and node-tested:
  - the block operations, each returning a new bundle: `insertBlock` (a paragraph or a quote; photos and cards come from the record), `moveBlock`, `moveToSection` and `stepTarget` (within a section or across sections), `deleteBlock`, and the edits in place, a section's heading included (`setSectionHeading`; the byline edit keeps the guest reporter's credit);
  - the checks: `deskProblems`, which is `emptyBlocks` (whitespace-only text included) and `headlineProblems` against `HEADLINE_LIMITS`, the schema's limits, which a test holds equal;
  - the naming rule (task 4.3b): `pairSectionBlocks` pairs a section's blocks across two versions, and `stayingInSection` keeps the longest run that kept its order; every other pair is a block the director moved, a move when unchanged and a cut and an addition when changed; a photo, a card or a reference pairs only with a block of its own name, so two the director swapped are two moves, each with its own caption or text (task 4.5d);
  - `deskChanges(opened, current)`: for each section, the blocks inserted, deleted, moved or edited since the stop opened, named by that rule, with `unchanged`, how many of its first blocks kept their place; the desk's marks anchor on it (`untouchedThrough`);
  - the pieces a mark sits beside (task 4.10): `printedPlaces(bundle)`, the headline, the byline, the hero, each section's heading and block and each sidebar card, with the words each prints (`PRINTED_TEXT_FIELDS`, which a test holds to `lib/hand-edit-diff.js` `PRINTED_BLOCK_FIELDS`), and `paragraphBlockIndex`, a paragraph's block from the fact check's ordinal;
  - what prints: the byline line by the header partial's rule (`bylineLabel`: the title and the guest reporter print only with an author), and the writer's money tracker (`writerTrackerState`, `writerTrackerDisplay`; see the `htmlPreview` row).

  `diffBundle` records a block the director moved as a move, within its section (with `between`, the blocks it follows and precedes) as across sections, so the desk's moves and deletes are standing edits at a send-back. The desk and the diff name moved blocks by one rule: `lib/hand-edit-diff.js` requires the desk module, as `server.js` requires `outline-edit-logic.js`, and its `matchBlocks`, `stayingInSection` and `sectionKey` are the desk's own functions. Approve and Send back send exactly the bundle on the desk, edited or not. The desk shows what prints, field by field: it edits and labels only the fields a journalist template reads (`__tests__/unit/console-desk-prints.test.js` holds the fields it lists to the templates: a photo's and the hero's characters, a sidebar entry's placement, owner and layer, and a tracker row's category and date print nowhere, and the desk neither edits nor labels them), and each editor saves only the fields the director changed (`DeskLogic.changedFields`; the sidebar card's since task 4.3c), so a field the page does not print keeps its value.
- **The desk's marks** (task 4.10; spec 6.2 and 6.3). Nothing sits in front of the article. `checkpoint-view-logic.js` `deskView(data, current)` gives `Article.js`, and the harness, the echo of the settled story above the headline (`deskEcho`); each mark beside its piece (`deskMarks`, read per piece with `deskMarksAt`, keyed by `deskAnchorKey`), shown under it in the piece's row or under its open editor; the marks with no piece (`apart`), one line each beside the approve button, whose count stays the fact check's structural issues (`approveLabel`); and the folds below the article: the marks possibly resolved, the fact check's list, the round's `RevisionDiff`, and the trace through `traceView`. No score, no evaluation bar and no questions panel. A mark is `{key, tone, label, text, where, anchor}`; its tone is `judge` (an escalated evaluation's structural issue), `structural` or `advisory` (a fact-check finding), `concern` (a finding under one of the director's edit ids, or the judge's concern) or `changed` (an entry `changedEditsToShow` keeps). A fact-check mark's text is its finding's `line` (brief 4.10b; `findingLine`): what is wrong in the article at that place, in the director's words, never the message the rework reads; where the line holds `DOCUMENT_SLOT` (a copy of the fact check's, which a test holds equal), the card's document is named by its name and owner through the payload's `evidenceIndex`, as the story meeting names a receipt (`receiptView`), and as "the document it cites" when the stop does not name it. Where it sits:
  - a paragraph finding by its section and ordinal while `untouchedThrough` holds, otherwise by its excerpt in a paragraph, its own section first, and a quote block's by its excerpt in a quote (brief 4.10b: its line names the piece it is about, and a card, a caption or a quote can hold the same words);
  - a headline, kicker or deck finding beside the headline while the field is as the stop opened it or holds the excerpt;
  - a card or a photo by its id or filename (the integrator's ruling 4): beside it, wherever it sits, while it is unchanged, and possibly resolved once the director changed or deleted it; its excerpt decides nothing;
  - the length on the heading of each section it counts;
  - a judge's issue or concern by a passage it quotes, read as the server's guard reads one (`locatingPassages`: split at an elision, three words or more, never a heading; a test holds it to `lib/hand-edit-diff.js` `locateQuotedText` on a corpus of findings, and `quotedPassagesOf` and `groundingText` to `lib/grounding.js`'s);
  - a changed edit beside what the director's text became, its section first.

  A mark whose text only the article as the stop opened it held folds below as possibly resolved, and one with no piece at all is apart. The marks follow the bundle on the desk: each move, edit or delete moves them.
- **Edited ARTICLES have two gates:** client-side, on every approve and send-back, the desk's checks and `EditLogic.validateBundleShape(bundle)` (the inline editors and the JSON editor alike); server-side, the `content-bundle` schema, which stays the last word on shape. `validateBundleShape` is deliberately never STRICTER than `content-bundle.schema.json` — `heading` stays optional, `metadata.generatedAt` is not required — because a false block on a bundle the server would accept is a dead end the director cannot clear. A test pins that direction. The empty-block check is the desk's, apart from it, because it is stricter by design: a blank paragraph passes the schema, and `validateContentBundle` would drop it without a word after the approve.
- **The pencil has two reveal modes** (pinned by `__tests__/unit/console-editable-pencils.test.js`):
  - `article-block--editable` alone → hidden until `:hover` / `:focus-within`, for a full-width host whose own first line reaches the top-right corner (an always-on corner button landed on the article's prose at 19 of 54 rendered blocks).
  - `+ article-block--editable-always` → rendered at low opacity, full opacity on hover/focus. **The map's hosts only** (each line at the host's left and its controls under it, so the corner is free) plus a `padding-right` gutter, which the hosts' own rules keep by setting their padding with the longhands. `Outline.js` routes every host through its `ALWAYS` constant: the headline and deck, the gap note, each section, each beat and the length.

  The **article** desk uses neither: each piece of the article is a `deskRow` whose pencil and block controls (move, delete, insert) sit in `.desk-rail`, a grid column of its own beside it, so every editor is visible and none covers the prose. The old outline's screen emitted neither class at any of its 13 call sites, so its whole editor layer was `display: none` forever. The always-visible rule is a **descendant** selector: a host may hold its button at any depth, and a child selector misses every button that is not a direct child.
- **Reset effect** is keyed on `EditLogic.computeResetKey` (collision-resistant): the map's through its version (`mapVersion`), `Article.js`'s on `(data, revisionCount)`. Do NOT revert to a truncated `safeStringify(...).slice(0, N)` — it collides across revisions and leaks stale edits.

## API Reference

### Session REST API

**Step-by-step Pipeline Control:**
- `/api/session/:id/start` (POST) - Start new session with raw input. **The session ID must be the session date as MMDDYY** (`091826`), optionally with one extra digit for a second session the same day (`0918262`); anything else is a 400 (B1: the emailer builds each player's report link from this id, and `data/<id>/` + `outputs/report-<id>.html` are named after it). `ALLOW_NONSTANDARD_SESSION_ID=true` in the server's env opts out for throwaway harness runs. **A session id whose thread already exists returns 409** `{currentPhase}` unless the body carries `{force:true}` (C1). A forced start seeds `buildFreshStartState()` (`lib/api-helpers.js`), which clears EVERY state channel except `theme`, `sessionId` and the new `rawSessionInput` — including the photo channels (`sessionPhotos`, `preprocessStats`, `photoAnalyses`), the raw full-context inputs and the parse. Fresh start is its OWN list (`FRESH_START_CLEARS` in `lib/workflow/state.js`), never a rollback target: `buildRollbackState('input-review')` deliberately preserves everything upstream of the parse, so seeding a start from it kept the old photos, roster and parse and paused once on them.
- `/api/session/:id/resume` (POST) - Resume existing workflow (re-invoke at current state). NON-BLOCKING: returns `{status:'processing'}` immediately, runs the graph in the background, and delivers the result via the `/progress` SSE `complete` event (same contract as `/approve`). Clients MUST use SSE-before-POST. (A long re-invoke would otherwise exceed undici's 5-min `headersTimeout` / Cloudflare's ~100s edge timeout on a held-open POST.) **A COMPLETE thread returns 409** `{currentPhase:'complete'}` unless the body carries `{force:true}` — re-invoking a finished thread replays it from START, and every skip condition is already satisfied, so the whole paid pipeline re-runs unattended and overwrites the session's inputs and published report (B9). A thread from before the story meeting returns 409 `{oldThread}` first, `force` or not (task 4.11; see **Threads from before the story meeting**).
- `/api/session/:id/approve` (POST) - Submit checkpoint approval. A thread from before the story meeting returns 409 `{oldThread}` (task 4.11).
- `/api/session/:id/rollback` (POST) - Roll back to checkpoint. NON-BLOCKING (same contract as resume/approve); the SSE completion payload carries `rolledBackTo` + `fieldsCleared`. **A rollback also invalidates the evaluations it makes stale** (I1): `buildRollbackState` appends `{phase, ready:false, reason:'rollback-invalidated', source:'rollback'}` for `article` when rolling back to `article`, `outline`, `photos` or `character-ids` (the outline's stub went with the outline judge, brief 4.6; see `PHASES_INVALIDATED_BY` in `lib/api-helpers.js`), because those four points preserve `evaluationHistory` and `evaluatePhase`'s skip logic returns early on a most-recent entry that is `ready:true` or (since 3.9) escalated to the director — so without the stub the regenerated article skipped both the Opus evaluation and the programmatic fact-check and the gate opened on the PREVIOUS article's verdict. `arc-selection` and everything upstream clear the history outright, so they need no stub. A rollback to `arc-selection` reopens the story meeting with no model call, the weave kept as the director left it (R9; see **The story meeting**), and a rollback to `outline` reopens the map the same way (see **The map**). A thread from before the story meeting may roll back only to `arc-selection` or a point before it, and every later point returns 409 `{oldThread}` (task 4.11).
- `/api/session/:id/state` (GET) - Get current state
- `/api/session/:id/state/:field` (GET) - Get single state field
- `/api/session/:id/checkpoint` (GET) - Get checkpoint info: `{sessionId, currentPhase, interrupted, checkpointType, checkpoint, theme, inProgress, lastOutcome, oldThread}`. `checkpoint` is the SAME merged payload the SSE/approve path delivers (`buildCompleteCheckpointData`, so state extras like `sessionPhotos` are included), or null when not interrupted. `inProgress` is `isSessionLocked(id)` and `lastOutcome` the persisted outcome, so a client can reattach to a run instead of blind-POSTing into a 409 (H1, H2, H8). `oldThread` flags a thread from before the story meeting, whose stop is sent as `{type, oldThread}` alone; one at no stop has the flag and a null `checkpoint` (task 4.11; see **Threads from before the story meeting**).
- `/api/session/:id/progress` (GET, SSE) - Stream pipeline progress events

**Utility:**
- `/api/health` (GET) - Health check
- `/api/config` (GET) - Client configuration: `{notionConfigured, allowNonstandardSessionId, parkedThemes}`. The console validates the session ID against the same MMDDYY contract `/start` enforces, so it needs the `ALLOW_NONSTANDARD_SESSION_ID` opt-out. `parkedThemes` is `PARKED_THEMES` (R1): each theme `/start` refuses, with the line it refuses it with, which the start form shows beside that theme's choice (task 4.8).
- `/api/browse` (GET) - List session data files
- `/api/file` (GET) - Read session data file

See `server.js` for detailed usage and request/response shapes.

**Non-blocking endpoints** (`/start` excepted — it interrupts in seconds): `/approve`, `/resume`, `/rollback` all run their `graph.invoke` in the background via `lib/api-background-runner.js#runGraphInBackground` (one source of truth for the CONC-1 lock + DUR-2 drain + DEL-1 outcome + SSE `emitComplete`). The sessionId-keyed lock gives mutual exclusion across all three; a concurrent second call gets a 409.

|-----------|---------|-----------|
| `inputs/` | User-provided and AI-parsed inputs | session-config.json (with the accusation word for word, `accusationRaw`, `exposures`, and since phase 3 the classified `adjustments`, the totals check `ledgerCheck` and the `sessionClock`; the roster is stamped from the roster stop), director-notes.json, orchestrator-parsed.json, photo-descriptions.json (the director's per-photo descriptions, brief 2.2), character-ids.json |
| `fetched/` | Raw data from external sources | tokens.json, paper-evidence.json |
| `analysis/` | AI-generated intermediate outputs | evidence-bundle.json, arc-analysis.json, article-outline.json, map.approved.json (the map as the director approved it, brief 4.6) |
| `summaries/` | Checkpoint-friendly summaries | evidence-summary.json, arc-summary.json, outline-summary.json |
| `output/` | Final deliverables | article.html, article-metadata.json, content-bundle.approved.json (the bundle as the director approved it at the article stop; compare it with the last `reviseContent`/`generateContent` response in `llm-log/` to see every change the director made) |
| `llm-log/` | Per-call prompt/response log (`lib/observability/llm-call-log.js`), written on `llm_start` and rewritten on completion; disabled under Jest unless a test opts in. An ERROR record carries `diagnostics` at the record's TOP level, as a completion does — not nested inside `error`, which holds `{message, errorName, schemaErrors}`. `diagnostics.servedModels` names the model(s) that answered (the record's `model` is the alias asked for); `diagnostics.refusal` marks a declined call; `diagnostics.refusalSignal` marks a completed call that a refusal signal preceded | `<yyyymmdd-HHMMSS>-<context>-<callId8>.json` per call, index.jsonl (with `servedModels`) |

For complete directory structure and file descriptions, see `PIPELINE_DEEP_DIVE.md#data-directory-structure`.

## Top-Level Directory Map

| Path | Purpose |
|------|---------|
| `data/{session-id}/` | Per-session pipeline state (inputs/fetched/analysis/summaries/output) — one folder per `--session` ID |
| `outputs/` | Published reports (`report-MMDDYY.html`) and refinement working files (`-refsheet`, `-findings`, `-editplan`, `-draft`, `-copyedit`) — see "Refining Generated Reports" below |
| `assets/images/{MMDDYY}/` | Per-session photos used in published reports (`notion/`, `photos/`, `whiteboard.jpg`) |
| `sessionphotos/{MMDDYY}/` | Raw session photo dumps before curation into `assets/images/` |
| `archive/` | Retired prompts, deprecated reports, and superseded remote-access docs — read-only history |
| `lib/`, `console/`, `templates/`, `scripts/`, `__tests__/` | See sections above |
| `report*.html` (root) | Loose published reports kept at root for direct browser access; new reports go in `outputs/` |

## Refining Generated Reports

Pipeline-generated reports contain systematic factual errors that read as plausible. The repo has a structured **two-pass refinement workflow** driven by the user-level `refining-aln-reports` skill (auto-loads when you mention reviewing/editing a session report).

**Working-file convention** (in `outputs/`, all prefixed `report-MMDDYY-`):

| Suffix | Pass | Purpose |
|--------|------|---------|
| `-refsheet.md` | Pre-read | Ground truth built from source data (`data/{id}/`) BEFORE reading the article. Roster, pronouns, accounts, transactions, accusation. |
| `-findings.md` | Pass 1 (fact-check) | Claim-by-claim verification against refsheet. Flags fabrications, evidence-boundary violations, pronoun errors. |
| `-editplan.md` | Pass 1 (fact-check) | Section-by-section rewrite plan addressing findings. |
| `-draft.md` | Pass 1 output | Revised prose (Markdown, not HTML) after applying editplan. |
| `-findings-copyedit.md` | Pass 2 (copy-edit) | Examines the **fact-corrected** article (not the original) for pacing, redundancy, throat-clearing, abstract→specific. |
| `-editplan-copyedit.md` | Pass 2 (copy-edit) | Structural and sentence-level polish plan. |

**Two-pass discipline:** Fact-check and copy-edit are separate cycles. Copy-edit always operates on the fact-corrected article, never the original. Don't pattern-match em-dashes from older reference reports (they predate the no-em-dash rule).

**Final HTML output:** Published as `outputs/report-MMDDYY.html`. The matching `assets/images/MMDDYY/` directory must exist before publishing.

**Editorial intent fetch:** If the pipeline server is running, the refinement skill pulls the director's checkpoint feedback (`_arcFeedback`, `_outlineFeedback`, `_articleFeedback`, `weave`, `_rescuedItems`; `selectedArcs` went with the arc selection, R4) from `/api/session/:id/state/:field` to inform the refsheet.
