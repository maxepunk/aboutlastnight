This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**ALN Director Console** - AI-powered investigative article generator for "About Last Night" using Claude Agent SDK with LangGraph workflow.

Generates journalist-style investigative articles by:
1. Fetching memory tokens and paper evidence from Notion database
2. Curating evidence bundle using three-layer model (exposed/buried/context)
3. Analyzing narrative arcs via single SDK call with player-focus guidance
4. Generating article outline and final HTML report with human-in-the-loop checkpoints

**Production URL:** `https://console.aboutlastnightgame.com` (via Cloudflare Tunnel)

**Deep Dive:** For business context, game mechanics, phase-by-phase breakdown, and detailed debugging scenarios, see `docs/PIPELINE_DEEP_DIVE.md`.

## Architecture

### LangGraph Workflow (6 Phases, 45 Nodes)

```
Phase 0: Input Parsing (conditional) → Phase 1: Data Acquisition → Phase 1.6-1.8: Processing
→ Phase 2: Arc Analysis (player-focus-guided) → Phase 2.4: Evidence Packaging
→ Phase 3: Outline → Phase 4: Article → Phase 5: Assembly
```

*See lib/workflow/graph.js for complete node list*

**Human Checkpoints (11 total - workflow pauses for approval via native `interrupt()`; `photos` is conditional):**

For data flow at each checkpoint, see `PIPELINE_DEEP_DIVE.md#phase-by-phase-breakdown`.

| Checkpoint | Phase | Purpose |
|------------|-------|---------|
| `paper-evidence-selection` | 1.35 | Select which paper evidence was unlocked during gameplay |
| `await-roster` | 1.51 | Wait for roster input (names + pronouns). Photos are not needed yet. |
| `await-full-context` | 1.52 | Wait for accusation/sessionReport/directorNotes (incremental input) |
| `input-review` | 0.2 | Review AI-parsed session input. Dedicated node `checkpointInputReview`, reached as `parseRawInput → checkpointInputReview` (so an approve does not re-pay the parse), gating on the `inputReviewApproved` channel |
| `pre-curation` | 1.75 | Review preprocessed evidence before curation |
| `evidence-and-photos` | 1.8 | Approve curated three-layer evidence bundle |
| `arc-selection` | 2.35 | Select which narrative arcs to develop (3-5 recommended) |
| `photos` | 2.36 | Collect the session photo folder. CONDITIONAL: skipped when `photosPath` was given at /start. The photo chain runs here, after arc analysis, so a session can be parsed, curated and arc-analysed while the photos are still being curated. |
| `character-ids` | 1.66 | Map characters to photos based on Haiku's visual descriptions. Runs INSIDE the photo branch, after arc selection (its 1.66 phase number is historical). |
| `outline` | 3.25 | Approve article structure and photo placements |
| `article` | 4.25 | Final article approval before HTML assembly |

The photo branch keeps its original phase NUMBERS, so the badge CheckpointShell renders runs backwards there: Arc Selection 2.35, Photos 2.36, Character IDs 1.66. The numbers are historical labels, not an order (see the plan's ruling R3).

**Threads started before the photo branch existed pause once at `photos`** (R9), pre-filled with the path they were started with and answered in one click: the branch then skips on the `sessionPhotos`/`preprocessStats`/`photoAnalyses` they already carry, so nothing is re-paid. This applies to a COMPLETE old session too — any rollback replays from START, so a rollback to `outline` or `article` on a finished pre-branch thread also stops at `photos` on the way through.

**Checkpoint payload keys** (added by `getCheckpointData` in `server.js`; the console consumes these names):

| Checkpoint | Keys beyond the interrupt payload |
|---|---|
| `input-review` | `enrichment: {quotes, characterMentions, transactionReferences, fallback, warnings}` — counts from the director-notes enricher, so an empty enrichment is distinguishable from empty notes; `ledger: {clock, adjustmentsParsed, adjustments, accounts, mismatches, unclassified}` (phase 3, brief 3.5) — `lib/session-ledger.js` `ledgerReviewOf`: which clock rule applied, the adjustments beside each account's total and sale count, and a totals mismatch or "adjustments not parsed" |
| `arc-selection` / `outline` / `article` | `lastEvaluation` — the most recent evaluation **for that phase** (`evaluationHistory` is append-only and mixes phases, so its last entry is routinely another phase's verdict). Raw `evaluationHistory` is kept alongside it |
| `article` | `htmlPreview` (the pending bundle rendered through the publishing `TemplateAssembler`, with `<base href="/">` injected; `null` on any render failure), `sessionPhotos`, `factCheck` (see below) |
| `outline` / `article` | `trace` — the automatic passes of the current round, each with its diff (see **The trace** below); `[]` when none ran |
| `arc-selection` / `outline` / `article` | `writerQuestions` — the current output's questions for the director, `[{kind, about, question}]` (see **The writers' questions** below); `[]` when there are none |

**Approval payloads** (`buildResumePayload`): `{inputReview: true}` approves the parse; `{inputReview: false, inputFeedback}` rejects it with prose corrections: `checkpointInputReview` stores the round's correction as `_inputCorrections` (the trigger the re-parse consumes and clears) and appends it to `inputReviewCorrections`, the whole list in order, and `routeAfterInputReview` routes back to `parseRawInput`. Every parse prompt gets the whole list: steps 1 and 2, the enrichment and the whiteboard parse (see **The director's words as record**). At the character-IDs stop, `{characterIdsRaw | characterIds, photoDescriptions?}` carries the director's `{filename: text}` descriptions beside the ids; `buildResumePayload` refuses a malformed map. `{selectedArcs, outlineGuidance?}` carries the director's emphasis into the outline AND article prompts as their final `<DIRECTOR_GUIDANCE>` section. A rejection may carry the director's edited object — `{outline:false, outlineFeedback, outlineEdits?}` / `{article:false, articleFeedback, articleEdits?}` (spec `docs/superpowers/specs/2026-09-19-director-steering-design.md`). It is validated exactly like an approval, becomes the version the reviser starts from (`incrementOutlineRevision` copies it into `_previousOutline`), and its diff (`lib/hand-edit-diff.js`) is written to `_outlineHandEdits`/`_articleHandEdits`, which the reviser renders as a `<HAND_EDITS>` block between HUMAN FEEDBACK and the revision instructions. After EVERY reviser pass the report `_outlineHandEditReport`/`_articleHandEditReport` (`{checked, changed}`) is rewritten; `changed` means the rework no longer contains the director's edited value anywhere in the addressed collection (a PRESENCE check, so a relocated block still counts as kept). The revisers never clear the diff (an evaluator-driven second pass must still see it), the checkpoint clears both on approve, and the server resets both on every reject. Every note the director sends is appended to `directorGateNotes` with its kind: `rejection` for the note sent with a send-back, `approval` for `outlineNote` / `articleNote` sent with an approve (phase 1, 2026-09-20). It is a REPLACE channel the server appends to by writing the full array; `round` counts per stop and kind. `pruneGateNotes` drops the invalidated stops' REJECTION notes on a rollback to `photos`/`character-ids`/`outline`/`article` and keeps their approval notes, which are forward guidance for the writer the rollback creates; points at or above `arc-selection` clear the channel. Notes render as standing notes inside `<DIRECTOR_GUIDANCE>` for every later writer and reviser; `filterGateNotes(notes, currentFeedback, gate)` keeps the note a rework is acting on (already its HUMAN FEEDBACK) out of that list, and throws without a gate. Arc-selection GUIDANCE is not a note; it persists in `_outlineGuidance`.

**Programmatic article fact-check** (`lib/content-bundle-fact-check.js`): `evaluateArticle` runs `factCheckContentBundle` BEFORE the Opus evaluation, mirroring how `validateArcStructure` gates `evaluateArcs`. Pure string checks, no LLM: evidence-card fidelity (every substantial sentence of a card's `content` must appear in its source's `fullContent`/`content`/`description`/`text` — never its `summary`, which is the paraphrase a fabrication imitates), unknown card sources, leaked prompt-example strings, roster coverage, photo references, reporter mode, repeated absence statements (remote), and NPC pronouns. A structural failure under `REVISION_CAPS.ARTICLE` short-circuits the Opus call and routes straight to `reviseContentBundle` with one actionable line per defect; at the cap Opus runs and escalates to the human with the fact-check attached. The result lives in `_articleFactCheck` and reaches the article checkpoint as `factCheck`. **Every judgement call in the module errs toward NOT flagging** — a false structural failure costs a paid Opus revision. Two consequences of that rule (I2): the **reporter-mode scan reads NARRATOR text only** (`narratorText` — paragraph blocks plus headline/kicker/deck; NOT `visibleText`, whose generosity is for roster coverage), because a correctly attributed player quote saying “I voted” is the article doing its job; and the uncalibrated checks named in **`FACT_CHECK_ADVISORY_ONLY = ['npcPronouns', 'leakedExample', 'repeatedAbsence', 'emDash', 'productionWords', 'novaPronoun', 'length', 'headCount']`** push to `advisoryWarnings` only, never to `structuralIssues`. `repeatedAbsence` (phase 2) counts the narrator's first-person statements that they were not in the room, remote only, skipping double-quoted spans, and flags more than one; its message has its own prefix, `Absence stated N times (remote):`, which no console group claims, so the article stop lists it under Advisory. Card fidelity, unknown sources, roster coverage, photo references and narrator-scoped reporter mode stay structural. **Phase 3 (3.4) added five code checks, journalist only, each an advisory with its own prefix and its own console group** (`ADVISORY_GROUPS` in `console/checkpoint-view-logic.js`), none of them on the approve button's unresolved count. Each reads the narrator's prose with quoted spans stripped (`narratorSegments` + `stripQuotedSpans`: the headline, kicker, deck and paragraph blocks, never a card, a quote block, a caption or a quoted line) and says what it found and where: `emDash` (`Em-dash in the narrator's prose:`, C4), `productionWords` (`Production word in print:`: director, GM, game master, tier, timer, a bare "token"; T14), `novaPronoun` (`Gendered pronoun for Nova:`, T9), `length` (`Over length:`: the narrator's prose, `narratorText` whole, above 1,800 words, with the words per section; C4, R4) and `headCount` (`Head count:`: a statement of how many people were in the room that disagrees with the roster, which counts a guest reporter who plays a character once; vote and account counts never match, nor does a statement about part of the room, such as "the two people in the room who never sold" or "three players sat in the room and never said a word"; T10). The NPC check (`npcPronouns`, `Pronoun error:`) reads the same quote-stripped narrator prose for the journalist and takes the theme's NPC entries (`npcs`): Marcus written they/them or "she", and Blake (or the Valet) given a gendered pronoun that neither the director's words (`directorText`: notes, corrections, accusation) nor the roster give; it reads the subject and reflexive forms and the possessive "his" there, and leaves the object forms, "her" and "hers" out ("Blake paid him", "Marcus buried her exposé", "Marcus took what was hers": on the 53 published reports every "her" read after Marcus was someone else's, fix 3.4c, and "hers" goes with it, fix 3.4cb), reading "his" only when no preposition governs the name ("the buyer who sold to Blake spent his cut" is the buyer's), and it never scans Nova, whose rule is `novaPronoun`'s. `evaluator-nodes.js#buildFactCheckArgs(state)` builds every argument, for the node and for `scripts/lib/render-calls.js`. The journalist fix lines say what T8 and the remote mode block say (since 3.9; a rework reads each as must-fix): the vote line puts T8 in round 7's words (Nova never votes, joins the room's accusation or exposes a memory) and never sends the rework to name who acted, since an exposure stays anonymous unless the evidence log or the director's notes name who turned it in; the remote line says Nova monitored from outside the warehouse and has the moment told as a scene, with attribution where it matters; the `repeatedAbsence` line says Nova says so once, early, and tells the room's events as scenes after it. No fix line carries an em-dash. The photo check no longer reads the top-level `photos` list, which never prints, and it reads a photo the director excluded as no usable reference, so its fix line offers only kept photos (the 4b fix batch), and the whiteboard photo likewise: a printed whiteboard is an invalid reference, "this is the whiteboard, the room's working notes, and its photo stays out of the article", checked even when the session's photo list is empty (`whiteboardPhoto`, from `whiteboardFilenameOf`; the 4c fix batch). The detective keeps today's checks and messages. To promote an advisory check after a live session supports it, drop its name from that list and push its message to `structuralIssues` at the marked call site — but do NOT reword the message: `console/checkpoint-view-logic.js` groups by message prefix.

**The judges read the rule set** (phase 3, brief 3.4). Each journalist judge's system prompt is its identity line, the session's mode block (`withReportingModeBlock`, the writers' placement), the world and the truth rules (`loadRuleSet('judge-arc' | 'judge-outline' | 'judge-article')`, its writer's list), then its instructions; its user prompt ends with its writer's craft files, after the material it judges (`renderJudgeCraft`). Each judge scores the truth rules as structural **truth criteria** (`TRUTH_GROUPS`, `truth: true`, with `rules` and no weight): `evidenceTruth` (T1, T3, T4, T6), `moneyTruth` (T5), `verdictTruth` (T2), `stagesTruth` (T7), `novaPositionTruth` (T8), `playersTruth` (T9, T11), `wordsTruth` (T12), and for the outline and article `photosTruth` (T13) and `fictionTruth` (T14); arcs place no photos and print nothing. Each criterion asks only what its judge can check against its own prompts and what the judged output can hold, because a clause the judge cannot check scores low and sends the draft to a rework with nothing to fix: a group is worded per judge, and its `reads` names the material it checks by the heading `TRUTH_MATERIAL` gives, which the tests find in that judge's prompts. So only the article's `wordsTruth` asks about card text; the outline's `photosTruth` asks only that each photo it places comes from its PHOTOS list, the article placing the rest (an outline has one photo slot per arc and one in FOLLOW THE MONEY, and no caption), and the article's that it prints every photo in its PHOTOS and no other, each caption keeping the director's description. Since 3.9 the article writer's and judge's PHOTOS is every photo the director kept, so T13's every-photo check is the article's (the integrator's ruling). `moneyTruth` (3.9; T5, R11) asks whether the money runs from the buyer to the seller's chosen account, with NeurAI and its board written as Nova's suspicion of who the buyer is, and checks each figure against the timeline at all three judges and against the writers' FINANCIAL_SUMMARY at the outline and article judges. A breach is written as a structural issue that opens with its rule ids and quotes the text at fault beside the record it contradicts, and `createEvaluator` holds an output whose truth criterion scored below `STRUCTURAL_PASS_SCORE` (0.8, defined in `node-helpers.js` since 3.10) to not-ready whatever the judge's `structuralPassed` says, adding the criterion's notes under its rule ids when the judge wrote no issue for it (`failedTruthCriteria`, `truthIssueLines`), so the evaluation bar lists it among the must-fix, labelled. A truth criterion the judge leaves out of its scores counts as not scored: it is logged by name (`unscoredTruthCriteria`, "Truth criteria not scored: …") and does not hold the output. Craft findings go in `advisoryWarnings`, naming their item: an editor's note for the director, never a blocker and never a rework's task (R22), and nothing in code holds a draft on an advisory, a truth-labelled one included. Every existing criterion keeps its type and weight and names the rule or craft item it scores (C2 for `arcSectionFlow`/`arcThreading`, with no every-arc-in-every-section; C16 for `convergence`; "about 1,500 words" for `sectionBalance`/`wordBudget`; no pull quotes in `visualMomentum`; C3 for `coherence`, which faults only facts that cannot both be true; T8 for `reporterMode`, with exposures by turn-in). Since 3.9 (R2, R22) a structural criterion asks what the plan's wording asks and carries no craft clause: `antiPatterns` scores only C4's em-dash house rule and T14's production words (length is the fact check's advisory and a craft finding), `requiredSections` that each printed section earns its place, `arcThreading` that every section is an essential part of one narrative, and `visualDistributionPlan` that the photos spread through the article. C9 states the card counts, so the journalist article judge carries no card-count line of its own (the detective's keeps one). The arc judge reads the director's notes under its writer's own label, not as ground truth: its `directorNotes` line prints `ARC_NOTES_LABEL`, imported from `arc-specialist-nodes.js`, so the writer's label and the judge's are one text. Its NPC list reads each canon line from `theme-config.js` (M26). The scoring rule says how the score is made: the weighted average of the weighted criteria (M30). The article judge reads only the bundle's printed fields (`printedBundle`: never `voice_self_check`, pull quotes, the top-level photos, a sidebar entry's content or owner, or the writer's tracker when the page prints the ledger's; when no `state.shellAccounts` account has a positive total the page prints the writer's tracker, so the judge reads its entries' descriptions and amounts and its total). **The card check reads only printed text** (phase 2 slice 2.5). Card fidelity reads inline `evidence-card` blocks only. A sidebar entry (`evidenceCards[]`) prints its significance, headline and summary and never its `content` or `owner`, so it is checked for a known document id and nothing else (a made-up id prints a headline about nothing); its `content` is not scanned for leaked examples either. `isVerbatim` strips each fragment's leading and trailing quotation marks before matching, and `normalize` folds every single and double quotation mark to `'` (092026's `ale003`, `mor003` and `95e749b7` were correct excerpts failed by those two faults). Roster coverage (`visibleText(bundle, theme)`) counts only what the theme's page prints: never sidebar `content`/`owner`, top-level `photos`, pull quotes or photo/hero `characters`, and on the detective page never the headline, the hero, the sidebar or a card owner; the evaluator passes `theme`. One report per defect: `cardFidelity` holds one item per document and outcome, `{tokenId, ok, reason, locations: [{placement: 'inline'|'sidebar', section}]}`, and one message per failing item, which names the places (`Evidence card "x" (in section "the-story", and in the sidebar) …`), so the console's card list (`cardFidelity`, with `cardLocationText`) and its counts (the strings) agree. The not-verbatim fix line says to keep the card and copy its sentences from the document with that id in `<RECORD>`; it never offers removal. The unknown-source and leaked-example lines still offer it. Each message keeps its prefix. The writer is no longer asked for `content` on a sidebar entry (`evidenceCards[].content` stays optional in the schema, described as not printed), and the article stop's sidebar editor edits the summary, not the content.

**The trace** (phase 2, brief 2.7): what the automatic passes of the current round did before the director reached the outline or article stop. Two REPLACE channels, `_outlineTrace` and `_articleTrace`, one per stop. `incrementOutlineRevision` / `incrementArticleRevision` append one entry on an AUTOMATIC pass only (a send-back rework writes none): `{pass, round, trigger: 'check'|'evaluation', findings: {structuralIssues, advisoryWarnings, criteriaScores, revisionGuidance}, before, at}`. `before` is the whole outline or bundle the rework started from, because the reworker clears `_previousOutline`/`_previousContentBundle` on every exit; `findings` is copied from `validationResults` (only when it is stamped for that phase), because the next evaluation overwrites it; `trigger` comes from `automatedRevisionSource`. The increment also drops entries from another round, so a channel holds at most the automated budget's two. Each channel is cleared exactly where its side's hand-edit fields are: in the reject arm of `buildResumePayload` (a send back opens a round), in the approve return of `checkpointOutline` / `checkpointArticle` (approval ends the round; the llm-log keeps every pass's prompts and responses for a later readout), and at the rollback points that clear that side's `_xFeedback` (the outline's at ten points, all but `article`; the article's at all eleven). **Structured Output Contract:** When `jsonSchema` is provided, the call returns a schema-valid object or throws `StructuredOutputExtractionError`. The wrapper sends the schema to the SDK's `structured_output` channel and validates the result; if the SDK channel ever skips (see #277 below), it falls back to extracting JSON from the `result` text and validating it against the schema.

**SDK #277 channel skip — root cause is the `format` keyword (FIXED 2026-06-23, branch `fix/sdk-format-channel-skip`).** [anthropics/claude-agent-sdk-typescript#277](https://github.com/anthropics/claude-agent-sdk-typescript/issues/277) (OPEN, `bug` label): the SDK's constrained-decoding subsystem (triggered by `outputFormat: { type: 'json_schema' }`) can fail silently — returning `subtype: 'success'` with `structured_output: undefined` and `stop_reason: end_turn`, so the model emits JSON as `result` text instead of via the tool channel. We long attributed this to schema *shape* (nested `additionalProperties:false` + `oneOf` + `$ref`), but a single-variable opus probe proved the actual trigger in this SDK build is the JSON-Schema **`format` keyword** (e.g. `format:"date-time"`) — NOT `oneOf`/nesting/`additionalProperties`, all of which keep the channel engaged. `content-bundle.schema.json` carried one `format:"date-time"` on `metadata.generatedAt`; removing it re-engages the channel for content-bundle generation AND revision (both themes), verified live on session 062126. (Note: the claude-api structured-outputs doc lists `format:date-time` as *supported* — this SDK build empirically chokes on it.)

**The fix (two layers, both in place):**
- `format` removed from the two schema files that had it (`content-bundle.schema.json` metadata.generatedAt, `preprocessed-evidence.schema.json` preprocessedAt) — both validated server-stamped timestamps, so zero validation lost.
- **Guardrail** — `lib/llm/client.js#sanitizeSchemaForSdk` strips `format` (only string-valued, so a data property *named* `format` survives) plus `$id`/`$schema` from any schema before it reaches `outputFormat`, memoized per original object and fed to BOTH the SDK channel AND the extractor. So a future `format:` can't silently regress the channel, and the SDK constraint can't disagree with post-hoc validation. The memo + `$id`-strip also avert an ajv `"schema with key or id 'content-bundle' already exists"` collision across generation→revision in one process (the extractor's module-level ajv registers `$id` globally). **Never re-add `format` to a schema passed to the SDK** — the guardrail strips it, but keep the schema files clean.

**Retained as defense-in-depth** (the SDK channel is the normal path now; these are backstops if it ever skips again):
- The embedded `<SCHEMA>` text in `lib/prompt-builder.js#buildArticlePrompt` / `lib/workflow/nodes/ai-nodes.js#buildArticleRevisionPrompt` (gives the model the shape contract directly), and since phase 3 (fix 3.2b) the journalist outline writer's and reworker's `<SCHEMA>` (`outline.schema.json`).
- `lib/llm/structured-output-extractor.js` path 2 — text extraction + ajv validation.
- The `channel` field on `llm_complete`/`llm_error` tells you which path fired (`structured_output` = SDK tool channel, the normal path now; `text_fallback` = channel skipped, we extracted from text — should no longer occur for content-bundle).

**`loadProjectSettings` flag:** Controls filesystem-settings scope:
- `false` (**default**, flipped 2026-09-18 for H22) → `settingSources: []` — pure SDK isolation
- `true` → `settingSources: ['project']` — loads project `.claude/skills/` and project `CLAUDE.md` only

We never load user-level (`~/.claude/`) or local sources. A probe found those contribute ~86K tokens of irrelevant context (superpowers meta-skill, MEMORY.md, MCP server instructions, two `CLAUDE.md` files) that none of our SDK calls use. **Project scope is not free either (H22):** this `CLAUDE.md` (~9.4K tokens), `.claude/settings.json` `enabledPlugins`, skill frontmatter and the nine agent descriptions come to ~15.5K tokens per call and ~75K per session, and nothing in the pipeline reads any of it (`ThemeLoader` loads its prompt files with `fs`). Hence the default is OFF; a call that genuinely wants the project skill asks for it. This is pure context hygiene — it does NOT prevent the channel skip described above; that's a separate SDK bug.

**Tool gating (H21):** `allowedTools` is a permission AUTO-ALLOW list in this SDK, not a restriction (0.3.282 `sdk.d.ts`: "To restrict which tools are available, use the `tools` option instead"), and it is a no-op under `permissionMode: 'bypassPermissions'`. A call with neither `tools` nor `disableTools` runs with the full set, **Bash/Write/Edit included** (and the default set changed across the 0.3 line). Every pipeline call now declares one: `disableTools: true` for pure text/structured output, `tools: ['Read']` for the two image calls. The server-start health call (`isClaudeAvailable`) passes `disableTools: true` as well. **MCP servers are gated separately:** `settingSources: []` does not stop the SDK loading the user's `~/.claude.json` MCP servers (the claude.ai connectors — a `tools: []` call still reported 103 `mcp__` tools, Gmail included, at `init`), so `client.js` always passes `mcpServers: {}` + `strictMcpConfig: true` (pinned by `lib/__tests__/sdk-mcp-isolation.test.js`). The tool names `init` reports on a pipeline call must be exactly the tools the call declared, plus `StructuredOutput` when the call has a schema: CLI 2.1.282 counts its own structured-output tool (at the 2026-09-25 gate an Opus call with `disableTools` and a schema reported `StructuredOutput` alone, a Haiku image call `Read` and `StructuredOutput`), which the 2026-09-19 probes on the old CLI did not. Any other tool, or a missing one, fails the isolation probe by name (`scripts/lib/probe-verdicts.js#isolationVerdict`). **Auto-memory is gated the same way:** the subprocess loads the operator's `~/.claude/projects/<cwd>/memory/` regardless of `settingSources` (a probe showed the model reading MEMORY.md's 33 entries), so `client.js` passes `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` through `options.env`; `init.memory_paths` must be absent (`lib/__tests__/sdk-memory-isolation.test.js`). Both are checked live by `scripts/probe-sdk-isolation.js`.

**Model Call Limits (idle timeout + cost ceiling):** SDK calls use a **15-min IDLE/stall timeout**, not a total-duration cap — the timer is re-armed on every streamed message (including the token-level `includePartialMessages` deltas emitted as `llm_delta`), so a legitimately long call (big prompt + extended thinking) survives as long as it keeps producing; only a genuine stall (no streamed activity for 15 min) aborts. A stall throws `SDK timeout after … idle … with no streamed activity`, which `isSdkTimeoutError` recognizes and `isTransientError` (`lib/llm/retry.js`) classifies **transient** (the node-level `retryPolicy` consumes this to auto-retry transient SDK failures). A runaway call is bounded separately by a **per-call `maxBudgetUsd` ceiling** (`MODEL_BUDGETS` in `lib/llm/client.js`: opus $100, sonnet $50, haiku $10). The pipeline runs on the director's subscription, so the figure is not a cost: the SDK derives it from token volume at list prices, and it exists only to stop a stuck loop before it burns the rate limit unattended. An overrun throws a labeled **non-transient** `error_max_budget_usd` that is never auto-retried (the budget is per-CALL, so N node-retries can cost up to N× the ceiling). Steady-state latency is still captured per-call via `duration_api_ms` on the `llm_complete` event (`lib/observability/progress-bridge.js`).

**Effort and thinking (operator gate 2026-09-19; Opus 5.5 since 2026-09-25):** `EFFORT_LEVELS` sets `xhigh` for opus and sonnet, sent explicitly on every call (Opus 5.5 defaults to `medium` when none is sent). The levels did not move with the Opus 5.5 pin; the 2.0 gate records every call's duration next to session 092026's first. On Opus 4.8, `xhigh` was a cliff for extraction-shaped prompts: the director-notes enrichment ended its first turn after thinking alone (~320s, no output), the SDK's structured-output enforcement re-requested, and the call cycled for 20 minutes without completing while re-arming the idle timer (it looked like a stall). `lib/director-enricher.js` therefore passes `effort: 'medium'` (165s; `high` 375s; both complete). The client also sets `thinking: { type: 'adaptive', display: 'summarized' }` for opus/sonnet — the default display on Opus 4.8 / Opus 5.5 / Sonnet 5 is "omitted", which streams thinking as EMPTY blocks, so a long think is a silent stream and the console's THINKING stage shows nothing. Opus 5.5 cannot run with thinking off (`disabled` and `budget_tokens` are both a 400), so on Opus the summarized text is also what keeps the idle timer fed. Arc analysis (286s) and outline/article generation completed at xhigh in the same run; if one of them ever shows the empty-thinking → `status: requesting` cycle, lower its effort per call.

**No model fallback:** the pipeline's calls are always served by their pinned model, never a substitute (integrator ruling, 2026-09-25). `client.js` sets `CLAUDE_CODE_NO_MODEL_FALLBACK=1` in `options.env` (pinned by `lib/__tests__/sdk-memory-isolation.test.js`, which holds the env to `process.env` plus exactly the three switches). In CLI 2.1.282 this is "the no-fallback guarantee": it turns the refusal fallback off (that lane's gate reads both this and `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK`), builds the availability fallback chain as the primary model alone, blocks model substitution, and makes a compaction that would need another model an error instead of a swap. An overload the CLI can then route nowhere ends the call as an `is_error` result whose assistant error is `server_error` ("API Error: Repeated 529 Overloaded errors…"). `isTransientError` treats the assistant errors `server_error` and `overloaded` as transient, as the CLI's own classifier does, so the node retry policy retries the call on the same model (`retry.test.js`, `client-contract.test.js`). A numeric status decides first: every 5xx is transient (a gateway's 502 or 504 too), 429 is the one transient 4xx, and every other explicit 4xx is permanent, whatever the assistant error.

**A model that wrote part of the answer and is not the pinned one fails the call** (integrator ruling, 2026-09-25; corrected 2026-09-26). The models that wrote the answer are the ones named on the call's own assistant frames (`message.model` on frames with no `parent_tool_use_id`; `answerModels` in `client.js`). When any of them fails `servedModelMatches` against the model the call resolved to, the wrapper throws `SdkModelSubstitutionError` (`lib/llm/model-substitution.js`; "SDK model substitution: requested claude-opus-5-5, served by claude-opus-4-8 - <label>; the result is not used", `sdkSubtype: 'model_substitution'`, with `requestedModel`, `servedModels` (the answer's models) and `substituteModels`). It emits one `llm_error` carrying both lists, `servedModels` (the result's modelUsage) and `answerModels`; a schema failure the result also has rides along as `cause`, with its `schemaErrors` on the `llm_error`. `isTransientError` classifies it permanent, through `.cause` and the message marker. **The result's modelUsage is recorded, not judged:** it also lists the CLI's own helper requests. On 2026-09-26 (session 092626) a Sonnet session-report parse listed `claude-haiku-4-5` beside `claude-sonnet-5` there while every frame of its answer was Sonnet's; the first version of this rule judged modelUsage and threw the correct answer away. A call with no frame naming a model has nothing to judge and returns. A subagent's frames (a `parent_tool_use_id`) are not the call's answer; pipeline calls run none. A substitute after a refusal signal is a declined request instead (next paragraph). The isolation probe and `check-model-freshness.js` judge `answerModels` the same way.

**Declined requests (refusals):** since 0.3.162 a declined request ends with `stop_reason: "refusal"` and `stop_details: {category, explanation}`. The category is `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms` or null (the installed `@anthropic-ai/sdk` 0.128.0 types; the CLI treats it as an open string). `lib/llm/refusal.js` reads every place the 0.3.282 types allow: the result's `stop_reason`, the assistant frame's `message.stop_reason`/`stop_details`, a `message_delta` stream event, and the CLI's `system/model_refusal_no_fallback` notice. No live refusal has been captured through this SDK, so each source is optional and pinned by mock (`client-contract.test.js`). The wrapper throws `SdkRefusalError` ("SDK refusal (category: bio): claude-opus-5-5 declined the request - <label>", `sdkSubtype: 'refusal'`) before any result branch, and emits one `llm_error` carrying `refusal` (and `schemaErrors`: the extraction failure's when the refusal names one, else null). `isTransientError` checks a refusal FIRST, through `.cause` and the message marker, so it is never retried. The four nodes that re-wrap SDK errors (arc analysis, character data, the whiteboard, photos) keep the original as `cause`. The paths that swallow errors into state keep the message: the evaluators (`evaluationHistory._error`, `errors`), `reviseArcs` (which never takes a refusal for its free timeout retry), the enricher (`_enrichmentFallback.reason`) and interweaving (`_arcAnalysisCache.interweavingError`). **A declined request is never answered by another model** (integrator ruling, 2026-09-25). The bundled CLI has refusal fallback routes of its own, keyed on the requested model and independent of the `fallbackModel` option: for `claude-opus-5-5` it retries `bio` and `frontier_llm` on `claude-opus-5` and `cyber` on `claude-opus-4-8`. `client.js` turns them off with `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` in `options.env`, and `CLAUDE_CODE_NO_MODEL_FALLBACK=1` turns them off as well (both pinned by `lib/__tests__/sdk-memory-isolation.test.js`). A main-thread fallback that runs anyway (a `system/model_refusal_fallback` whose `scope` is not `local`, or an assistant frame that `supersedes` the refused frames) throws `SdkRefusalError` at once, naming the category and the fallback model, and the `llm_error` carries it as `refusalFallback`. Any other failure after a refusal signal (a schema failure, an iterator throw, no result, an idle abort) is thrown as `SdkRefusalError` with the original failure as `cause`, so a stall after a refusal is never retried as a transient `SDK timeout`. A refusal signal followed by a clean, schema-valid finish on another stop reason returns the result, and `llm_complete` carries the signal as `refusalSignal` (in `diagnosticsOf`, so the call log has it). The exception: when the result's `modelUsage` names a model that is not the one the call resolved to under `servedModelMatches` (`lib/llm/sdk-fields.js`, shared with the probe scripts; a `[1m]` or dated suffix is the same model), another model finished the declined request, and the wrapper throws `SdkRefusalError` naming that model (a schema failure, if there is one, rides along as its `cause`). A result with no `modelUsage` has no other model to name and returns. Without a refusal signal, the same `modelUsage` is a model substitution (previous paragraph).

**What the 2.0 gate reads:** the `init` forward carries `effort` and `memoryPaths` as well as `model`/`betas`/`toolCount`/`toolNames`/`permissionMode` (the isolation probe prints the names on every init line, with the expected set above them). Neither is typed for `query()` calls in 0.3.282 (`memory_paths` is absent from the public `SDKSystemMessage`; `effort` is documented for Remote Control frames), so both are forwarded raw and absent is normal. A loaded memory path prints as an error line. Every result envelope carries `servedModels`, read from the result's `modelUsage` (`canonicalModel` preferred) because the call log otherwise records only the alias and 0.3.174 added silent model fallbacks. A served model other than the pinned one fails the call (above), so the `answerModels` of a completed call name only the pinned model; its `servedModels` (the result's modelUsage) can also name a CLI helper model such as `claude-haiku-4-5`, or be null or empty (a zero-turn result carries an empty `modelUsage`). It reaches the per-call record, both SSE envelopes, `index.jsonl` and the console completion line (`served=`). One builder (`llm-call-log.js#diagnosticsOf`) makes the record's and both SSE envelopes' diagnostics. Open at the gate: whether the `context-1m-2025-08-07` beta, still sent to every non-Haiku call, is accepted, ignored or rejected on Opus 5.5 (1M native).

### Arc Analysis Architecture (Commit 8.15+)

Arc analysis uses **player-focus-guided split-call architecture**:
- Player conclusions (accusation + whiteboard) drive arc identification
- The director's notes are record for what happened and was said in the room; backstory in them is what Nova knows but the record cannot back, T1's third point
- Three-lens analysis (financial/behavioral/victimization), each lens noting where it supports an arc and where it cuts against it (C16)
- Returns 3-5 narrative arcs with evidence mapping
- `disableTools: true` flag prevents unnecessary tool invocations (pure analytical task)

**The rule set in the arc calls** (phase 3, briefs 3.3 and 3.10). The journalist arc writer, the interweaving call and the arc reworker read `loadRuleSet('arc')` / `loadRuleSet('interweaving')`: the world and the truth rules after the mode block in the system prompt (`coreArcSystemPrompt`, `interweavingSystemPrompt`), the craft files last in the user prompt, before `<DIRECTOR_GUIDANCE>`. The arc writer's SECTION 3 is the whole record view with its morning timeline (it passes the session config; its own buried list is gone), and the director's sentences about Blake and the Valet print from the stored `blake-proximity` tension through `directorTensionSentences` (`director-notes-renderer.js`), which drops the retired tension types. **Each rule is stated once** (spec section 8): C16, in `<craft-story>`, is the one statement of the lenses, the order of the threads (by how they bear on the room's verdict, TH2) and the convergence (one, near the end, where the thesis lands), and T1, in `<truth-rules>`, of the notes' status; the inline text maps them onto the output fields without restating them. SECTION 5 points at C16 (`<craft-story>`) for the lenses, and the `analysisNotes` placeholders name the three lens fields; the interweaving task's `suggestedOrder` / `convergencePoint` lines and the two schema descriptions (`SUGGESTED_ORDER_DESCRIPTION`, `CONVERGENCE_POINT_DESCRIPTION` in `subagents.js`, which the arc rework's addendum prints) name C16 the same way. The interweaving principles (shared characters as bridges, callback seeds, the four bridge types, the convergence role) are one text, `INTERWEAVING_PRINCIPLES` in `subagents.js` (3.10): the interweaving call's system prompt is built on it, and the arc reworker reads it once for the fields it returns; a principle that would restate C16 points at C16 instead (a callback seed is a detail the record holds, planted for the payoff C16 describes). The journalist interweaving call's own text follows C16 too (the 4c fix batch): its task finds each arc's shared characters and bridges and where the threads can meet, and its `callbackSeeds` placeholder and `keyCallbacks` description (`KEY_CALLBACKS_DESCRIPTION`) say what each field holds; "compulsive readability" and callbacks as "opportunities" are gone. The detective keeps its wording (D13). The notes label, `ARC_NOTES_LABEL`, reads "the record for the room, under T1" and adds only that backstory in the notes is what Nova knows but the record cannot back, T1's third point (3.10); `arc-specialist-nodes.js` exports it, so the arc judge prints the arc writer's own label. **The roster with pronouns** (3.10; T9): the arc writer, the interweaving call and the outline writer print the roster section the article writer and the judges print (`_rosterSection`, built without the character data: the roster lines with their pronouns and the NPCs' canon lines), so each player's pronoun reaches them once. At the gate the arc writer, given first names alone, asked the director five pronoun questions the roster stop had answered. The arc writer keeps its session roster too, whose first names decide `rosterCoverage`. `arc-specialist-prompts.test.js` holds each C16 term to as many occurrences as the rule files carry. The detective keeps today's prompts, sections and schemas (`DETECTIVE_*` in `subagents.js`; D13).

**Architecture Evolution**: See `lib/workflow/nodes/arc-specialist-nodes.js` header for history (8.12 parallel → 8.15 single → 8.28 split).

**Three-Category Character Model** (Commit 4193772):
- **Roster PCs**: Must appear in arcs (coverage validation): placed through the record, or, since phase 3 (3.7), named in a question to the director (journalist)
- **NPCs**: Valid but don't count (Marcus, Nova, Blake/Valet)
- **Non-Roster PCs**: Evidence-based mentions only (valid game characters not in session)
- **Canonical Name Preservation**: Accepts both "Sarah" and "Sarah Blackwood" as valid

For details, see `PIPELINE_DEEP_DIVE.md#three-category-character-model`.

**Arc Validation Routing (Commit 8.27):** Before expensive Opus evaluation, `validateArcStructure` performs programmatic checks (roster coverage, accusation arc present, evidence ID validity, and since phase 3 a valid source label: an arc whose `arcSource` is missing or invalid is sent back for one, never relabelled "discovered"). Structural failures route directly to revision, skipping evaluation. An accusation arc with no one to place survives when the verdict names no character (`isNoCulpritVerdict` or `blamesNoCharacter`). Since phase 3 (3.7) a journalist roster member a writer's question of kind `player` names counts as covered (see **The writers' questions**), and the check's fix line offers both ways to cover a missing player: a placement through what the record shows, or a question of kind `player` to the director. The check writes that guidance in code (`buildValidationRevisionGuidance`), so it reaches the automatic rework that follows, under the check's own label (the 4b fix batch; see **The rework rules**).

**Three-Layer Evidence Model:**
| Layer | Contains | Journalist Can |
|-------|----------|----------------|
| **EXPOSED** | Full memory content, paper evidence | Quote, describe, draw conclusions |
| **BURIED** | Transaction data ONLY (amounts, accounts) | Report patterns, NOT content |
| **DIRECTOR** | The director's notes; the whiteboard | Report the room's events and lines from the notes; read the whiteboard as context, never cite it |

What Nova can do with each layer is the rule set's: `world.md` ("What each memory became") and `truth-rules.md` (T1, T3 to T6, T13). `PIPELINE_DEEP_DIVE.md#three-layer-evidence-model` points at each layer's rules.

### Prompt Architecture

**The rule set (phase 3, tasks 3.1 and 3.8).** The journalist's rules are model-facing Markdown files in `.claude/skills/journalist-report/references/rules/`, written from the rule-set spec (`docs/superpowers/specs/2026-09-30-rule-set.md`): `world.md` (the article's purpose, the world, how a memory moves through the game), `truth-rules.md` (T1 to T15: the floor), eight `craft-*.md` files (C1 to C19: the engine, the craft rebuilt around the article's form in spec round 7) and the two mode files. The craft files group the items by the writer's job: `craft-story` (C1, C3, C16), `craft-form` (C2, C5, C6, C17, C18, C19, C14), `craft-material` (C8, C7, C10, C11), `craft-voice` (C12), `craft-judgement` (C13), `craft-telling` (C4), `craft-cards` (C9) and `craft-questions` (C15); task 3.8 regrouped the craft into them and deleted five of the ten files it had been split into. Each call reads the craft files spec section 8 gives it (`RULE_SET_CALLS`, every list in that order): the arc writer story, form, material, judgement and questions; the interweaving call the same without questions (it has no output for them); the outline writer every file but voice (`OUTLINE_CRAFT`); the article writer all eight; each judge its writer's list. An item is its heading (`## C16. …`, `## T8, remote: …`), stated once across the files (T8 once in the truth rules and once in each mode file), and a body may point at another item ("(T1)", "as T5 sets out"). `lib/__tests__/rule-set.test.js` lints the files: each item once, every pointer naming an item the set states, no em-dash, no gendered Nova, nothing on `lib/__tests__/fixtures/removed-phrases.js`, no old example accounts or sums. `lib/rule-set.js` is synchronous (readFileSync, cached for the process, so an edited rule file reaches the prompts on the next server start): `loadRuleSet(call)` for `arc`, `interweaving`, `outline`, `article`, `judge-arc`, `judge-outline` or `judge-article` returns `{core, craft}`, the world then the truth rules and the call's craft files (`RULE_SET_CALLS`), each wrapped in one tag named after its file; a reworker passes its writer's call; a missing or empty file throws, named. `loadModeBlock(mode)` returns the mode file in one tag named after it (`<mode-remote>`), as `loadRuleSet` wraps each file, so the system prompt's text after the block is not read as part of its "## T8" section. Tests pass `{root}`, and the pinned renders point the default root at the one-line stubs in `lib/__tests__/fixtures/rules/` (`setDefaultRulesRoot`), so a rule-text edit never moves a pin. Journalist only: a detective caller keeps its own text. Since 3.2 the outline and article writers and their reworkers read it, placed by the integrator's ruling: `core` (the world, the truth rules) in the system prompt right after the mode block, and `craft` last in the user prompt, after the data and before `<SHOULD_CONSIDER>`/`<DIRECTOR_GUIDANCE>`. The inline text the rule set states or contradicted went with it (the old financial block's "Blake now possesses all buried memories", the agency rule that kept Blake out of the room, the fixed section table, every arc in every section, pull quotes, the voice self-check, and the JSON shape restated in the outline prompt's own words, M27), and the schema descriptions are shape only. The journalist outline writer embeds `outline.schema.json` itself as `<SCHEMA>`, after `SESSION_FACTS` and before the craft files, as the article writer embeds the content-bundle schema (fix 3.2b); the detective outline keeps its own JSON shape.

**Data Wiring (Commit 6ffeef8):**
- Memory tokens use `fullDescription` field (rich second-person narrative)
- Fallback chain: `fullDescription` → `content` → `description` → `summary`
- `extractFullContent()` helper ensures full quotable content (not summaries)
- Fixed in 3 locations: preprocessor, token routing, arc evidence packages

**The record view (phase 2 slice 2.1):** `lib/prompt-renderers/record-view.js` renders the evidence bundle as one `<RECORD>` section. Each exposed document is `<document id kind name owner layer="exposed">` with its full text as the body; the buried memories follow only as sales on the morning timeline, `<morning-timeline>` (phase 3, brief 3.5, in place of the old `<buried-transactions>`): `buildMorningTimeline(bundle, sessionConfig)` merges the bundle's sales (account, amount and time and nothing else; a memory no one sold has no line), the evidence log (`sessionConfig.exposures`, only for memories the bundle holds as exposed: the document id and the name on the turn-in) and the classified adjustments (`sessionConfig.adjustments`: the first-burial bonus, transfers) in time order, every logged time on the session clock (`lib/prompt-renderers/session-clock.js`: the parse stamps `sessionConfig.sessionClock`, decided on the first exposure or sale, never a setup row; at 5 PM or later every time shows AM for PM; a thread from before phase 3 decides from what it holds). Events go in order from the first of them, the adjustments included (`firstEventTime`), so a bonus logged before the first sale opens the timeline; the clock decision still reads only exposures and sales. Events in the same minute sit under that minute, the ledger's before the evidence log's, in no claimed order; each event's `minute` is its minute on the session clock in one format (`printClockMinute`, "07:50 AM"), which the group breaks on and its heading prints, so a minute the session report writes two ways ("07:50 PM", "07:51PM") is still one group. `renderRecordView(bundle, {buried, sessionConfig})`: the callers that print the timeline pass the session config (`prompt-builder.js` from `this.sessionConfig`, `buildInterweavingPrompt`, the outline and article judges). The id is `id`, else `tokenId`, else `notionId`, the order the fact check's source map keys on, so a rescued item (no `id`) is named by its Notion id, and `buildValidEvidenceIds` accepts a paper `notionId` for that reason. The owner is the record's own `owners[]`, never the bundle's `owner` (the preprocessor's guess); the text is the record's `fullDescription` or `description`, never a summary; an attribute with no value is left out. Only the parked detective's arc writer takes the documents alone in its SECTION 3 (`renderRecordView(bundle, {buried:false})`) and keeps its Buried Transactions list (`extractEvidenceSummary`, which keeps only the rows the view prints: `isBuriedTransactionRow`, exported by the view, is the one rule, and the detective arc judge's list applies it too). The journalist arc writer (since 3.3) and arc judge (since 3.4), the interweaving call, and the outline and article writers (both themes) take the whole view once, in the data part, before the rules. `buildOutlinePrompt` and `buildArticlePrompt` read it from `options.evidenceBundle` (`scripts/render-prompts.js` and the content-bundle probe pass it too). The outline's `<arc-evidence>`/`<evidence-context>` and the article's ARC EVIDENCE PACKAGES list each arc's documents by id and keep the quotable excerpts, with no five-per-arc cap. An instruction that sends a writer to a document's text uses `DOCUMENT_POINTER` ("the document with that id in <RECORD>"). Upstream, the preprocessor sends an exposed memory's `fullDescription` to Haiku, and never sends a buried memory at all: its item is made in code from the sale (`buriedMemoryItem`: the input's id, the account, amount and time, and a summary of the sale), because a memory's id and name name its owner (final fix wave). Every item a batched model call returns is keyed to its input item, never to the id the model echoed (`pairRepliesWithBatch`, exported by the preprocessor: by id, else by position when the model kept the batch's order, else by elimination, else the reply is rejected). On 092026 curation's Sonnet paper scoring (`scorePaperEvidence`) echoed a rescued email's Notion id with `583f-` missing, and its find-by-echoed-id merge kept the model's id and dropped `rawData` and `fullContent`, so every `<RECORD>` printed the email with no text. That merge now uses the rule and takes only the scoring fields from a reply (`scoredPaperItem`). An item it cannot place is kept, not dropped, as not scored (`notScored`, `excludeReason: 'scoringError'`, rescuable), so the evidence stop shows it as "never evaluated". The rescue cache is keyed on the input's own name. The preprocessor's merge uses the same rule as hardening (an input it cannot place keeps a fallback summary), so an input's id, record and disposition always survive, and its items keep their input order. And `extractCharacterData` reads `selectedPaperEvidence` and every exposed memory, in full, through the view. Machine-made material carries a label from `lib/prompt-renderers/derived-labels.js` saying who made it and that the record decides where they differ: the character context (arc writer, article roster section), the narrative tensions (arc writer, article; since the 3.6 fix batch their label says the gathered sentences are the director's own and record, and only the gathering is code's), the Haiku photo descriptions at the outline judge, and the director-notes indexes `<QUOTE_BANK>` and `<TRANSACTION_LINKS>` wherever the notes are rendered. The enricher links an observation to a buried sale by an opaque row key (`tx-1`, …) that `resolveTransactionLinks` maps back to the row, so neither its prompt nor the stored links carry a memory id, and `<TRANSACTION_LINKS>` prints each linked sale through the record view's transaction formatter (`buriedTransactionFields`: account, amount and time, the time on the session clock from the `sessionConfig` the block is given). Its three callers (the outline and article writers' `_buildInvestigationObservations`, the arc writer, the judges' `renderJudgeDirectorNotes`) pass the session config through `withSessionClock(sessionConfig, evidenceBundle)`, so a thread with no stamped clock and no exposures (092026's shape) prints its links on the clock its timeline decides from the bundle's sales. `lib/__tests__/buried-memory-sentinel.test.js` plants one buried memory everywhere one can enter and checks every prompt for its id, owner and text.

### Modifying Checkpoint Components

Each checkpoint component follows the same pattern:
1. Registers on `window.Console.checkpoints`
2. Receives `{ data, sessionId, theme, onApprove, onReject, onRollback, dispatch, revisionCache, pendingEdits }` props
3. Renders checkpoint-specific UI from `data`
4. Calls `onApprove(payload)` / `onReject(payload)` with the checkpoint-specific payload, or `onRollback(checkpointType)` to open the rollback modal

**Conventions:** `const` not `var`, direct destructured imports (no aliasing), `safeStringify` instead of `JSON.stringify`, CSS utility classes over inline styles, aria-labels on interactive elements, functional state updaters for Set manipulation, `useEffect` reset on data change.

Each of `Outline.js` and `Article.js` validates a pending hand edit through ONE local `gateEdits` helper that both the approve and the reject path call (the reject path passes `verb: 'send'`, so its message reads "Cannot send …"); a new path that sends edits goes through it too. ONE exception: `Outline.js`'s JSON editor (`handleJsonApprove`) keeps its own inline validation and its own message in the JSON error slot — `__tests__/unit/console-edit-gates.test.js` pins that file's validator call count at 2 for exactly that reason, and `Article.js`'s JSON path at 1 because it routes through the helper.

**`onRollback` is the only way a checkpoint may open the rollback modal.** It is the same `setRollbackTarget` callback the stepper uses, so Confirm goes through the existing streaming rollback. A component must NOT dispatch its own rollback action — ArcSelection's zero-arc dead end dispatched `SHOW_ROLLBACK`, which no reducer handles, so the only offered recovery logged `[state] Unknown action` and did nothing.

### Input-review reject flow (re-parse, not rollback)

`InputReview` is not approve-only. Approve sends `{ inputReview: true }`; Reject with Corrections sends `{ inputReview: false, inputFeedback: '<prose>' }`. `buildResumePayload` turns that into `{approved: false, feedback}`, and `checkpointInputReview` stores it as `_inputCorrections`, appends it to `inputReviewCorrections` (every correction of the session, in order), nulls `sessionConfig`/`directorNotes`/`playerFocus` so `parseRawInput` re-runs, and routes the graph back — `parseRawInput` appends every kept correction to every parse prompt, the whiteboard parse included, and the writers read them after the director's notes (see "The director's words as record"). A mis-parsed accusation, exposure, sale or quote is therefore fixed with a note, not with a rollback and a full re-collection. The roster, its pronouns, the reporting mode and the reporter's name are not: code stamps them from where the director entered them (the roster stop, the start form), no parse returns them, and a note leaves them as they are (phase 3, brief 3.5; spec D15). The parse's correction block says only that the corrections apply to what the parse reads from the source text. There is no `inputEdits` path (the key wrote a state channel nothing declared or read).

### Rolling back a COMPLETE session

A finished thread has no checkpoint (`GET /checkpoint` returns `checkpoint: null`), so neither rollback opener could be reached for it. `SessionStart`'s `'complete'` branch therefore loads the completion instead of resuming (resuming re-runs the whole paid pipeline): `SET_THEME` → `SET_SESSION` → `SESSION_COMPLETE_LOADED`, whose payload comes from `sessionStartLogic.completedResultFrom(checkpointResponse)`. That action sets `completedResult` plus `completedStepper`, and `app.js` renders `PipelineProgress` with `completedCheckpoints: CHECKPOINT_ORDER` above `CompletionView`, so every step is a rollback target and the existing `RollbackPanel` flow applies. Nothing is POSTed until Confirm. `CHECKPOINT_RECEIVED` clears `completedResult`/`completedStepper`, because App renders the completion branch BEFORE the checkpoint branch and a stale completion would hide the checkpoint the rollback just produced.

### Outline Editor Architecture (`Outline.js` + `outline-edit-logic.js`)

The Outline checkpoint's per-section editors (journalist LEDE / THE STORY / FOLLOW THE MONEY / THE PLAYERS / WHAT'S MISSING / CLOSING, and the 5 detective sections) are **thin wrappers**: each seeds `useState` from `EditLogic.init*(section)`, composes shared module-scope widgets (`TextField`, `EnumSelect`, `StringListEditor`, `ObjectListEditor`, `KeyValueEditor`, `actionsRow`), and on save calls `onSave(EditLogic.build*Payload(state, originalSection))` → `saveSectionEdit('<sectionKey>', payload)`. `EditLogic` = `window.Console.outlineEditLogic` (aliased at module scope in both `Outline.js` and `Article.js`).

- **All save/build/merge/validate logic is PURE and lives in `outline-edit-logic.js`, not in the React components.** Builders `deepClone` the original section, so untouched required/extra keys are preserved and NO stray keys are emitted (every section is `additionalProperties:false`). Builders keep blank rows — pruning/non-empty enforcement is the validation layer's job.
- **Edited outlines are schema-validated before article generation** (the B7 gate): client-side via `EditLogic.validateOutlineShape(outline, theme)` (dependency-free — blocks Approve + renders `.validation-error`) and server-side in `buildResumePayload` (`SchemaValidator` against `outline` / `detective-outline`, rejects invalid edits). Distinct from the generation-time `validateOutlineStructure` removed in 8.23 — this specifically gates HUMAN edits.
- **The journalist outline's six keys are optional slots** (phase 3, 3.2; TH4): a slot may be left out or empty, a section's `arcConnections` list only the arcs it carries, `convergencePoint` and an account's `inference` are optional, and `thePlayers.buried` / `whatsMissing.buriedItems` are gone (BU3). `validateJournalistOutlineShape` follows the schema and is never stricter (a test runs a corpus through both); the editors no longer show or write the retired fields, and `EditLogic.dropRetiredOutlineFields` strips them from an outline written before phase 3 when an edit starts (and from the JSON editor's text), so its edits still pass the server's schema gate. `buildResumePayload` diffs a send back's edits against the stored outline through the same function, so `_outlineHandEdits` records no removal of the two fields the director never made (fix 3.2b).
- **Edited ARTICLES have the same two gates:** `EditLogic.validateBundleShape(bundle)` client-side (blocks Approve from both the inline editors and the JSON editor) and the `content-bundle` schema server-side. `validateBundleShape` is deliberately never STRICTER than `content-bundle.schema.json` — `heading` stays optional, `metadata.generatedAt` is not required — because a false block on a bundle the server would accept is a dead end the director cannot clear. A test pins that direction.
- **Every container that holds a pencil must carry `article-block--editable`**, and the pencil has **two reveal modes** (pinned by `__tests__/unit/console-editable-pencils.test.js`):
  - `article-block--editable` alone → hidden until `:hover` / `:focus-within`. This is what the **article** gate uses: its 13 hosts are full-width per-block containers (paragraph, quote, list, evidence card, photo, pull quote, financial row, one-line byline) whose own first line reaches the top-right corner, and an always-on button landed on the prose at 19 of 54 rendered blocks.
  - `+ article-block--editable-always` → rendered at low opacity, full opacity on hover/focus. **Outline hosts only** (a short ALL-CAPS `<h4>` sits at the top-left, so the corner is free) plus a `padding-right` gutter. `Outline.js` routes all 13 of its hosts through its `ALWAYS` constant. Never put it on an Article host.

  `Outline.js` emitted neither class at any of its 13 call sites originally, so the whole editor layer was `display: none` forever. The always-visible rule is a **descendant** selector: across the three opt-in host shapes the button sits at three different depths, so a child selector silently misses two of them.
- **Reset effect** is keyed on `EditLogic.computeResetKey(data, revisionCount)` (collision-resistant) in both `Outline.js` and `Article.js`. Do NOT revert to a truncated `safeStringify(...).slice(0, N)` — it collides across revisions and leaks stale edits.
- **Wiring debugging:** the section→editor→builder→`saveSectionEdit` key→schema map is documented in `docs/superpowers/plans/2026-05-28-outline-rich-editor-fixes.md` (the implementation plan + bug→task table).
- **Known minor:** the list widgets key rows by array index, so removing a mid-list row can momentarily drop input focus (no data-correctness impact).

## API Reference

### Session REST API

**Step-by-step Pipeline Control:**
- `/api/session/:id/start` (POST) - Start new session with raw input. **The session ID must be the session date as MMDDYY** (`091826`), optionally with one extra digit for a second session the same day (`0918262`); anything else is a 400 (B1: the emailer builds each player's report link from this id, and `data/<id>/` + `outputs/report-<id>.html` are named after it). `ALLOW_NONSTANDARD_SESSION_ID=true` in the server's env opts out for throwaway harness runs. **A session id whose thread already exists returns 409** `{currentPhase}` unless the body carries `{force:true}` (C1). A forced start seeds `buildFreshStartState()` (`lib/api-helpers.js`), which clears EVERY state channel except `theme`, `sessionId` and the new `rawSessionInput` — including the photo channels (`sessionPhotos`, `preprocessStats`, `photoAnalyses`), the raw full-context inputs and the parse. Fresh start is its OWN list (`FRESH_START_CLEARS` in `lib/workflow/state.js`), never a rollback target: `buildRollbackState('input-review')` deliberately preserves everything upstream of the parse, so seeding a start from it kept the old photos, roster and parse and paused once on them.
- `/api/session/:id/resume` (POST) - Resume existing workflow (re-invoke at current state). NON-BLOCKING: returns `{status:'processing'}` immediately, runs the graph in the background, and delivers the result via the `/progress` SSE `complete` event (same contract as `/approve`). Clients MUST use SSE-before-POST. (A long re-invoke would otherwise exceed undici's 5-min `headersTimeout` / Cloudflare's ~100s edge timeout on a held-open POST.) **A COMPLETE thread returns 409** `{currentPhase:'complete'}` unless the body carries `{force:true}` — re-invoking a finished thread replays it from START, and every skip condition is already satisfied, so the whole paid pipeline re-runs unattended and overwrites the session's inputs and published report (B9).
- `/api/session/:id/approve` (POST) - Submit checkpoint approval
- `/api/session/:id/rollback` (POST) - Roll back to checkpoint. NON-BLOCKING (same contract as resume/approve); the SSE completion payload carries `rolledBackTo` + `fieldsCleared`. **A rollback also invalidates the evaluations it makes stale** (I1): `buildRollbackState` appends `{phase, ready:false, reason:'rollback-invalidated', source:'rollback'}` for `article` (and for both `outline` and `article` when rolling back to `outline`, `photos` or `character-ids` — the two photo-branch points preserve the arc verdict but regenerate both later phases; see `PHASES_INVALIDATED_BY` in `lib/api-helpers.js`), because those four points preserve `evaluationHistory` and `evaluatePhase`'s skip logic returns early on a most-recent entry that is `ready:true` or (since 3.9) escalated to the director — so without the stub the regenerated article skipped both the Opus evaluation and the programmatic fact-check and the gate opened on the PREVIOUS article's verdict. `arc-selection` and everything upstream clear the history outright, so they need no stub.
- `/api/session/:id/state` (GET) - Get current state
- `/api/session/:id/state/:field` (GET) - Get single state field
- `/api/session/:id/checkpoint` (GET) - Get checkpoint info: `{sessionId, currentPhase, interrupted, checkpointType, checkpoint, theme, inProgress, lastOutcome}`. `checkpoint` is the SAME merged payload the SSE/approve path delivers (`buildCompleteCheckpointData`, so state extras like `sessionPhotos` are included), or null when not interrupted. `inProgress` is `isSessionLocked(id)` and `lastOutcome` the persisted outcome, so a client can reattach to a run instead of blind-POSTing into a 409 (H1, H2, H8).
- `/api/session/:id/progress` (GET, SSE) - Stream pipeline progress events

**Utility:**
- `/api/health` (GET) - Health check
- `/api/config` (GET) - Client configuration: `{notionConfigured, allowNonstandardSessionId}`. The console validates the session ID against the same MMDDYY contract `/start` enforces, so it needs the `ALLOW_NONSTANDARD_SESSION_ID` opt-out.
- `/api/browse` (GET) - List session data files
- `/api/file` (GET) - Read session data file

See `server.js` for detailed usage and request/response shapes.

**Non-blocking endpoints** (`/start` excepted — it interrupts in seconds): `/approve`, `/resume`, `/rollback` all run their `graph.invoke` in the background via `lib/api-background-runner.js#runGraphInBackground` (one source of truth for the CONC-1 lock + DUR-2 drain + DEL-1 outcome + SSE `emitComplete`). The sessionId-keyed lock gives mutual exclusion across all three; a concurrent second call gets a 409.

## Refining Generated Reports

Pipeline-generated reports contain systematic factual errors that read as plausible. The repo has a structured **two-pass refinement workflow** driven by the user-level `refining-aln-reports` skill (auto-loads when you mention reviewing/editing a session report).

**Working-file convention** (in `outputs/`, all prefixed `report-MMDDYY-`):

| Suffix | Pass | Purpose |
|--------|------|---------|
| `-refsheet.md` | Pre-read | Ground truth built from source data (`data/{id}/`) BEFORE reading the article. Roster, pronouns, accounts, transactions, accusation. |
| `-findings.md` | Pass 1 (fact-check) | Claim-by-claim verification against refsheet. Flags fabrications, evidence-boundary violations, pronoun errors. |
| `-editplan.md` | Pass 1 (fact-check) | Section-by-section rewrite plan addressing findings. |
| `-draft.md` | Pass 1 output | Revised prose (Markdown, not HTML) after applying editplan. |
| `-findings-copyedit.md` | Pass 2 (copy-edit) | Examines the **fact-corrected** article (not the original) for pacing, redundancy, throat-clearing, abstract→specific. |
| `-editplan-copyedit.md` | Pass 2 (copy-edit) | Structural and sentence-level polish plan. |

**Two-pass discipline:** Fact-check and copy-edit are separate cycles. Copy-edit always operates on the fact-corrected article, never the original. Don't pattern-match em-dashes from older reference reports (they predate the no-em-dash rule).

**Final HTML output:** Published as `outputs/report-MMDDYY.html`. The matching `assets/images/MMDDYY/` directory must exist before publishing.

**Editorial intent fetch:** If the pipeline server is running, the refinement skill pulls the director's checkpoint feedback (`_arcFeedback`, `_outlineFeedback`, `_articleFeedback`, `selectedArcs`, `_rescuedItems`) from `/api/session/:id/state/:field` to inform the refsheet.
